# Granular monitor sync

Generated by Lazarus Project Assistant.

Change the remote-monitor synchronising process so a connected phone reacts quickly, and so the last committed conversation can be read with no link. The means is a smaller grain of transfer, not another frame type beside the ones already in flight.

This plan supersedes the sync portion of `Documents/Plan-20261029-035918.md`. That plan's libraries exist. The live wire does not use them. Do not reopen those items, and do not implement catalogue 3 beside catalogue 2. A build that still applies both `patch` and `event` to the screen is a failed cut, not a checkpoint.

Out of scope: pairing, TLS, HMAC, dictation, the image pixel pipeline, and a redesign of command idempotency. Command acknowledgements, pongs, and approvals must not wait behind content. They are not otherwise changed.

## 1. What the link does today

The phone and the IDE still speak catalogue 2 (`MonitorCatalogueVersion = 2` in `AssistantMonitorCodec.pas`). Catalogue 3 is specified in `Documents/MonitorProtocolV3.md` and is not the live wire. The October 2026 plan marked the event log, the Room store, and the sync applier complete. Those pieces were then left beside the old path. That is the drift.

Content moves as documents, not as slices.

- `PumpMirror` runs every 150 ms from `AssistantMonitorBridge.pas`. It builds a `patch` from dirty blocks. A pure suffix can be an append. The first patch, and any edit that is not a suffix, sends the whole block body. Busy, phase, and status text ride in that same patch, so a flag change is a content cursor step.
- Resume is answered twice. `TMonitorSession.ServeResumeFromMirror` runs on the connection thread. `TAssistantMonitorBridge.AnswerResume` runs on the IDE thread. A matching epoch becomes one `catchup` blob of every stored patch. Otherwise the host sends snapshot pages of the open turn. A turn that does not fit 32 KiB is split into one page per block, and each page still carries the whole block body.
- `TMonitorMirror.ObserveTurn` also records `turn_open`, `block_append`, `block_replace`, and `block_close`. Resume does not replay those events. It replays patches. The phone's `SyncApplier` only receives a decoded `event` (`LanSession.kt` offers the applier when `type` is `event`). The host does not send that type on the live path, so the applier does not see the stream the user is watching.
- The screen is `MonitorCoordinator` memory: patches, catchups, and snapshot pages. Room is a later full-document rewrite. `persistBoard` in `MonitorViewModel.kt` calls `saveScreen`, which keeps the previous `seq` and `streamId`. A repository watch can paint those rows back onto the coordinator. Two writers, and the cursor does not describe the text.
- The socket is still the 250 ms idle loop in `AssistantMonitorLan.pas` (`MonitorAcceptIdleMs`). One pass reads, then writes one buffer. Nothing wakes the thread when a frame is queued. `TMonitorOutbox` is not used by the session. The session has its own lanes and drops bulk at 32 frames (`MonitorOutboundQueueLimit`). A plan that does not fit is replaced with the sentence "The plan is too large to cache on the phone."
- The last measured host harness (`Documents/MonitorLinkBaseline.md`, 2026-10-29) was 4 frames/s, a first frame at 251 ms, and a pong at 8261 ms behind 32 bulk frames. Re-measure before quoting those numbers again. The idle write is still the structural ceiling until item 4.4 lands. Smaller payloads alone cannot meet a 150 ms response while the socket leaves once per quarter second.

The two features fail for those reasons. Connected response waits on whole blocks, history pages, and the idle poll. Offline reading depends on a debounced copy of the in-memory screen, not on the frames that arrived. A gap can leave the last flags on screen while later content is discarded. An empty page can be filed as the conversation.

## 2. The sync this plan installs

One grain. One cursor. One store. One resume answer. One outbound queue. No second decode path.

The cursor is the mirror head. The epoch string already stored by the host, and already kept by the phone as `hostEpoch` / `streamId`, is the stream id. Do not mint a second id. `conversation_id` is never `current`. The Room host key stays the installation host id the phone already stores, falling back to the pinned fingerprint only when that id is absent, so existing rows stay readable.

Three kinds of transfer:

- **State.** Latest value of one key. No sequence. Sent on change and before any content on resume. Keys required for a fast connected response: `status` (busy, sending, phase, status text, can-send, can-steer, can-stop) and `approval`. Other menus may follow. They must not block status.
- **Slice.** One mirror event, one sequence number. `turn_open`, `block_open`, `block_append`, `block_replace`, `block_close`, `turn_close`, `title_changed`. `block_append` carries `offset` plus at most 4 KiB of new UTF-8, split only on a code-point boundary. The phone applies a slice only when its sequence is the stored sequence plus one. A lower sequence is a duplicate. A higher sequence is a gap.
- **Fetch.** The phone asks for what it does not have: a block body from a byte offset, a turn that is not in the cache, an image, or the plan body. The host answers in pieces of at most `MonitorBlockDataBytes` (24 KiB). Fetches are not pushed on connect.

Connected behaviour:

- The phone paints the Room conversation as soon as it opens, then sends `resume` with conversation id, epoch, and sequence. It does not wait for a snapshot to show cached text.
- The connection thread answers from the mirror. The IDE thread is not on the content path. There is one answer.
- If the epoch matches and the log still holds every event after the sequence, the host replays those slices and nothing else. No catchup blob. No turn page.
- Otherwise the host sends state, then one outline (turn ids, indexes, prompt previews, block ids, byte lengths, no bodies), then slices for the open block only. Older turns stay in the phone cache or are fetched when shown. A gap repair must not delete cached rows until the replacement transaction commits. An empty observation is not a conversation and must not be filed as one.
- The live pump queues mirror events that have not been acknowledged. It does not build a patch from the last blocks it thinks it sent. A slice stays replayable until the phone acknowledges it. A socket drop does not lose it.

Offline behaviour:

- Room is the only conversation the UI reads, connected or not. Disconnect does not clear it. Commands that need the host are disabled. Reading is not.
- Each applied batch commits the rows and the sequence in one transaction. A process kill must not show text the cursor does not cover.
- The plan's row summaries are state. The plan body is a fetch, stored when it arrives. Never replace a body with an error sentence in order to fit a frame.

Transport, required for the connected budget:

- When a frame is queued, wake the listen thread. A pass writes until the socket would block, state and control before slices, slices before fetches.
- One queue. Use `TMonitorOutbox` or the session lanes, and delete the other. The log lane never drops a slice. If it passes its budget, close the link and let the phone resume.
- The 32-frame bulk cap must not apply to slices.

Budgets, from the existing plan, still the acceptance bar:

- IDE change to the phone screen while a turn streams: p95 under 150 ms on a LAN.
- Pong while slices are queued: under 100 ms.
- After a drop, the cached screen is visible immediately and the open-block gap is filled within 1 s, without re-sending cached history.
- With no network, the last committed conversation is readable, including stored bodies.

Do not grow `AssistantMonitorSession.pas`, `AssistantMonitorBridge.pas`, `AssistantMonitorCodec.pas`, `AssistantMonitorLan.pas`, `MonitorCoordinator.kt`, or `MonitorViewModel.kt` with the new path. Put host sync decisions in a new `AssistantMonitorSync.pas`. Put phone apply rules in the existing `SyncApplier` path or a new file next to it. Deleting the hybrid should shrink the old files.

## 4. Host sends slices

### 4.1 Mirror events are the only content the new unit produces
Status: not started

Add `Source/LazAssistantTools` is the wrong package. The unit belongs in `Source/LazAssistantMonitor/AssistantMonitorSync.pas`, registered in the monitor package. Interface uses stay limited to what the public types need. No form unit, no LCL.

The unit takes the mirror log and the resume request and returns the frames to queue. It does not read the assistant form. `ObserveTurn` remains the producer of `turn_open`, `block_open`, `block_append`, `block_replace`, `block_close`, and `turn_close`. Split a `block_append` or `block_replace` that exceeds 4 KiB into ordered slices with matching offsets before framing. A `block_replace` is only for a change that is not a suffix, and its body over 4 KiB is a deferred body: the event carries `deferred` and `body_bytes`, and the phone fetches with the existing `block_get` path (`ServeBlockGet`).

`PumpMirror` stops selecting dirty blocks and stops calling `ReplaceLivePatch`. The 150 ms timer may still notice a status or plan-row change. Those are state, coalesced to the latest value, and they do not allocate a content sequence. Do not set a "sent blocks" copy. Acknowledgement of the sequence is the only sent mark.

Keep the new unit under 1000 lines. If the page JSON in `AssistantMonitorMirror.pas` is only needed for the old push path, leave it until item 6.1 deletes that path. Do not add more page writers.

### 4.2 One resume answer, from the mirror, on the connection thread
Status: not started

`HandleResume` is the only resume entry. It calls the new unit and queues the answer. Remove the fall-through that queues `mmkResume` onto the IDE thread for content. `AnswerResume`, `SendCatchupSnapshot`, and `ServeResumeFromMirror` must not both send.

Rules for the answer, in order:

- State keys first, including approval when one is active.
- Epoch match and the log holds every event after the phone sequence: those slices, then stop.
- Otherwise: one outline frame, then open-block slices from the phone's stored offset when that offset is still a prefix, otherwise a deferred body and no inline text. Do not walk older turns.
- `commands` on the resume, if present, still get `command_states`. That reply is control, not content.

If the mirror has not observed the open conversation yet, send state and a short `not_ready` the phone can show without clearing its cache. Do not send an empty point page. The comment in `DeliverOpenScreen` and `SendCatchupSnapshot` about filing an empty page as the conversation is the bug this rule closes. When the form later observes real turns, the mirror appends events and the connection thread queues those slices. It does not start a second resume.

A parked mirror log for another conversation id is the resume source when the phone names that id. If that log was folded, use the gap answer. Do not wipe the phone by sending a blank outline for a conversation the host has not loaded.

### 4.3 State before content, and no truncated plan
Status: not started

Classify frames in the new unit, not with another copy of `OutboundLane` left to drift. Control and state are taken before slices. Slices are taken before fetches (`block_data`, `image_data`, plan body).

`PushPlan` stops packing the plan markdown into the plan frame. The plan state value is path, title, running, and the row summaries. The body goes out only in answer to a fetch, in 24 KiB pieces, and is stored by the phone when those pieces arrive. Delete the branch that substitutes "The plan is too large to cache on the phone."

Status flags move off the patch. A busy change is a state replace. Losing it and then receiving a later state is harmless. A content gap must not freeze the last busy flag: state still applies while content waits for resume.

### 4.4 Wake the socket and stop dropping slices
Status: not started

`TMonitorListenThread.ServiceIdle` must write every ready frame in the pass, stopping on `SSL_ERROR_WANT_WRITE` or an empty queue, not after one `SSL.Write`. Queueing a frame wakes the listen thread in the same turn. `AcceptIdleTimeOut` may stay 250 ms for accept. It must not be the send cadence.

Pick one queue. `TMonitorOutbox` already has the lane order, the per-key state replace, and the rule that the log lane does not drop. Wire the session to it and delete the session's `FControlSends`, `FLiveFrames`, `FPlanFrames`, and `FBulkSends` path, including `MonitorOutboundQueueLimit`. If that unit cannot express the plan-coalesce rule, extend it. Do not keep both queues.

A slice that cannot be queued because the log budget is exceeded closes the link with `bye`. The phone resumes. Incrementing `FFramesDropped` and continuing is not allowed for slices, state, or control. Fetches may be refused with `not_found` or by leaving them unsent until the phone asks again. They are not silently discarded after the phone has been told they were sent.

Re-run `Tests/AssistantMonitorLinkTest.lpr` after this item and add a row to `Documents/MonitorLinkBaseline.md`. The pass condition for this item is the harness, not a phone: pong behind a queued bulk transfer under 100 ms, and a resume answer started without waiting 250 ms for the first byte. If the harness still cannot be compiled in that session, say so and leave this item in progress. Do not record a guessed number.

## 5. Phone cache is the screen

### 5.1 Apply slices only, with the cursor
Status: not started

`LanSession` already offers a decoded `event` to `SyncApplier`. That becomes the only content apply. `MonitorCoordinator.incoming` must not apply `patch`, `catchup`, `snapshot`, or `snapshot_page` onto the conversation board.

`SyncApplier` already batches to 128 events or 50 ms and commits rows with the sequence in one Room transaction. Keep that. A gap emits resume and leaves committed rows in place. An append whose offset does not match the stored UTF-8 length emits `block_get` from offset 0 for that block and does not guess. Other blocks continue.

State frames update a small state row or the existing view fields. They do not advance the content sequence. Approval stays on the control path the session already applies at once.

Do not add this logic to `MonitorCoordinator.kt` or `MonitorViewModel.kt`. Those files are already far past a reviewable size. A new file next to `SyncApplier.kt` is the right place if the applier needs a state channel.

### 5.2 Open on the cache, including with no link
Status: not started

On launch, and on every reconnect, the conversation screen collects Room flows for the selected host and conversation and renders those rows. It does not wait for `hello_ok`, a point page, or `desktopMatched`. If the database has no row, the screen is the empty state, not a spinner that blocks the cached list.

Disconnect clears the connected chip and disables send, steer, stop, and approval. It does not clear turns, blocks, or the plan summaries already committed. Background and process death use the same rows. The sequence stored in the conversation row is the resume sequence.

`watchRepository` may paint Room into the UI. It must not be a second writer fighting `persistBoard`. After this item, the applier is the writer and the collector is the reader.

The offline list already reads `ConversationRecord`. Keep that list available with no address configured. Opening a row shows its stored turns and blocks. Images whose files are present decode from disk. Missing image bytes stay a placeholder, not a fetch, while the link is down.

### 5.3 Fetch what is on screen, and do not push the rest
Status: not started

After resume, the phone requests bodies only for blocks the outline marked deferred and that are in the visible range, plus a small prefetch. The coordinator already limits background turn requests. Keep a cap of two outstanding content fetches so a history fill cannot sit in front of a live slice. The host's state and slice lanes already go first once item 4.4 has landed. The phone must still stop asking for turns the user has not opened.

A turn request answers with slices or with one fetched turn page that the applier commits as rows. It does not replace the whole conversation. Visible-turn tracking (`noteVisibleTurns`) is the trigger. Scrolling back must not re-download a block whose stored byte length matches the outline.

Plan body: if the user opens the plan and the stored body is absent or older than the plan state revision, send one plan fetch. Store the pieces as they arrive so a drop keeps the prefix.

### 5.4 Stop the full-document live save
Status: not started

`persistBoard` and `ConversationRepository.saveScreen` must not run on the live path. They rewrite every turn and preserve the old sequence, which undoes item 5.1. Delete the call in `MonitorViewModel.kt` that saves the board when `board.revision` changes.

Keep a one-time import of any `monitor-cache` files that are still on disk, then do not write that format again. `saveImported` can stay for that import. New text reaches Room only through the applier, or through a fetch commit that uses the same transaction rule.

`OfflineCache.kt` helpers that exist only to copy the in-memory screen into a document become unused after this item. Delete them in item 6.1 if nothing else references them. Do not keep a second cache file beside `monitor.db`.

## 7. Prove the two features

### 7.1 Connected response on the host harness
Status: not started

Extend `Tests/AssistantMonitorLinkTest.lpr` so it measures the new grain, not only bulk frames. Record a row in `Documents/MonitorLinkBaseline.md`.

Required host measurements, on 127.0.0.1, with slices in flight:

- Time from queueing a state frame to the client reading it, p95 under 150 ms.
- Ping to pong while at least 2 MiB of slices are queued, under 100 ms, and the pong is not after those slices.
- Resume from a sequence near the head delivers the tail without an outline of every older turn.
- Resume from a sequence the log no longer holds delivers one outline and the open block, and the client still has its previous rows until it chooses to replace them.

A miss is a defect in items 4 or 6, not a note under this item. Leave this item in progress if the harness was not actually run.

### 7.2 Offline read and a gap
Status: not started

Kotlin tests, not a device:

- Commit three slices, close the store, reopen it, and read the same bodies and sequence with no socket.
- Apply a gap. The stored bodies remain. The following resume fills only the missing sequence. Status from a state frame still updates while the gap is open, including busy changing to false.
- Kill the applier mid-batch. The reopened sequence matches the rows. There is no body whose sequence was not committed.
- A plan body fetch stores a prefix if the link drops before `last`. The row summaries from state remain.

This item is the offline-reading proof the host harness cannot give. Do not mark it complete from a Pascal test.
