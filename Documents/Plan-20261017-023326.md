# Tasks Implementation Plan

Generated by Lazarus Project Assistant.

The Tasks… button is already on the assistant bottom bar, immediately before Settings…. It has a caption and no action. This plan wires that button to a list of named tasks. A task is a user-editable recipe: a mode, the evidence it requires, and either a prompt or a direct host action. Run starts the work. Edit opens a prompt editor. The user can add, duplicate, hide, and reorder tasks.

This is not a skill, and it is not a plan item. Skills stay on the system prompt. The plan runner stays on Run Plan. A task is one user turn, or one host action that does not call the model.

Working root is LazWorkflow. Do not edit EcologySurveyScheduler. Do not add a Tasks page to the settings dialog. `TAssistantConfig.SaveWithConnections` rebuilds the `assistant` section from fields it knows. A tasks array stored there would disappear the next time Settings is saved. Tasks live in their own `assistant_tasks` section.

Assumptions, used so Build can start. Correct them before Build if they are wrong:

- Run sends immediately. Insert fills the composer and does not send. A non-empty composer is not overwritten without a confirm.
- The store is IDE-global (`LazWorkflow.json`, section `assistant_tasks`), not per project. A project overlay is out of scope.
- Format Unit does not call the model. It uses `FormatPascalSource` and refuses to apply a result whose token fingerprint differs.
- Dead-code elimination does not delete in the first catalog. It reports. Deletion is a later task and only when a reference search covered every project Pascal file.
- Code review, simplify, optimise, and format stay separate turns. There is no workflow engine.
- Review Compile, Review Build, and Fix Error stay as they are. The new compiler tasks are the batch path. Fix Error remains the one-message path.

## 1. Decisions

A task without a scope will rewrite whatever the model feels like rewriting. Every built-in names the evidence it requires. If that evidence is missing, the host refuses and does not send.

Do not merge the requested list into one quality pass. Simplify plus dead-code deletion plus format is an unreviewable diff. Compiler errors and hints stay apart: a hint pass must not run while errors remain, and an error pass must not wander off into style. Technical documentation and the user manual are different readers. They share the document machinery and keep separate prompts and files.

Format does not belong in a prompt. `PascalStyleFormat.FormatPascalSource` and `TokenFingerprintsEqual` already exist under `Source/Tools`. An LLM format pass will drift house style and spend a turn to do it. The built-in formats the active Pascal unit in the editor buffer so Undo works. It does not save, and it does not format a selection: the formatter is whole-file, and a partial replace would corrupt the unit.

Dead code must not be judged with grep. An `.lfm` event, a published method, an override, and a call in an inactive branch all look unused to a text search. `QueryAssistantSymbol` can find references, but that query is not on the Grok tool list. The broker copy also caps `search_paths` at 32 files. Until a search covers the whole project and is not truncated, the honest result is a report, not a deletion.

Code review is Inspect, not Build. It must not be given write tools "so it can fix what it finds". The user can run a fix task afterwards. Review Compile already reviews the Messages window with tools off and starts a fresh conversation. Do not fold that into this button, and do not remove it.

These are worth having and are not built-ins. The user can add them from the editor:

- Add tests for the active unit.
- Plan a split of a unit that is over the 1000-line preference.
- Suggest a commit message. That path already exists: `SuggestCommitMessageHandler` calls `CompleteOnce` and does not use the chat.
- Rename. Local rename preview exists on the broker and is not on the Grok tool list. Do not add a rename task in this plan.

Explain Selection is the one extra built-in. It is Inspect, it requires a selection, and it is the cheapest way to read code before changing it.

Out of scope: a pipeline runner, per-project task files, a Tasks page inside Settings, raising the 32-file reference cap, and any task that commits, pushes, or formats the whole tree.

## 2. Task model

### 2.1 Add the task unit and the built-in catalog
Status: complete

Add `Source/LazAssistantTools/AssistantTasks.pas`. No forms, no IDE units, no `ProjectAssistantForm`. The unit owns the record, the catalog, JSON load/save, and placeholder expansion.

Record fields:

- `Id`: stable, unique, same character rules as `SkillNameIsSafe`. Not shown as the main label.
- `Title`, `Summary`: list text. Title is required.
- `Mode`: `inspect`, `document`, `plan`, `build`, or `chat`. Store the same words the skill grid uses.
- `Kind`: `prompt` or `format`.
- `Scope`: `none`, `active_editor`, `selection`, `changed_files`, `messages`, or `user_note`. Scope is what the run requires. An open editor inside the target is optional context, not a second scope.
- `MessageFilter`: `errors`, `warnings`, `hints`, or `all`. Used only for `messages`.
- `CompileFirst`, `FreshConversation`, `Enabled`, `Hidden`: booleans.
- `DocumentPath`: project-relative. Empty except for Document tasks that must update one file.
- `BuiltinId`: catalog id, or empty for a user task. Reset uses it. Hiding a built-in keeps the row so a later catalog does not resurrect it.
- `Prompt`: the template. Empty only when `Kind` is `format`.

Placeholders, and no others: `{project_name}`, `{active_file}`, `{cursor}`, `{selection}`, `{messages}`, `{git_status}`, `{git_diff}`, `{user_note}`. An unknown `{token}` fails expansion. A required value that is empty fails expansion. An optional value that is empty becomes `(none)`. Caps, with a truncation line when cut: selection 16000 characters, messages 48000, git diff 48000. Do not paste a whole unit into the prompt. The model has `read_file` when the mode allows it.

Seed these eleven rows, in this order, enabled, not hidden. Item 5.1 is the prompt text. This item only needs the ids, modes, scopes, and flags so the tests can lock the catalog:

| Id | Mode | Scope | Flags |
| --- | --- | --- | --- |
| code-review | inspect | changed_files | fresh conversation |
| explain-selection | inspect | selection | |
| bug-fix | build | user_note | |
| fix-compiler-errors | build | messages, filter errors | compile first |
| fix-compiler-hints | build | messages, filter hints | compile first |
| simplify-code | build | active_editor | |
| report-dead-code | inspect | active_editor | |
| optimise-selection | build | selection | |
| format-unit | format | active_editor | no prompt |
| technical-documentation | document | active_editor | path `Documents/Technical.md` |
| user-manual | document | user_note | path `Documents/UserManual.md` |

`DocumentPath` must be relative, start with `Documents/`, end in `.md`, contain no `..`, and must not be the active plan path. Do not register it as a plan.

On load, if the section is missing, use the catalog and do not write. If the section exists, keep the saved order and append any catalog id that is not already stored. A hidden built-in stays hidden. Reset copies the catalog row back onto that id and clears `Hidden`, without moving it.

### 2.2 Save tasks in their own settings section
Status: complete

Read and write section `assistant_tasks` through `ReadWorkflowSection` and `WriteWorkflowSection`. Replace only that section. Do not add fields to `TAssistantConfig`. Do not call `Save` or `SaveWithConnections` from the task unit.

JSON shape:

```json
{
  "tasks": [
    {
      "id": "code-review",
      "title": "Code review",
      "summary": "Review the saved diff. No edits.",
      "mode": "inspect",
      "kind": "prompt",
      "scope": "changed_files",
      "message_filter": "",
      "compile_first": false,
      "fresh_conversation": true,
      "enabled": true,
      "hidden": false,
      "builtin_id": "code-review",
      "document_path": "",
      "prompt": "..."
    }
  ]
}
```

Omit empty optional strings rather than writing null. Reject a duplicate id, an unsafe id, an unknown mode, kind, or scope, and a prompt task with an empty prompt. A bad file is not silently replaced with the catalog: keep the catalog in memory, set an error string, and do not write until the user saves from the dialog.

`WriteWorkflowSection` must not run from a test against the developer config. The test sets the settings directory to a temp folder and restores it.

## 3. Dialogs

### 3.1 Build the Tasks list form
Status: complete

Add `AssistantTasksForm.pas` and `AssistantTasksForm.lfm`. Class `TAssistantTasksForm`. Streamed controls in the unnamed first section. No trailing `Published`. No `F` prefix on streamed controls. No `CreateUI`. `RegisterClass` in the unit initialization.

Layout, top to bottom:

- A client row: task list on the left, a narrow Up / Down strip, a preview on the right.
- The preview shows title, mode, scope, summary, and the prompt. The prompt view is read-only.
- A bottom strip, left to right: Run, Insert, Edit…, New…, Duplicate, Remove, Close.

Use `ChildSizing` on those strips. Do not stack `alLeft` and call it left-to-right. Up is above Down. Create them in that visual order with `alNone`, not with `alTop`.

Actions live in an `ActionList`. Double-click and Enter run. Escape closes. Remove asks first. A built-in is hidden, not deleted, and the confirm says it can be restored. A user task is deleted. Duplicate makes a user task, title suffixed with `copy`, new id, empty `BuiltinId`. Up and Down reorder the array and mark the form dirty.

Show hidden is a checkbox. Hidden rows are not in the list until it is checked. A disabled row stays visible and its Run action is disabled.

`ShowAssistantTasksForm` is modal. It does not send, format, or switch mode. On Run or Insert it returns a prepared request and closes only after preparation succeeds. A missing-evidence message leaves the list open.

### 3.2 Build the editor and the note dialog
Status: complete

Add `AssistantTaskEditorForm.pas` / `.lfm`, class `TAssistantTaskEditorForm`. Fields, top to bottom: Title, Summary, Enabled, Mode, Kind, Scope, message filter, Compile first, Fresh conversation, document path, prompt memo. `TButtonPanel` for OK and Cancel, so the button order is the Lazarus OK / Cancel order rather than an `alRight` stack.

Kind `format` disables the prompt, locks scope to `active_editor`, and shows one line: the active Pascal unit is formatted in the editor, Undoable, not saved, and no model is called. Message filter and Compile first are enabled only for scope `messages`. Document path is enabled only for mode `document`. ## 4. Execution

### 4.1 Prepare evidence and refuse a bad run
Status: not started

Add `AssistantTaskRun.pas`. It may use the IDE, `AssistantGit`, and `AssistantEditorEdits`. It must not use `ProjectAssistantForm`, and it must not call `BeginBuildWorkTracking`.

Preparation returns one of: ready, missing, or formatted. Missing carries a sentence the dialog can show. Ready carries the mode, a short display label, the API text, `FreshConversation`, and `DocumentPath`.

Refuse, and do not send, when:

- A turn or a plan run is already active. The list disables Run; the runner still checks.
- Scope `active_editor` and there is no active editor, or the editor is outside the selected package.
- Scope `selection` and the selection is empty.
- Scope `changed_files` and the working root has no `.git`. Say so. Do not silently review the whole tree. The diff is saved files only (`RunAssistantGit` with `status` and `diff`). Say that unsaved editor text is not in the diff.
- Scope `messages` and the filter matches nothing. For hints, also refuse when the error count is greater than zero, and name the errors task.
- Scope `user_note` and the note dialog is cancelled or blank.
- The task is disabled or hidden.
- Expansion fails.

`CompileFirst` runs the same project or package compile Review Compile uses, then reads Messages. It does not archive the conversation, disable tools, or call `SubmitReviewRequest`. A clean compile does not then send an errors task. Report that there is nothing to fix.

Display labels stay short, in the Fix Error style: `Task: Code review — 4 changed files`, `Task: Fix compiler errors — 3 error(s)`. The template is API text only.

Active-file context on a prompt task is the path and cursor, plus the selection when there is one. Do not attach the full unit as well as the IDE-context block.

Validation: build

### 4.2 Send a prompt task on the existing turn path
Status: not started

`ProjectAssistantForm` applies a ready prompt request. It does not grow a second send path.

When `FreshConversation` is set, call `StartNewChat(False, False)` so the previous chat is archived and the mode is not forced to Chat. Do not call it while a plan run is active; item 4.1 already refused that case.

If `DocumentPath` is set, `RememberDocumentRelativePath` before submit so the Document directive names that file. Do not call `set_active_plan`. Do not write the active plan from the host.

Then `ForceModeAndLock` to the task mode, `ShowChatSurfaceKeepMode`, and `SubmitUserTextEx(DisplayLabel, ApiText, True)`. If send does not start, unlock the mode. Do not clear `InputMemo`. Do not start build-work tracking. A task turn must not mark a plan item complete.

Insert does not send and does not start a conversation. It switches the mode combo to the task mode without locking, and it puts the expanded prompt in `InputMemo`. If the composer is non-empty, confirm before replacing it.

Codex and Claude already branch inside `SubmitUserTextEx`. Use that. Do not call `CompleteOnce` for a task that needs tools.

Validation: build

### 4.3 Format the active unit without a model
Status: not started

`format-unit` never builds an API prompt and never calls `SubmitUserTextEx`.

Accept `.pas`, `.pp`, `.lpr`, and `.dpr` only, matching the PascalStyle CLI. Refuse `.lfm`, `.inc`, and anything outside the target. Read the editor buffer, not disk. Call `FormatPascalSource`. If `TokenFingerprintsEqual` is false, do not apply; report that the formatter would change tokens. If the text is unchanged, report that and do not touch the buffer. Otherwise `ApplyAssistantEditorText` with the exact buffer text as the expected text. Do not save. Do not ask the tool-approval dialog: the button press is the approval.

The package does not depend on `PascalStyle` today. Add `../Source/Tools` to `LazAssistantTools.lpk` `OtherUnitFiles` and add `PascalStyleTokens.pas` and `PascalStyleFormat.pas` to the package file list. Do not shell out to the `PascalStyle` executable.

Post one system note on the assistant transcript: the unit path, whether it changed, and that it is not saved. No assistant bubble and no tool trace.

Validation: build

## 5. Built-in prompts

### 5.1 Write the ten prompt tasks
Status: not started

Put the prompt strings in the catalog inside `AssistantTasks.pas`. Each prompt is the user message. It must not tell the model to leave the task mode, edit the active plan, change a Status line, or widen the scope. It must not ask the model to call a tool that mode does not have.

Shared closing lines for every Build prompt: smallest change that does the job; do not reformat the file; do not delete unused code; update the matching `.lfm` when a form change needs it; `run_compile` after edits; visible reply is the cause and what changed.

Per task:

- **Code review.** Inspect. Review only the attached saved diff. Do not edit. Do not claim a truncated region was reviewed; name the omitted paths. Do not treat unsaved editor text as part of the diff. Group findings by severity. No per-line essays. If there is nothing to report, say so in one line.
- **Explain selection.** Inspect. Explain the selection to a maintainer. Do not propose a rewrite unless asked. Do not edit.
- **Bug fix.** Build. The note is the bug. Do not invent a second bug. If the note does not match the active file, read before editing and say which file you changed.
- **Fix compiler errors.** Build. Fix error, fatal, and panic lines only. Do not clean warnings, hints, or style in this turn. Stop when `run_compile` reports no errors, or when a fix would be a guess. Name any error left.
- **Fix compiler hints.** Build. The host has already refused this task if errors remain. Fix hint and note lines that are real code issues. Do not delete a method because a hint says it looks unused. Compile after. Do not start an error fix in the same turn.
- **Simplify code.** Build. Behaviour-preserving. Prefer the active selection when one was attached, otherwise the active unit. Do not optimise and do not format. If the code is already direct, say so and do not edit.
- **Report dead code.** Inspect. Report only. Say that a text search is not a reference search. Do not recommend deletion of published methods, `.lfm` event handlers, overrides, `initialization` / `finalization` references, or registered classes. List candidates separately from confident findings.
- **Optimise selection.** Build. The selection is the only edit region. Name the cost before editing (allocation in a loop, repeated string growth, repeated work). If there is no such cost, do not edit.
- **Technical documentation.** Document. Write or update `Documents/Technical.md`. Maintainer audience. Do not edit source. Do not use the plan format or Status lines. Chat is a short summary.
- **User manual.** Document. Write or update `Documents/UserManual.md`. Operator audience. No implementation detail unless it changes what the user does. The note is the topic. Same document rules as the technical task.

Format Unit has no prompt. Item 4.3 is its behaviour.

Validation: tests

## 6. Later tools

The Tasks button does not wait on this section. Do not start it until sections 2 to 5 are in place.

### 6.1 Expose CodeTools queries on the Grok tool list
Status: not started

`lazarus_find_declaration`, `lazarus_symbol_context`, and `lazarus_find_references` already run in `AssistantToolBroker` for the Codex path. The Grok catalog in `AssistantTools.pas` does not offer them.

Add `find_declaration`, `symbol_context`, and `find_references` to the Grok tool JSON. Allow them in Inspect and Build only. Dispatch to `QueryAssistantSymbol`. Do not duplicate the CodeTools calls. Descriptions must say positions are 1-based, columns are UTF-8 bytes, and `find_references` needs an explicit `search_paths` list of 1 to 32 project files. A truncated or partial search is not whole-project coverage. Read-only. No editor movement and no edit revision.

Do not raise the 32-file cap in this plan.

Validation: build

### 6.2 Allow read-only git inspection in Inspect
Status: not started

Code review's first turn uses the diff item 4.1 attached. A follow-up in that Inspect conversation cannot call `run_git` today, because `ToolAllowedInMode` keeps it on Build.

Allow `run_git` in Inspect for `status`, `diff`, `log`, `show`, `rev-parse`, and `ls-files` only. Refuse `add`, `commit`, and every other subcommand in Inspect. Build keeps the current rules. Update `AssistantGitDescription` so the model is not told that git is Build-only for those read commands.

Validation: tests

### 6.3 Add a guarded dead-code removal task
Status: not started

Do not start until item 6.1 is complete. Add a built-in `remove-dead-code`, Build, scope `active_editor`, disabled until the user enables it. New catalog ids append on load; this one must append disabled, not enabled.

The prompt may delete a declaration only when `find_references` was called with every project Pascal file, the tool did not truncate, and the result has no references. If the project has more than 32 Pascal files, or the search did not cover them, the task reports and does not delete. The same exclusions as Report dead code still apply: published, `.lfm` handlers, overrides, initialization, finalization, and registered classes. Compile after any deletion. If the compile fails, revert that deletion with the editor Undo path or a reversing edit in the same turn, and stop.

Validation: build
