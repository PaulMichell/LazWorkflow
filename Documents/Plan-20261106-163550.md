## 1. Overview

The first live Build-mode run on the Claude backend could not stage or commit. Every `run_git add` and `run_git commit` was refused with "Inspect git allows status, diff, log, show, rev-parse, and ls-files only.", even though the panel was in Build mode. The same turn was offered Build-only tools (`stage_patch`, `start_build`, `delete_path`), so the broker run did have the Build write scope.

The cause is in the code, not in the mode the panel reported:

- The broker allows the call. `TAssistantToolBroker.Execute` (`AssistantToolBroker.pas` ≈ 1533–1547) checks `FWriteScope`, which is `awsProject` for a Build turn, and passes the call on.
- `TAssistantIDEWorkspace.RunGit` (`AssistantIDEWorkspace.pas` ≈ 112) then calls `ToolRunGit` directly.
- `ToolRunGit` (`AssistantTools.pas` ≈ 1076) checks the unit global `GAssistantToolMode`, not the broker scope. That global is set only at the start of `ExecuteAssistantToolForMode` (≈ 4613). The Claude path never calls that routine for git, so the global keeps whatever an earlier tool call left in it. In a fresh IDE that is its zero value, and `amInspect` is the first value of `TAssistantMode`.

The review also found two related faults, and one problem with how large a tool result can be. They are listed below.

## 2. The mode reaching the tools

### 2.1 Give git the turn's mode, not a global left by another call
Status: complete

Problem. `ToolRunGit` decides between the Inspect and Build git commands from `GAssistantToolMode`. Only `ExecuteAssistantToolForMode` sets that global. Broker calls go through `TAssistantIDEWorkspace.RunGit`, which bypasses it. So a Claude Build turn is refused `add` and `commit`. The decision also depends on whatever ran last: after a Codex Inspect turn, or an Inspect Markdown write, git stays read-only. After a Build turn, a later broker call keeps the Build rules until something else resets them. The broker already applies the scope (`FWriteScope <> awsProject` allows the read commands only), so this second check adds nothing except the stale-global fault.

Fix.

- Give `ToolRunGit` an explicit `Mode: TAssistantMode` parameter, and make it check that, not `GAssistantToolMode`.
- `ExecuteAssistantToolForMode` passes its own `Mode`. `TAssistantIDEWorkspace.RunGit` passes `FToolMode`.
- Check that `ToolStagePatch` and the other `Tool*` routines the workspace calls directly (`ToolDeletePath`, `ToolRenamePath`, `ToolAddUnitToProject`, `ToolEnsureFormComponent`) do not read `GAssistantToolMode`. Today only git and the Markdown writers read it, and the Markdown writers always come through `ExecuteAssistantToolForMode`.
- Put the git rule in one pure function, for example `AssistantGitAllowedInMode(Mode, Command)`, so it can be tested without the IDE.

Test.

- A non-GUI test calls `AssistantGitAllowedInMode`. Build allows `add` and `commit`. Inspect allows only the six read commands. Plan and Document refuse `commit`, matching the broker's `awsMarkdown` rule.
- Live check: in a fresh IDE, before any other tool call, a Claude Build turn runs `run_git add` on one file and `run_git commit`, and both succeed. A Claude Inspect turn is still refused `add`.

### 2.2 Set the workspace mode for every broker run
Status: complete

Problem. `TAssistantIDEWorkspace.ToolMode` controls how `WriteMarkdown` applies the mode rules. After 2.1 it controls git as well. It is set in only two places: `StartClaudeTools` (`ProjectAssistantForm.pas` ≈ 4781, `ActiveMode`) and `ClaudeBuildToolsJson` (≈ 3161, always `amBuild`). `LaunchStoredCodexRun` (≈ 4910) starts a broker run on the same workspace without setting it. A Codex turn's `lazarus_write_markdown` or `lazarus_update_markdown` therefore runs under the mode of the last Claude turn. Before any Claude turn, it runs under `amInspect` (**confirm first**: check that Codex calls reach the broker's `lazarus_*` Markdown tools, and not only the shared catalogue in `AssistantCodexRun.ServiceOneTool`).

Fix. Set `FCodexWorkspace.ToolMode := ActiveMode` next to each `FCodexBroker.BeginRun`, or better, make the broker run carry the mode. For example, `BeginRun(WriteScope, Mode)` stores the mode and hands it to the adapter. Then scope and mode cannot disagree.

Test. A broker test with a recording adapter checks that two runs in a row, Plan and then Build, each pass their own mode to `WriteMarkdown` and `RunGit`. Live check: a Codex Plan turn writes a plan with `write_markdown` in a fresh IDE.

### 2.3 Build the plan prompt's tool list without starting a broker run
Status: not started

Problem. `ClaudeBuildToolsJson` (`ProjectAssistantForm.pas` ≈ 3156), called from `BuildWorkPrompt` for each Claude plan item, calls `FCodexBroker.BeginRun(awsProject)` only to read `ToolsJson`. `BeginRun` cancels any running build or test job (`FAdapter.CancelBuild`), drops prepared change sets and the rename preview, and replaces the run id. It also sets `ToolMode := amBuild`. Building a prompt should change nothing. If a prompt is built while a turn's run is open, that turn's later calls fail with a stale run id, and its build job is lost.

Fix. Add a read-only `ToolsJsonForScope(Scope)` on the broker that builds the catalogue for a given scope without touching run state. Call it from `ClaudeBuildToolsJson`, and leave `ToolMode` alone there.

Test. A broker test starts a run, starts a fake build, calls `ToolsJsonForScope(awsProject)`, and checks that the run id, the build and the prepared change set are unchanged.

## 3. Tool results Claude can read

### 3.1 Keep build_status within Claude's tool-result limit
Status: not started

Problem. In the live run, each `build_status` result was 62–83 KB on one line. Most of it is the observed-input manifest: every LCL include file, with its path. Claude Code refuses a tool result that large and saves it to a file instead. A one-line JSON file cannot be read in parts with the Read tool, so the assistant had to grep for `outcome` and `exitCode`. The "stale" reason for the first build could not be found at all.

Fix. By default, `build_status` returns a summary: job id, done, exit code, outcome, stale and the reason it is stale, the diagnostic items (capped), and the counts of manifest and dependency entries. Add an optional `detail` argument (for example `manifest`) that returns the full manifest only when it is asked for. Keep the field names that the plan-run completion check reads (`FCompletionBuildJSON` in `ProjectAssistantForm` ≈ 5256). Check that check still works on the summary, or give it the full form internally.

Test. A test of `AssistantBuildStatusJSON`, or of the broker's `build_status` path, checks that the default result stays under 16 KB for a manifest of 2000 inputs, and that it still names the stale reason and every error diagnostic.
