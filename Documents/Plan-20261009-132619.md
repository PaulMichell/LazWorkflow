# One tool path for every model

Generated by Lazarus Project Assistant.

ChatGPT opens a plan in the Lazarus source editor. Grok opens the same kind of file in the Assistant Markdown viewer. That is not a Codex transport limit. It is a second product path.

Grok and an OpenAI-compatible connection already share one prompt, one tool catalogue, and one dispatcher. Codex builds its own prompt, advertises `lazarus_*` tools, and executes them through `TAssistantToolBroker`. Claude is a third stub: the form never starts a Claude turn, and `RunClaudeTurn` has no caller. The fix is to put every backend on the path Grok already uses. Transport may differ. Tool names, prompts, Markdown writes, and which window opens must not.

## 1. Confirmed split

`SubmitUserTextEx` in `ProjectAssistantForm.pas` sends Grok and OpenAI-compatible turns through `AssistantClient`. Plan mode tells the model to call `write_markdown`. Document mode calls `AssistantDocumentDirective` with the Codex flag false, so that text also names `write_markdown` and `update_markdown`. `write_markdown` goes through `WriteMarkdownFile` and `PublishPlanFileWrite`. That publishes the file on the event bus and, unless a plan run is quiet, calls `OpenMarkdownDocument`. `open_markdown` does the same. Plan mode does not offer `open_file`.

A Codex connection never enters that function for a real send. `SubmitUserTextEx` returns at `StartCodexReply`. That prompt says to use `lazarus_*` tools and, before editing a closed file, `lazarus_open_buffer`. Document mode then appends `AssistantDocumentDirective(..., True)`, which names `lazarus_create_file`, `lazarus_replace_buffer`, and `lazarus_save_buffer` instead of the Markdown tools. `TAssistantCodexClient.StartThread` adds a second instruction: use the Lazarus tools, and live buffers may differ from disk. The tool list is `TAssistantToolBroker.ToolsJson`, not `BuildAssistantToolsJsonForMode`.

`lazarus_open_buffer` is described as opening a background editor tab. `TAssistantIDEWorkspace.OpenBuffer` calls `OpenEditorReuse`, which calls `LazarusIDE.DoOpenEditorFile`. There is no Markdown exception. `lazarus_create_file` writes through `CreateNewProjectText` and returns `opened:false`. It does not call `WriteMarkdownFile`, so it does not register a plan or open the viewer. The model is then told to open the closed file, and the source editor appears. That matches the failed ChatGPT plan turn.

Two further forks keep the behaviours apart. `FinishAssistantReply` calls `PersistPlanReplyIfNeeded` only when `Not FUseCodex`, so a ChatGPT plan that was only pasted into chat is not saved through `WriteMarkdownFile`. `BuildWorkPrompt` has its own `FUseCodex` tool essay. `AssistantPlanCompletionRules` tells every model to call `update_markdown` and `run_git`, which the Codex catalogue does not contain.

`open_file` on the shared path has the same hole for any backend that is allowed to call it. `ToolOpenFile` does not look at the extension. Document, Inspect, and Build can still open a `.md` file in the source editor.

Pictures are a real transport limit, not a second product. `TAssistantCodexRun.Steer` records that this protocol has no image item. Do not invent a Codex image tool or a text note that stands in for a picture. Keep the existing refusal. Do not copy it into a Codex-only prompt.

## 2. Constraints

Touch the units named on each item. Follow Michell Computing style: PascalCase keywords, 2-space indent, and `Result` assigned on every path. Do not add a trailing `Published` section. Do not build a new static dialog in code. The existing Ask confirmation in `ApproveToolIfNeeded` is the shared approval path; do not grow `ApproveCodexTool` to understand more tool names.

Do not add a compatibility alias that still opens the source editor. Do not fix this by teaching `lazarus_open_buffer` to open the viewer and leaving that name in the model-facing list. One name, `open_markdown`, and one writer, `write_markdown` / `update_markdown`.

`TAssistantToolBroker` and `AssistantWorkspaceTest.lpr` may stay for this pass. They are an IDE-buffer test harness, not the model API. The turn must not advertise or execute those tools. A later pass can delete the broker once nothing calls it. Do not port `lazarus_find_declaration`, change sets, or local rename into the shared catalogue here. Grok does not offer them, and this plan is parity with Grok, not a new editor protocol.

`ProjectAssistantForm.pas` is already far past the unit size preference. Do not add another prompt literal there. Call the existing helpers.

The wire shape may differ. Grok tools are `{"type":"function","function":{"name","description","parameters"}}`. Codex `dynamicTools` are `{"type":"function","name","description","inputSchema"}`. A converter copies name, description, and the parameters object. It does not rewrite descriptions or invent names.

## 3. Markdown windows

### 3.1 Refuse Markdown in the source editor
Status: complete

`OpenEditorReuse` in `AssistantTools.pas` is the choke point for `ToolOpenFile`, `TAssistantIDEWorkspace.OpenBuffer`, and the write-file open flag. If the path extension is `.md`, `.markdown`, or `.mdown`, do not call `DoOpenEditorFile`. Return failure and a note that names `open_markdown`. No source tab is created.

`ToolOpenFile` surfaces that note as the tool error. A `write_file` or `replace_in_file` of a Markdown path that asks to open the file calls `OpenMarkdownDocument` instead of `OpenEditorReuse`. Other files keep the current source-editor open.

Check: opening `Documents/Plan.md` through `open_file` or `lazarus_open_buffer` does not create a Lazarus source tab. The error names `open_markdown`. A `.pas` file still opens in the source editor.

### 3.2 Keep plan and document writes on WriteMarkdownFile
Status: not started

Do not add a viewer call to `TAssistantIDEWorkspace.CreateFile`. A plan or document is written only by `WriteMarkdownFile` and `ReplaceInMarkdownFile`, which already register an assistant plan, honour the plan format checks, and call `PublishPlanFileWrite`.

`write_markdown` and `update_markdown` keep `open` defaulting to true. `PublishPlanFileWrite` still skips a new viewer when a plan run is quiet, and still refreshes a viewer that is already open. A normal Plan or Document turn is not quiet, so the Assistant Markdown viewer opens. That is the Grok behaviour ChatGPT must match.

Check: a Plan-mode `write_markdown` of a recognised plan opens the Markdown viewer and registers the plan. It does not open a source tab.

## 4. One catalogue and one dispatcher

### 4.1 Send ChatGPT the shared tool list
Status: not started

`StartCodexReply` must stop passing `FCodexBroker.ToolsJson`. Build the list with `BuildAssistantToolsJsonForMode(ActiveMode)`, the same call `TAssistantService` uses, then convert that array to Codex `dynamicTools` shape in `AssistantCodexClient` (or a helper that unit owns). Chat mode still sends an empty tool list.

Plan mode therefore offers `write_markdown`, `update_markdown`, `open_markdown`, `read_file`, `list_directory`, and the plan registry tools. It does not offer `lazarus_open_buffer`, `lazarus_create_file`, `lazarus_replace_buffer`, or `lazarus_save_buffer`. Document, Inspect, and Build offer the same names Grok offers in that mode, including `open_file` only where Grok already allows it. Plan still does not offer `open_file`.

`TAssistantCodexClient.StartThread` must not hard-code "use the lazarus tools". Developer instructions are the harness system prompt for that mode, from `TAssistantHarness.BuildSystemPrompt`, including the skill bodies `CollectSkillsForMode` already selects. Pass that string in. Do not maintain a Codex copy of the mode essay.

Check: the JSON embedded in `thread/start` for Plan mode contains `"name":"write_markdown"` and `"name":"open_markdown"`, and does not contain `lazarus_`. Descriptions match the shared catalogue. Chat mode still has an empty `dynamicTools` array.

### 4.2 Execute ChatGPT tool calls on the shared dispatcher
Status: not started

`TAssistantCodexRun.ServiceOneTool` currently calls `Broker.Execute`. Change that call to `ExecuteAssistantToolForMode` with the mode captured when the turn started. That function already sets `GAssistantToolMode`, applies `ToolAllowedInMode`, and runs `ApproveToolIfNeeded`. Call it from the IDE timer, which is already the main thread, so Markdown windows and editor tools stay on the IDE thread.

Drop the broker argument from the run's service path. `PollCodex` must not require `FCodexBroker` for a tool result. Leave `ApproveCodexTool` unhooked from turns. Ask mode uses the existing confirmation, not a dialog that switches on `lazarus_*` names.

A tool name outside the shared catalogue is an error from `ExecuteAssistantToolForMode`. Do not fall through to the broker.

Check: a serviced `write_markdown` call from a Codex run increments the same plan-write path Grok uses and opens the viewer. A serviced `lazarus_open_buffer` call is rejected and does not open an editor.
