## 1. Git clone accepts an option as the URL

### 1.1 Reject option-like clone URLs before Git runs
Status: complete

`Source/LazRepositoryTools/GitService.pas` `TGitService.CloneRepository`, the `RunGitEx` call at line 1938. The clone dialog in `Source/LazRepositoryTools/GitCloneForm.pas` only checks that the URL and folder are non-empty (`FormCloseQuery`). `Source/LazRepositoryTools/RepositoryManagerMain.pas` `DoCloneRepository` passes that URL straight through.

Symptom: pasting a "URL" that starts with `-` makes Git treat it as an option. `git clone --upload-pack=/path/to/helper /chosen/dest` runs that helper. There is no shell, but Git option parsing is enough.

Cause: the argument vector is `['clone', Url, Dest]`. Remote add/remove/rename already end options with `--` and reject a name whose first character is `-` (`GitNameIsSafe`, line 809). Clone does neither. `TProcess` parameters do not protect against Git's own options.

Fix: reject a URL that is empty after trim, contains a NUL or other ASCII control character, or starts with `-`. Call `git clone -- <url> <dest>` so a rejected check cannot be bypassed by a later caller that forgets the check. Do not log the URL if it was rejected. Add a regression in `Source/Tests/RepositorySafetyTest.lpr`: a temp parent directory, URL `--upload-pack=/bin/true`, assert `CloneRepository` returns false, `LastError` explains the rejection, and the destination was not created.

While that function is open, apply the same end-of-options marker and `GitNameIsSafe` check to `Fetch` (line 1791), `Pull` (lines 1817–1819), and `Push` (lines 1847–1849). The Manage form currently calls those with the default remote `origin`, so they are not the live exploit. They are the same missing guard.

## 2. macOS waste bin builds AppleScript from the path

### 2.1 Pass the path as data, not as script text
Status: complete

`Source/LazRepositoryTools/GitPathUtils.pas` `MovePathToWasteBin`, the Darwin fallback at lines 163–166.

Symptom: on macOS, deleting a file whose name contains `"` can run extra AppleScript. The confirmation dialog shows the path as text; Finder then interprets the constructed script. Linux (`gio` / `trash`) and Windows (`SHFileOperationW`) pass the path as an argument and are not affected.

Cause: the script is `'… POSIX file "' + StringReplace(FullPath, '"', '\"', [rfReplaceAll]) + '"'`. AppleScript does not treat `\"` as an escape inside a double-quoted string. A quote ends the string. Doubling the quote (`""`) would be the AppleScript escape, but concatenation is the wrong fix.

Fix: keep using a parameter array. Run `osascript` with a script that reads `item 1 of argv`, and pass `FullPath` as a separate parameter after `--`. Do not interpolate the path into `-e`. If `osascript` is unavailable, fail with the existing waste-bin error. A unit test can assert the argument list contains the path as its own parameter and that a quote in the path does not appear inside an `-e` string; skip execution when not on Darwin.

## 3. Conversation archive ignores an index rename failure

### 3.1 Roll back when the index cannot be moved
Status: complete

`Source/LazAssistantTools/AssistantConversation.pas`.

`ArchiveCurrent` lines 1010–1018: if the conversation file renames and the index rename fails, the failure is only a log warning. The method still clears memory and returns true. `StartNewConversation` then deletes a leftover current index. History (`ListHistory`) counts turns from the index file, so the archived chat is listed with turn count 0 and the raw archive id. Opening it later can rebuild the index from the JSONL (`Load` / `LoadConversationFileIntoMemory`), but the history row is wrong until then.

`ActivateArchive` lines 1210–1239: parking the current index is optional (`ParkedIdx` stays false on failure) and the archive index rename result is ignored. `Load` rebuilds the current index from the conversation body, so the open chat can recover, but the parked chat is left without an index and the old archive index file can be left behind.

Fix: treat an index rename failure like a conversation rename failure. In `ArchiveCurrent`, rename the conversation file back, set `FLastError`, clear `ArchiveId`, and return false. In `ActivateArchive`, if the current index exists and cannot be parked, restore the parked conversation and return false. If the archive index cannot be moved onto the current index, restore both sides and return false. Do not log success after a partial rename. Add a fixture that makes the destination index path already exist (or otherwise makes `RenameFileUTF8` fail) and assert both functions return false with the original current files still in place.

## 4. Plan saves rewrite every line ending

### 4.1 Keep the plan file's existing line endings
Status: not started

`Source/LazAssistantTools/AssistantPlan.pas` writes through `TStringList.Text` and `SaveToFile` in `WriteMarkdownFile` (line 628), `ReplaceInMarkdownFile` (line 714), and `SetPlanSectionStatus` (line 1521).

Symptom: `update_markdown` / `write_markdown` / a status change rewrites the whole file with the platform `LineEnding`. A CRLF plan becomes LF on Linux, and an LF plan becomes CRLF on Windows. Git then shows every line changed. `replace_in_file` in `Source/LazAssistantTools/AssistantTools.pas` already detects the file ending (`DetectFileEol` / `NormalizeToEol`) and does not do this.

Cause: `TStringList.Text` joins with the process line ending. The plan helpers never set `LineBreak` from the bytes already on disk.

Fix: if the file exists and is not a symlink, detect its ending the same way `DetectFileEol` does and set `SL.LineBreak` before `SaveToFile`. New files should use LF (`#10`), matching the house sources. In `ReplaceInMarkdownFile`, normalize `old_text` to that ending before `Pos`, as `ToolReplaceInFile` does, so a model snippet with LF still matches a CRLF file. Add a small test: write a plan with CRLF, replace one status line, assert the other lines still end in CRLF and only the intended text changed.

## 5. Spell suggestion click reads the menu caption

### 5.1 Store the suggestion and apply that string
Status: not started

`Source/LazWorkflowCommon/SpellMemo.pas` `RebuildSpellMenu` sets `Item.Caption` from the suggestion (around line 1576). `SuggestionClick` (lines 1666–1668) does `StringReplace(Caption, '&', '', [rfReplaceAll])`.

Symptom: choosing a suggestion that contains `&` inserts the word with every ampersand removed. LCL menus default to automatic accelerators, which insert an extra `&`. Stripping every `&` repairs the accelerator and destroys a real one. Ignore and Add already use `FActiveToken`, not the caption.

Fix: keep the raw suggestion beside the menu item (a list parallel to `FSpellItems`, or another field that is not the caption). `SuggestionClick` must use that string. Escape a literal `&` as `&&` only in the caption. Set the owned popup's `AutoHotkeys` to manual if the host menu would otherwise rewrite captions. Add a spell-memo test that a suggestion `AT&T` replaces the misspelled word with `AT&T`.
