# LLM harness review and unification

Generated by Lazarus Project Assistant.

This is a static review of the Grok, ChatGPT, and Claude integrations in `Source/LazAssistantTools`, written so the findings can be implemented without another discovery pass. It replaces the stub in this file. An earlier write-up, `Documents/Opus LLM Integration Review.md`, was checked against the current tree; where it disagrees, this file wins.

Nothing here was compiled or run against a live model. Evidence is the current source: procedure names below were read. Line numbers are omitted on purpose so a later edit does not make the plan look more precise than it is.

The six objectives are shared code and standardised behaviour, one Lazarus-facing tool and data contract, a cheaper way to add a model, a stable extension API, less duplicated code, and one defined response when a model or a harness lacks a capability.

Constraints that this work must not weaken:

- Claude turns stay on the user's Claude subscription. Do not read or copy Claude sign-in files. Do not add `--bare`, `--max-budget-usd`, or `--betas`.
- A Claude turn that has already run a tool must not be replayed automatically. Generalise that rule; do not drop it.
- Do not log keys, tokens, Authorization headers, or account email.
- Codex-native approval requests stay declined. IDE tool approval stays in the assistant policy.
- Known failures in `CLAUDE.md` predate this review. Do not treat them as regressions caused by this work, and do not "fix" `AssistantMCPApprovalTest` by putting `bufferUpdated` back.

How to use this file: sections 1 to 6 are the review. Section 7 holds the decisions. Section 7.1 is decided. The other decisions in that section stay blocked until you choose. Section 8 is the implementation sequence. Do not start a blocked item. An unblocked item should leave the IDE working and should not depend on a still-blocked decision.

## 1. Scope and method

Reviewed: the live turn paths for Grok (`grok`), ChatGPT (`codex`, the `codex app-server` program), and Claude (`claude`, the `claude` program). Also reviewed, because it is the obvious place a fourth HTTP model would be added: the OpenAI-compatible connection (`openai-compatible`). That row is not one of the three tested turn engines. It is called out because the settings UI presents it as a connection and the send path does not honour it.

Not reviewed as a design to preserve: model quality, prompt wording taste, or the phone app protocol beyond the approval and steer calls the IDE already makes. The `claude-connector` documents named in `CLAUDE.md` were not re-read; the constraints above were taken from `CLAUDE.md` and from the Claude client header.

Packages touched by the findings: `LazAssistantTools` for the turn engines, tool catalogues, broker, and settings; `LazAssistantMonitor` only where the phone waiter and `RemoteSteer` meet the form.

## 2. Current architecture

There is no shared turn contract. `IAssistantModelProvider` covers sign-in, model listing, and `CompleteOnce`. Its header says managed agent runtimes own a separate loop, and Codex and Claude sit entirely outside it. The three live loops meet in `ProjectAssistantForm` (about 11,800 lines), which holds `FUseCodex` / `FUseClaude`, a field set per runtime, and separate start, launch, poll, and release methods. Anything that is not those two flags is treated as the Grok HTTP actor.

| Stack | Connection id | Turn engine | What the model is offered | What runs the tool |
| --- | --- | --- | --- | --- |
| Grok | `grok` | `TAssistantService` + `TAssistantActor` | OpenAI `function` JSON from `BuildAssistantToolsJsonForSession` | `ExecuteAssistantToolForMode` |
| ChatGPT | `codex` | `TAssistantCodexRun` over app-server JSON-RPC | The same catalogue, converted by `CodexDynamicToolsFromCatalogue` | `ExecuteAssistantToolForMode`, always from the IDE timer, with an empty tool id |
| Claude | `claude` | `TAssistantClaudeRun` via `claude -p` stream-json | `ToolsJsonForScope` names (`lazarus_*`), seen by Claude Code as `mcp__lazarus__*` | `TAssistantToolBroker` on the IDE thread, through the loopback MCP server |
| OpenAI-compatible | `openai-compatible` | None | None on the live path | None. `TAssistantCompatibleClient.CompleteOnce` is a non-streaming chat completion with no tools and no harness prompt. Settings and account usage call it. Send does not. |

Codex also opens a broker run in `StartCodexReply`, then sets `FCodexBroker.OnApproval` to nil and never executes through that broker. The comment says turns use `ApproveToolIfNeeded`, not the `lazarus_*` review dialog. The broker run is bookkeeping. The same `FCodexBroker` and `FCodexWorkspace` fields are what Claude's MCP bridge uses. The form comment already says so. The names are wrong.

Rough size, from the units as they stand: `AssistantTools.pas` is 4,929 lines. `AssistantToolBroker.pas`, `AssistantService.pas`, `AssistantActor.pas`, `AssistantSettingsForm.pas`, `AssistantIDEWorkspace.pas`, and `AssistantAccountUsage.pas` are each well over the 1,000-line preference; several already carry a dated size note. Codex is 13 units plus its settings form. Claude's process wrapper is three units (`AssistantClaudeClient`, `AssistantClaudeStream`, `AssistantClaudeInput`) plus the MCP listener, bridge, and protocol. The bloat is not only those files. It is the same policy written again in the form for each runtime.

## 3. What is already shared

Keep these. The target is to extend them, not to replace them with a third copy.

- `TAssistantHarness.BuildSystemPrompt` already builds the work policy, tool-calling rules, IDE fusion notes, mode overlay, skills, and `AGENTS.md`. Grok sends that text as the system prompt. Codex sends the same text as `developerInstructions` from `CodexDeveloperInstructions`.
- The native tool bodies in `AssistantTools` are the real IDE operations. The broker already calls back into them for Markdown, Git, project run, and open-file, after its own approval.
- `TAssistantToolBroker` is the stronger run model: run id, write scope, revision snapshots, approval hook, and a refusal when the workspace identity changes. Only Claude gets the revision check.
- `RegisterAccountUsageQuery` is the registration pattern the rest of the integration should copy. Grok, Codex, and OpenAI-compatible register. Claude is deliberately unregistered: the unit comment says plan quota is an interactive screen, not a JSON result this program owns. Leave that until there is a real query.
- Image output is already a capability flag. `AssistantBackendCanDraw` is false for Codex and Claude, and `AssistantTurnOffersImageOutput` will not put `write_image` in the catalogue for them. That is not an offer-then-fail.
- Image attach goes through one check, `ComposerAttachAllowed`, before the backend branch in `SubmitUserTextEx`.
- Approval mode is already stored on the connection and copied onto `AssistantChatConfig` for every backend. The divergence is in who calls the gate, and with what id, not in where the setting is saved.
- Dropped-transport recovery (`TryDeferDroppedTransport`) is already shared by Codex and Claude. Grok has its own HTTP retry path.

## 4. Findings

### 4.1 Three turn engines, and a fourth connection that is not an engine

`SubmitUserTextEx` branches to `StartClaudeReply` or `StartCodexReply`. Every other connection, including `openai-compatible`, requires `AssistantChatConfig.IsSignedIn` and calls `AssistantClient.StartStream`. `IsSignedIn` is a Grok access or refresh token. `LoadConnectionSettings` calls `AdoptGrokSampling` only when the active row is `grok`. `SyncConfigFromGrokRow` runs only for an active Grok row. `RefreshFromConfig` applies `AssistantChatConfig` to the HTTP client and does not apply `FAccountApiBase` or the compatible key.

Effect: a selected OpenAI-compatible row still shows its own model in the footer (`FActiveModel`), but a send either demands a Grok sign-in or posts through the Grok actor with the Grok endpoint and Grok credentials. `TAssistantCompatibleClient` can list models and can call `/chat/completions` once, without tools, streaming, or the harness prompt. It is not a turn engine. `CanCompactContext` nevertheless returns true for that backend, because the predicate is `Backend = 'grok' or Backend = 'openai-compatible'`.

This is the main obstacle to objective 3. Adding a model today means another flag, another start method, and another set of form fields, or, for an HTTP model, falling into the Grok actor by accident.

### 4.2 Two catalogues, two executors, one hybrid

Native names, built as hand-written JSON in `Build*ToolsJson` and composed by `BuildAssistantToolsJsonForSession`: `read_file`, `replace_in_file`, `write_file`, `run_compile`, `run_tests`, `grep`, `spawn_subagent`, `write_image`, and the plan, Git, and symbol tools. Chat gets an empty catalogue. Mode gates live in `ToolAllowedInMode` and again in which builder runs.

Broker names, built in `ToolsJsonForScope`: `lazarus_read_buffer`, `lazarus_replace_buffer`, `lazarus_replace_in_buffer`, change-set tools, `lazarus_start_build` / `lazarus_build_status`, async tests and commands, and local-rename preview. Claude Code then prefixes them to `mcp__lazarus__*`. The trace shows the short name via `ClaudeToolDisplayName`.

The edit models differ. Native write and replace are direct. Broker edits require a revision token from the read, and a stale token is refused. Long work differs too. Native `run_compile` blocks. The broker starts a job and expects a status poll. Claude Code's own `Read`, `Grep`, and `Glob` remain available outside Chat (`--tools=Read,Grep,Glob`), so Claude can also read by a third path that does not take a revision token. `AppendClaudeModeArguments` correctly refuses Claude Code's own Edit, Write, and Bash.

Codex is the hybrid. It advertises the native catalogue, including `spawn_subagent` because `BuildAssistantToolsJsonForMode` passes allow-subagents true. `TAssistantCodexRun.ServiceOneTool` then calls `ExecuteAssistantToolForMode` and the dispatcher returns `spawn_subagent must run on the parent session actor.` The tool was offered and then failed. That is a harness bug, not a model limit.

The broker comments still describe behaviour as Grok's (`run_command, with Grok's checks`, `Grok offers todo_write in Plan and Build only`). Those comments are evidence that the second catalogue was grown by copying, not by sharing a spec.

### 4.3 Mode to permission mapping is copied

The same five-way mapping exists in more than one type and in more than one place:

- `StartCodexReply` and `LaunchStoredCodexRun` each `BeginRun` with `awsNone`, `awsProject`, `awsMarkdown`, or `awsReadOnly`.
- `ClaudeToolScopeForMode` maps onto `TClaudeToolScope`.
- `ClaudeBrokerWriteScope` maps that enum back onto `TAssistantWriteScope`.
- The native catalogue encodes the same policy a third way in `ToolAllowedInMode` and the per-mode builders.

`TClaudeToolScope` does not say anything `TAssistantWriteScope` does not already say. A new mode has to be added in all of these or the runtimes drift.

### 4.4 The harness prompt is not actually shared

| Part | Grok | ChatGPT | Claude |
| --- | --- | --- | --- |
| `BuildSystemPrompt` (policy, tools, mode overlay) | System prompt | `developerInstructions` | Not sent |
| Skills and `read_skill` | Yes | Yes | No. The client header says the turn does not receive skill bodies. |
| `AGENTS.md` | Yes, inside the harness prompt | Yes | No. Claude Code may read `CLAUDE.md` itself. That is a different file. |
| Plan or Document directive | User text via `BuildSubmitApiText` | Same | Same |
| IDE context | Full, then light after `AssistantClient.MessageCount >= 8` | Same test, and Codex does call `AddUserMessage`, so the switch can fire from a side history the app-server never sees | Always full. `StartClaudeReply` does not copy the turn into the HTTP client, so the count never advances. |
| Backend note | None | None | `ClaudeReadImageNote` only, and only when the MCP config is loaded |

`ClaudeReadImageNote` is appended with `--append-system-prompt`. The constant comment says Claude Code records that system prompt on the session's first request and reuses it on resume. A later prompt fix will not reach an already resumed session.

Some of the "Claude behaves differently" reports are this gap. The model is not given the work policy, the completion rules, or the skill the other two receive.

### 4.5 Continuity is three strategies with two copied recap loops

Grok keeps a message array on `TAssistantService`, trims it, and can compact it. Codex starts an ephemeral thread and prepends a bounded recap built inline in `StartCodexReply` (stop at 24,000 characters, 4,000 of each user prompt, 8,000 of each answer), and re-attaches stored images because the thread has no message array. Claude resumes `--session-id` / `--resume` when the session key still matches, and calls `ClaudeRecapPrompt` only when a new session must start. Plan items have a Claude-only holder, `TClaudePlanItemSession`: a new item does not resume the conversation session.

The recap loops are copies. The strategy can stay per backend. The builder, the limits, and the image rules should not.

### 4.6 Approval and steer do not mean the same thing

`ApproveToolIfNeeded` consults the phone waiter only when the tool id is non-empty. Codex passes `''` and comments that it does not call the remote waiter. `ApproveClaudeTool` also passes `''`, then a broker summary. Ask mode therefore cannot be approved from the phone for ChatGPT or Claude. The desktop dialog still runs.

`aamAlways` and `aamAuto` both return success immediately in that function. The Auto comment says the sandbox still applies. Always has no separate comment and no separate branch. Either the distinction was never finished, or one of the two settings should go. Do not invent a difference in this work.

Steer matches the same split. Grok queues on the actor. Codex calls `FCodexRun.Steer`. Claude from the desktop puts the text back in the composer and returns, with no sentence. Claude from the phone gets `This connection cannot steer.` in `RemoteSteer`. A missing capability must not be a silent no-op on one client and an ad hoc error on the other.

### 4.7 Capability facts are string tests

`CanCompactContext`, `AssistantBackendCanDraw`, the steer checks, the effort footer, and the settings panels all branch on `Backend = 'grok'` and the other literals. The settings form shows a different panel per backend and is the largest concentration of those tests. `TAssistantConnection` is a flat union: `SearchMode` is meaningful for Grok, `Runtime` for the two programs, `KeyEnv` / `WireApi` for the compatible row. Every backend shares one load path and one form.

The effort footer is a small example of the drift. Only `grok` and `codex` get an effort caption. Claude stores `FClaudeEffort` and passes it as `--effort`, but the footer says the connection does not set an effort level.

The account-usage registry is the exception that should become the rule. A missing registration is unknown, not an error, and does not open a socket. Capability questions should work the same way.

### 4.8 Trace, events, and usage are three pipelines

`RecordCurrentTurn` writes an events file only when the turn is not Codex and not Claude. History replay and the monitor therefore see less for those two. Codex and Claude rebuild trace blocks in the form from `TCodexRunSnapshot` and `TClaudeRunSnapshot`. The native path uses the stream callback and `TAssistantEvent`. Usage arrives as actor totals, `TCodexContextUsage`, and the Claude token fields on the snapshot. The footer already special-cases the caption per runtime.

A new behaviour (a phase, a retry, a usage field) has to be taught three times. That is the technical debt objective 4 is about.

### 4.9 Where a missing capability is handled badly

The failures are not random. They are the absence of one rule.

- Offered, then failed: `spawn_subagent` on Codex.
- Silent no-op: Claude steer on the desktop.
- Ad hoc sentence: Claude steer on the phone.
- False positive flag: `CanCompactContext` for OpenAI-compatible, which has no history engine.
- Withheld correctly: `write_image` for Codex and Claude, via `AssistantBackendCanDraw`.
- Left to the other program: Claude Code `Read` / `Grep` / `Glob`, which the harness did not declare as a capability.
- Real provider limit, already gated: image generation endpoints. Codex and Claude have none here. Do not emulate `write_image` by calling a different vendor.

### 4.10 Size

The integration is large because each runtime grew its own loop, its own snapshot, and, for Claude, its own tool list. Sharing the harness prompt and the native executor removed some of that for Codex, then the broker grew a parallel list for Claude. A size pass that only splits files, without collapsing those duplicates, will not meet objective 5. The units that are large because one backend's wire is inherently large (Codex qualification and schema, the Claude stream folder) should keep a dated size note rather than be split into meaningless halves.

### 5.1 Standard method for a missing capability

Every capability is declared by the backend as Native, Emulated, or Absent. One shared function decides the catalogue, the prompt section, the desktop control, the phone response, and the tool error. The sentence is built from the capability and the backend display name, for example `Not available with this connection (Claude).`

- Native: offered, enabled, executed by that backend's own wire.
- Emulated: offered, enabled, executed by shared code. The recap is emulation of continuity. A queued next-turn steer would be emulation of steer. Subagents for a managed runtime would be emulation. Emulation does not live inside the backend unit.
- Absent: not offered, and the prompt section is omitted. Desktop controls are disabled and show the sentence. The phone receives the same sentence, not a different one. If the model calls the tool anyway, the tool result is that sentence and the call is logged. That path is a bug, not a feature.

Rules that follow:

- Never offer a tool and then return a private error.
- Never silently put the user's text back in the composer.
- A false capability flag is a defect. `CanCompactContext` must be false when there is no history to compact.
- Do not emulate a missing vendor endpoint by calling another vendor. Image output stays Absent for Codex and Claude.
- Tests, not comments, hold the matrix. For each registered backend and each mode, every advertised tool has a capability that is not Absent, and no Absent capability appears in the catalogue, the prompt, or the enabled UI.

## 6. Target shape

Follow the layering already required for this codebase. Backends self-register. Adding one does not edit the form, the settings form, or another backend. The deletion test is the exit criterion: removing the Claude units from the package leaves Grok and ChatGPT building, and removing the Codex units leaves the others building.

Foundation, no IDE and no process:

- Capability, support level, turn request, turn snapshot, usage record, and the unsupported-sentence function.
- A declarative tool table: canonical name, description, schema, minimum write scope, read-only flag, thread affinity, required capability, handler id. Data, not JSON strings copied per wire.
- Wire adapters that render that table as an OpenAI function, a Responses tool, Codex `dynamicTools`, or MCP `inputSchema`.
- Prompt sections as pure functions. `TAssistantHarness` becomes that, or calls it. Delivery (system message, `developerInstructions`, `--append-system-prompt`) stays a backend concern.

Services:

- One executor. The broker's run id, scope, revision, and approval hook are the base. Native tool bodies move under it. `ExecuteAssistantToolForMode` becomes a shim and then goes.
- One session object for continuity strategy, the recap builder, events JSONL, and the usage log.
- A backend registry. `IAssistantModelProvider` remains the HTTP sign-in and one-shot helper. It stops being mistaken for the turn API.

Backends, each in its own unit, registered in `Initialization`:

- Grok, wrapping the actor and sampler.
- ChatGPT, wrapping the Codex units. Qualification and schema stay private to that backend.
- Claude, wrapping the process client and stream folder.
- OpenAI-compatible, only if section 7 says it becomes a real turn backend. Until then it is not registered as a turn backend, and send is refused.

Bridges, the only place a wire meets the executor:

- MCP bridge for Claude, and for any later CLI that speaks MCP.
- Codex dynamic-tool bridge. It must call the same executor. It must not keep a second dispatcher.

Application:

- The form talks to a backend id and a turn snapshot. One poll replaces `PollCodex`, `PollClaude`, and the native stream callback's form-side special cases.
- Each backend registers its settings frame. `AssistantCodexSettings` is already a frame. Grok, Claude, and the compatible row should follow that, not another panel switch in `AssistantSettingsForm`.

Connection config becomes common fields (`Id`, `Name`, `Backend`, `Model`, `ReasoningEffort`, `ApprovalMode`) plus a backend-owned JSON object that the backend loads and validates. Existing assistant config files migrate once, on load. OAuth tokens stay out of events and history.

One mode-to-scope function replaces the copies in section 4.3. One approval gate is always called with the real tool-call id, so the phone waiter runs for every backend. The approval summary is the broker summary, used everywhere, not the first 240 characters of raw JSON on one path and a path snippet on the other.

One snapshot carries content, thinking, phase, tool steps, usage, error, done, and replay-safety. Replay-safe is false once a tool has run. Recovery code reads that flag. The Claude rule then holds for Grok and ChatGPT too, which is stricter than today and should be called out when that item starts.

Expected size: the first packages add units. The reduction comes when the form branches, the second catalogue, and the copied recap and mode maps go. A net drop of a couple of thousand lines is plausible. It is not the success criterion. Success is that a behaviour fix lands once, and a new backend does not add a fourth start method.

## 7. Decisions required before the tool merge

A decided item records the choice and is complete. The others stay blocked so later packages do not guess them. The recommended default is stated so a yes is enough to unblock. Unblocking means recording the choice here. It does not by itself start the implementation items in section 8.

### 7.1 Must an edit prove it was based on the current buffer?
Status: complete

Decision: use the broker rule for every backend. An edit must present the revision token from the read of that buffer. A stale or missing token is refused. Grok and ChatGPT do not keep today's token-free overwrite.

This is not a question about tool names. Names are section 7.2. This is a question about when an edit is allowed to land.

Grok and ChatGPT change files with `write_file` and `replace_in_file`. `write_file` sends a whole new body and overwrites. `replace_in_file` sends a snippet (`old_text`) and its replacement. The IDE searches the open editor buffer, or the file on disk if it is not open, and swaps the snippet if it is found. There is no ticket. The model does not have to prove that it read this exact version. If you type in the file after the model read it, a replace still succeeds when the snippet is still there, and a full write can replace your newer text with the model's older copy of the file.

Claude does not get those tools. A read returns a revision token (a run id plus a counter) and the broker remembers the exact text it showed. An edit must send that token back. The broker refuses the edit when the token is unknown or the buffer no longer matches the remembered text (`Stale buffer revision; read the buffer again`). The model has to read again and retry. The write goes into the IDE buffer, so Undo still works.

The choice is which of those rules the shared editor uses:

- Ticket for everyone. Grok and ChatGPT keep calling `write_file` / `replace_in_file` if section 7.2 says so, but the shared editor also requires a current revision token, the same check Claude already has. A stale edit is refused instead of overwriting your buffer.
- Ticket only for Claude. Grok and ChatGPT keep today's direct overwrite and snippet replace, with no token. Claude keeps the stricter check. One executor would then have two edit rules, which is the split this review is trying to remove.

Token cost is not a reason to choose. The revision string is a few tokens in the read result and again on the edit call. The file body dominates either way: a read already returns that text, and a replace already makes the model echo `old_text` and `new_text`. A full `write_file` is expensive because it outputs the whole file, with or without a ticket. The only extra cost of the ticket is a refused edit followed by another read, and that happens when the buffer changed or the model lost the token. Today's native replace can force the same re-read when `old_text` is no longer found. A separate, larger cost is Claude's current `lazarus_read_buffer`, which can return the whole buffer (up to 1 MiB) while native `read_file` pages at 48,000 characters. Unification should keep the paged read. That saving does not depend on this decision.

Recommendation: ticket for everyone. The check is what stops a model writing over a buffer that changed after it was read. It does not by itself rename the tools.

Recorded from the review conversation: use the broker revision check for every backend.

### 7.2 What name does the model call?
Status: blocked

Section 7.1 decided the safety check. This decides the spelling of the tool call. The same edit can be named either way. The broker check does not force the broker's names.

Today the model sees two spellings for the same kind of work:

- Grok and ChatGPT, and the harness prompt and skills, say `read_file`, `replace_in_file`, `write_file`, `run_compile`.
- Claude sees `read_buffer`, `replace_in_buffer`, `replace_buffer`, `start_build`, because the broker lists `lazarus_read_buffer` and Claude Code shows that as `mcp__lazarus__read_buffer`. The `lazarus_` and `mcp__lazarus__` pieces are wiring. They are not a third naming scheme.

The choice is which spelling is the one in the shared catalogue, the prompt, and the skills:

- Keep the Grok and ChatGPT names (`read_file`, `replace_in_file`, `write_file`, `run_compile`). Claude is taught those names. An already resumed Claude session still expects `read_buffer` until it starts a new session, so the old broker names stay as aliases for one release. This matches the prompt and the skills as they are written today.
- Switch everyone to the broker names (`read_buffer`, `replace_in_buffer`, `replace_buffer`, `start_build`). Existing Claude sessions keep working. The harness prompt, the skills, and every Grok and ChatGPT conversation have to be rewritten, because they currently say `read_file` and `replace_in_file`.
- Invent a new set. Both sides break. There is no current reason to do that.

Two names are not pure synonyms, so picking the Grok spelling still needs a defined meaning under the broker rule:

- `write_file` today means "here is the whole file, overwrite". Under the broker, replacing an existing buffer is a revision-checked replace, and creating a file must not overwrite. If this name is kept, it means "create a new file, or replace an existing buffer only when the revision token is current". It does not mean a blind overwrite.
- `run_compile` today waits and returns the log. Claude's `start_build` returns immediately and the model polls `build_status`. The name can stay `run_compile` either way. Whether the call blocks or returns a job id is a later behaviour choice, not this naming choice.

Recommendation: keep the Grok and ChatGPT names, and accept the old broker names as aliases for one release. Do not rename the prompt and the skills unless those names are themselves misleading.

Need from you: keep `read_file` / `replace_in_file` / `write_file` / `run_compile`, or switch everyone to the broker spellings.

### 7.3 Claude Code built-in read tools
Status: blocked

Outside Chat, the Claude turn still gets `Read`, `Grep`, and `Glob`. Those bypass the broker's revision token and the project sandbox the Lazarus tools enforce. Write, Edit, and Bash are already refused. Web search and the agent tool are excluded.

Recommendation: keep `Read`, `Grep`, and `Glob` for now, but declare them as a Native capability of the Claude backend only, so the matrix shows the split. Do not enable Bash, Edit, Write, web search, or the agent tool in this work. A later item can force all reads through Lazarus if you want one sandbox.

Need from you: keep the three read tools, or require every read to go through the Lazarus tool.

### 7.4 Steer on Claude
Status: blocked

Claude Code print mode has no steer call in this client. The desktop hides that. The phone states it.

Recommendation: Absent, with the standard sentence on both clients, until a real steer API exists. Do not emulate mid-turn steer by queueing the text as the next turn unless you explicitly want that. Queuing is a different feature.

Need from you: Absent, or Emulated as a queued next turn.

### 7.5 Auto and Always
Status: blocked

`aamAlways` and `aamAuto` both allow the tool without a dialog. The sandbox is elsewhere and applies to both.

Recommendation: do not invent a split (for example "Auto still asks for Git and delete") in this work. Keep both labels as aliases of one behaviour, and say so in the settings hint. Removing a label is a config migration and can wait.

Need from you: confirm they stay aliases, or define the difference you actually want.

## 9. Adding a backend after this work

This is the checklist item 8.18 is aiming at. It is not a second work package.

- Add one unit that implements the backend contract and registers itself in `Initialization`.
- Declare every capability as Native, Emulated, or Absent. The matrix test fails until each entry is set.
- `StartTurn` returns a turn that publishes the shared snapshot and appends events.
- Deliver tools through an existing wire adapter or a new bridge. Do not add a tool inside the backend.
- Choose prompt delivery and a continuity strategy. Emulation, if any, is shared code.
- Register a settings frame and the backend-owned config keys. Register an account-usage query only when there is a real response to parse.
- Add catalogue, prompt, and wire fixtures.

No change to the form, the settings host, the executor, or another backend should be required. If it is, the abstraction is not done.
