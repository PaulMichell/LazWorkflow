## 1. What the link does today

The phone and the IDE still speak catalogue 2 (`MonitorCatalogueVersion = 2` in `AssistantMonitorCodec.pas`). Catalogue 3 is specified in `Documents/MonitorProtocolV3.md` and is not the live wire. The October 2026 plan marked the event log, the Room store, and the sync applier complete. Those pieces were then left beside the old path. That is the drift.

Content moves as documents, not as slices.

- `PumpMirror` runs from a 150 ms `TTimer` on the IDE thread (`AssistantMonitorBridge.pas`). Each tick can copy the whole live turn through `FillMonitorTurn`, call `ObserveTurn`, then build a `patch` from dirty blocks. A pure suffix can be an append. The first patch, and any edit that is not a suffix, sends the whole block body. Busy, phase, status text, and `ElapsedMs` ride in that same patch, so a flag change is a content step. The pump is also the live producer of mirror events, so an IDE change waits up to 150 ms before anything is queued.
- `TMonitorMirror.ObserveTurn` records `turn_open`, `block_open`, `block_append`, `block_replace`, `block_close`, `image_added`, and `turn_close`. A new block emits `block_open` and, when it is not running, `block_close`, and emits no body. A `block_append` carries the whole suffix since the last observation. `AppendLocked` drops one event larger than the 8 MiB log budget and still advances the head. Resume does not replay these events. It replays patches. The phone's `SyncApplier` only receives a decoded `event` (`LanSession.kt` offers it when `type` is `event`). The host does not send that type on the live path.
- The screen is `MonitorCoordinator` memory: patches, catchups, and snapshot pages. Room is a later full-document rewrite. `persistBoard` in `MonitorViewModel.kt` calls `saveScreen`, which keeps the previous `seq` and `streamId`. `watchRepository` can paint those rows back onto the coordinator. Two writers, and the cursor does not describe the text. The phone's content `ack` is paced by the coordinator from the patch cursor (`scheduleAck`), not by the applier after a commit. `SyncApplier.flush` copies the batch, clears `pending`, then calls `store.apply`, so a failed apply loses the batch.
- There are three outbound queues in series, and only the first two know about priority. The session lanes (`FControlSends`, `FLiveFrames`, `FPlanFrames`, `FBulkSends`, bulk capped by `MonitorOutboundQueueLimit = 32`) are drained by `DrainSends` into the carrier. The carrier (`TMonitorLanCarrier.Send`) holds one plain FIFO capped at `MonitorOutboundCap = 32`. Once a frame is in that FIFO, a pong queued later waits behind every frame ahead of it. `TInetServer.RunIdleLoop` (`ssockets.pp`) calls `fpSelect` on the listening socket only, with `AcceptIdleTimeOut = MonitorAcceptIdleMs = 250`. The accepted socket is not in that wait, so neither a queued frame nor an arriving ping wakes the thread. One pass reads once and writes at most one frame (`WriteOnce`). A second authenticated socket is answered `rejected {reason: "busy"}` and closed. The spec's replacement is `bye {reason: "replaced"}` on the old link.
- A plan that does not fit one frame is replaced with "The plan is too large to cache on the phone." `ReadMonitorPlanPreview` reads through `ReadAssistantPlanDocument`, which stops at `AssistantPlanDocumentMaxBytes` (4 MiB) and then appends "The rest of the plan is on the desktop." `PlanDocumentRevision` is `PlanTextFingerprint` of that capped text, plus `:cut` when the cap hit. `savePlan` stores the body inside the plan row's JSON through `planCacheText`. The phone cannot review a plan the host refused to send, and a plan that did fit is one string in the UI state.
- The last measured host harness (`Documents/MonitorLinkBaseline.md`, 2026-10-29) was 4 frames/s, a first frame at 251 ms, and a pong at 8261 ms behind 32 bulk frames. The resume row delivered 1 of 8 frames and then hit an arithmetic overflow because the answer clock was never set. Re-measure before quoting those numbers again. Fix the overflow before recording a new number. The transport is the structural ceiling. Smaller payloads alone cannot meet a 150 ms response while the socket leaves once per quarter second, and neither can a 150 ms producer timer.

`SweepCommands` cancels a user command still unclaimed after 5 s and sends `host_busy`. `EnterBusy` sets `mssBusy` when `send`, `run_plan`, `work_on_plan`, or `run_task` is accepted, before `SetHostFlags` reports `Sending` or a plan run. A modal already defers resume. The same defer is not the rule for every command. `TMonitorCommandIntake` records the id, and a duplicate is answered with `command_state`, but a blocked command sends `error` without `NoteRejected`.

The two features fail for those reasons. Connected response waits on the pump timer, the idle poll, a FIFO with no priority, whole blocks, and history pages. Offline reading depends on a debounced copy of the in-memory screen, not on the frames that arrived. A gap can leave the last flags on screen while later content is discarded. An empty page can be filed as the conversation. A large plan is replaced by a sentence, so the phone cannot review it.

## 2. The sync this plan installs

One grain. One cursor. One store. One resume answer. One outbound queue, pulled by one link thread. No second decode path.

The cursor is the mirror head. The epoch string already stored by the host, and already kept by the phone as `hostEpoch` / `streamId`, is the stream id. Do not mint a second id. `conversation_id` is never `current`. The Room host key stays the installation host id the phone already stores, falling back to the pinned fingerprint only when that id is absent, so existing rows stay readable. Turn and block ids are stable across stream ids. That is what lets the phone keep its cache across a gap.

Four watermarks, kept separate so a pump cannot enqueue the whole unacknowledged tail on every pass: produced (mirror head), queued (sitting in the outbox), sent (handed to TLS), acknowledged (phone ack). The link thread pulls the next event when the queued watermark is behind the produced watermark and the unacknowledged serialized event bytes are inside the credit window.

Three kinds of transfer:

- **State.** Latest value of one key. No sequence. Sent on change and before any content on resume. Keys required for a fast connected response: `status` (`busy`, `sending`, `phase`, `status_text`, `can_send`, `can_steer`, `can_stop`, and `started_at`; the phone computes elapsed time) and `approval`. Other menus may follow. They must not block status.
- **Slice.** One mirror event, one sequence number, assigned when the event is appended to the log. `turn_open`, `block_open`, `block_append`, `block_replace`, `block_close`, `turn_close`, `title_changed`, `image_added`. The mirror splits a long append into slices of at most 4 KiB of UTF-8, on a code-point boundary, before it assigns sequences, and it splits smaller when JSON escaping would push the encoded frame over `outbox_frame_bytes` (32 KiB). The phone applies a slice only when its sequence is the stored sequence plus one. A lower sequence is a duplicate. A higher sequence is a gap.
- **Fetch.** The phone asks for what it does not have: a block body from a byte offset, a turn that is not in the cache, an image, or the plan body. The host answers in pieces of at most `block_data_bytes` (24 KiB). Each answer names the request, the revision, the total byte length, the offset, and `last`. Fetches are not pushed on connect, and a fetch never allocates or advances a live event sequence.

Connected behaviour:

- The phone paints the Room conversation as soon as it opens, then sends `resume` with conversation id, stream id, and sequence. It does not wait for a snapshot to show cached text.
- The link thread answers from the mirror. The IDE thread is not on the resume path. There is one answer.
- If the stream id matches and the log still holds every event after the sequence, the host sends `resume_ok` and replays those slices. No catchup blob. No snapshot.
- Otherwise the host sends state, then a baseline at a head H captured under the mirror lock: `snapshot_begin`, as many `snapshot_page` frames as the outline metadata needs, then `snapshot_end`. The outline carries turn ids, indexes, prompt previews, and per block its id, kind, state, revision, byte length, and body hash. It carries no historical body. The open block's current body may sit inline in `snapshot_begin` when the encoded frame stays within 32 KiB. Otherwise that block is deferred and the phone fetches it at once. `snapshot_end` is a barrier: it is not taken until every earlier frame of that resume generation has been taken. Pong, approval, and command acknowledgements may pass a page. They may not pass `snapshot_end` ahead of its pages. Live events begin at H+1. The host does not fabricate append events numbered at or below H.
- The phone commits the baseline in one Room transaction at `snapshot_end`. It keeps every cached block whose hash matches, marks the others stale, removes turns and blocks the completed outline does not name, and stores the new stream id and head. A failed or incomplete stage keeps the previous committed view. Stale blocks stay visible, marked not current, until a fetch replaces them. Byte length is not identity. An empty observation is `not_ready`, and it is not filed as a conversation.
- The mirror log is the only retained copy of a slice. The outbox log lane holds only what is inside the credit window (512 KiB of serialized unacknowledged event JSON, the existing `MonitorCreditWindowBytes` / `InboundCreditBytes`). A socket drop loses nothing the log still holds. When the 8 MiB log budget folds older events, a later resume from before the oldest kept event takes the baseline path. An offline phone does not require unbounded retention.

Offline behaviour:

- Room is the only conversation the UI reads, connected or not. Disconnect does not clear it. Commands that need the host are disabled. Reading is not.
- Each applied batch commits the rows, the deferred obligations, and the sequence in one transaction, and only then is the sequence acknowledged. A process kill must not show text the cursor does not cover, and must not acknowledge text that was discarded.
- Rows imported once from `monitor-cache` have no sync provenance. They are readable offline. The next resume of those rows is a baseline. Do not invent a cursor for them.

Plan, coordinated by the IDE and transferred in full:

- The plan belongs to the project, not to one conversation. The IDE stays the authority. `select_plan`, `new_plan`, `close_plan`, `run_plan`, `stop_plan`, `run_task`, and `insert_task` keep the form's existing remote handlers. `work_on_plan` stays refused: Run Plan starts at the first item that is not complete. Which section runs is not a wire decision.
- State key `plan` is path, title, running, revision, and the row summaries (`index`, `level`, `title`, `parent_title`, `status`, `actionable`). State key `plan_choices` is the choice list `PushPlan` already gathers. State key `tasks` is the task rows. The other spec keys (`status`, `session`, `mode`, `target`, `targets`, `conversations`, `models`, `reasoning`, `permissions`, `approval`) go out the same way: on change, and before content on resume. A conversation gap does not freeze them.
- The revision is FNV-1a 64 of the whole file, with the same basis and prime as a block hash, written as 16 lowercase hex digits. It is not `PlanTextFingerprint` of the capped preview. The existing plan file timer remains the detector. Hash a file over 256 KiB off the IDE thread. The pump publishes the cached revision and the rows. It does not read the file.
- The body is `plan_get {path, offset, revision}` answered by `plan_data {path, revision, offset, text, total_bytes, last}` pieces of at most 24 KiB of UTF-8. Each piece is its own frame on the bulk lane. The body is not one `chunk` item, so `max_item_bytes` (4 MiB) does not apply and is not a reason to stop. There is no size at which the host refuses a plan. Delete "The plan is too large to cache on the phone." The monitor path does not call `ReadMonitorPlanPreview`, and it does not append "The rest of the plan is on the desktop."
- The host reads the file in slices when a `plan_get` is in progress, off the IDE thread, and releases any lock before the read and the socket write. A revision that changes mid-transfer is `revision_changed`. The phone starts again from offset 0. The same revision resumes from the stored length.
- If the encoded `plan` state exceeds `outbox_frame_bytes` (32 KiB), send it as `chunk` frames on the state lane. Do not drop rows to make it fit.
- The phone keeps a body file per host and path for every path still in `plan_choices`, plus the one on screen. Rows and revision stay in the plan record. The markdown is not stored inside `rowsJson`, `planCacheText`, or `MonitorUi` once `total_bytes` exceeds 256 KiB (`inline_body_bytes`). Under that size the body may stay in memory, as it does today. Offline review reads the file. A path that leaves `plan_choices` drops its file after the plan screen leaves it. A full disk keeps the prefix, reports storage, and does not substitute a sentence for the document.
- A body over 256 KiB would break the 150 ms budget if it were pushed as content. It stays on the bulk lane and yields every frame, so a live turn and a pong are not behind it. While `last` has not checked out, the plan screen shows a progress dialog: bytes received, `total_bytes`, and a way to open the incomplete prefix. The dialog does not cover the conversation and does not disable send, steer, stop, or approval. It closes when the length and the final piece check. Cancel stops the fetch and leaves the prefix labelled incomplete, with a way to continue. A body of 256 KiB or less arrives without the dialog.

Rules that bind every item:

- Capture the head, the outline, and the stream id under the mirror lock, then release the lock before encoding JSON, writing the socket, or touching Room or the UI.
- Tag queued work and phone staging with the connection generation and the host, conversation, and stream identity. A new resume cancels unsent work of the old generation. The receiver discards a response whose generation, revision, or identity does not match the fetch it still wants.
- One credit authority. The mirror retains the log. The outbox tracks what is queued inside the window. `TMonitorLogCredit`'s hold-then-copy path does not remain beside that.
- `bye` on overflow is best effort, with a bounded flush, and is not a prerequisite for closing the socket. Unavailable content is `not_found`. Transient overload is a documented retryable error. Do not report overload as a missing object.
- Offsets and lengths count UTF-8 bytes. The host never splits a code point.

Transport:

- A link thread owns the accepted socket, including the TLS handshake. It waits on the socket and on a wake handle together, so a queued frame and an arriving ping both wake it at once. The accept loop only accepts and hands the socket over.
- Each wake reads what is readable, then writes a bounded quantum, then returns to the poll, so a bulk stream cannot sit on the write path while a ping waits in the receive buffer. Priority is control, then state, then slices inside the credit window, then fetches. A partial TLS write keeps its buffer and offset. `SSL_ERROR_WANT_READ` and `SSL_ERROR_WANT_WRITE` retry the same call. An owed read is retried before a new write. A new frame is not inserted into an unfinished one.
- One queue: `TMonitorOutbox`. The session lanes and the carrier FIFO are deleted.

Budgets, still the acceptance bar. The split below is a design allocation to tune against, not a measured result and not a set of additive percentile guarantees: about 20 ms to observe, 25 ms to schedule and cross the LAN, 50 ms to apply, 25 ms in the database, 25 ms to draw.

- IDE change to the phone screen while a turn streams: p95 under 150 ms on a LAN, measured through the real producer.
- Pong while slices or fetches are queued: under 100 ms.
- After a drop of up to 60 s, with a backlog up to 2 MiB, the cached screen is visible immediately and current state plus the open block are filled within 1 s, without re-sending cached history bodies.
- With no network, the last committed conversation is readable, including stored bodies, and so is a plan body that finished transferring.

Do not grow `AssistantMonitorSession.pas`, `AssistantMonitorBridge.pas`, `AssistantMonitorCodec.pas`, `AssistantMonitorLan.pas`, `MonitorCoordinator.kt`, or `MonitorViewModel.kt` with the new path. Put the link thread in `AssistantMonitorLink.pas` and host sync decisions in `AssistantMonitorSync.pas`. Put phone apply rules in the existing `SyncApplier` path or a new file next to it. Deleting the hybrid should shrink the old files. Item 8 checks that this happened.

## 4. Transport first

This section changes no content format, so it ships before the cut and is measured on catalogue 2. It is the largest single gain for the connected response and the precondition for every later budget.

### 4.1 One link thread with a wake handle
Status: complete

Add `Source/LazAssistantMonitor/AssistantMonitorLink.pas`, registered in `Packages/LazAssistantMonitor.lpk`. The listen thread keeps `TInetServer` for accept and the simultaneous cap, then hands the controller socket to a link thread and stops touching it. The `SSL` object is used by the link thread only, including a non-blocking `SSL_accept` under the existing 10 s handshake deadline.

The link thread loops on `fpPoll` over the socket and the read end of an `fpPipe` on Unix, or `select` on the socket plus a loopback socket pair on Windows, as the October plan's item 4.1 specified. Write interest is requested only while a frame is ready or a write is owed. Each wake reads until `SSL_ERROR_WANT_READ`, hands complete frames to the session handler, then writes one bounded quantum (one frame, or until the socket would block). Heartbeat and partial-frame timeouts use the poll timeout. `AcceptIdleTimeOut` may stay 250 ms. It is no longer on any send or receive path.

`TMonitorOutbox.OnWake` writes one byte to the wake handle. Queueing a frame wakes the link thread in the same turn. Preserve the owed-read-before-write rule from `WriteOnce`, and preserve the unsent offset across `WANT_WRITE`.

Heartbeat and dead-link detection stay at 10 s and 30 s. `NoteTime` runs from the link thread's poll timeout, so a quiet socket is still watched while the accept loop is blocked in `select`. TCP keepalive stays as it is.

A new socket that finishes TLS replaces the controller. The old link queues `bye {reason: "replaced"}`, flushes for at most 500 ms, and closes. The session resets as it does on a socket close, and the new link starts at `mssAccepted`. Delete the `rejected {reason: "busy"}` spare-socket path in `AssistantMonitorLan.pas`. A handshake that stalls must not delay frames on the link already up. `MonitorSimultaneousCap` still bounds how many sockets are accepted.

### 4.2 One queue
