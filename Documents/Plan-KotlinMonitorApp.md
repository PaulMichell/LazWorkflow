# KotlinMonitorApp review

Generated by Lazarus Project Assistant.

Review of `Source/KotlinMonitorApp` as it is now. The October note in `Source/KotlinMonitorApp/REVIEW.md` is history; several of its items are already fixed, and it does not describe the live catalogue-3 path. This plan does not change the desktop. The host already wipes its log and bulk lanes on every `resume` (`TMonitorSession.HandleResume` in `Source/LazAssistantMonitor/AssistantMonitorSession.pas`). A phone that asks again while a plan is streaming is what drops the link. Do not edit `Source/LazAssistantMonitor` in these items.

The suite was not run for this review. `Source/KotlinMonitorApp/Backup` and `app/build` are not part of the app.

The failure the user sees — Offline, in the same room, on a strong Wi-Fi signal, usually while a plan is running — is software. The screen is painted from Room. The coordinator's own board is often empty. A 250 ms timer treats that empty board as "the chat has no turn" and sends `resume` every 2 seconds. The host then clears the event log and any in-flight `plan_data`. The phone never finishes a snapshot, declares a gap, closes a socket that was still on the LAN, and the chip says Offline for the whole backoff. Screen-off is a second, independent close: the activity sends `bye` when the backlight goes off, so a plan longer than the screen timeout always drops.

## 1. Bugs

In severity order. Each item is a defect, not a style note. Connection robustness is 1.1 through 1.6.

### 1.1 Do not resume while the socket is already delivering the plan
Status: complete

A live plan is dropped by the phone asking the host to start again.

`MonitorCoordinator.flush` runs from `MonitorViewModel` every `ScreenRefreshMs` (250 ms). It looks only at `content.current()`. If that board has no turn, and a conversation id is set or catch-up is on, it sends `resumeNow()` every 2 seconds. The screen does not use that board. `shownConversation` paints Room (`storedBoard`). `noteHostConversation` replaces the coordinator board with an empty list and zeros `hostEpoch`, `hostCursor`, `resumeStream` and `resumeSeq`. Nothing copies Room rows back into `content`. So for a normal live plan the board flush inspects stays empty, and flush keeps firing.

`resumeNow` then prefers `encodeSyncResume(resumeConversation, resumeStream, resumeSeq)`. After `noteHostConversation` that is stream `""` and seq `0`. `followHostConversation` sends the same frame the first time it sees the id. An empty `stream_id` misses the host's tail-replay check (`MonitorSyncResumeAnswer`), so the host builds a full baseline of the open turn, including the plan that is running. Before that it always `ClearLog` and `DiscardBulk`, and sets the phone ack to the resume cursor. A later Room `noteResumeCursor` makes the next flush a tail resume, but the host still clears both lanes. `plan_data` already on the wire is discarded. The phone sees a gap, `SyncResumePolicy` retries, and after 1+2+4+8 seconds `SyncEffect.Reconnect` calls `session.reconnect()`, which cancels the live socket.

Two more senders use a different, incomplete encoder. `LanSession.requestLiveSync` and the last branch of `resumeNow` call `encodeResume(id, epoch, cursor)`, which writes `epoch` and `cursor` and omits `conversation_id` and `stream_id`. `MainActivity.onStart` and `onResume` both call `enterForeground`. The session starts with `inForeground` already true, so a resume that is not a return from background calls `requestLiveSync` on whatever socket is up. Catalogue 3 requires those fields. The host answers `error` reason `protocol` and does not have to clear the lanes, but it is still a stray resume on a live plan.

Locations: `MonitorCoordinator.kt` `flush`, `resumeNow`, `noteHostConversation`; `MonitorViewModel.kt` `followHostConversation`, the 250 ms loop, `enterForeground`; `LanSession.kt` `requestLiveSync`; `Messages.kt` `encodeResume`; `SyncFrames.kt` `encodeSyncResume`.

Fix: one resume rule. Send `resume` only from the hello path, from an explicit gap, or when the user opens another stored conversation. The payload is always `encodeSyncResume` with the Room cursor for that `(host_id, conversation_id)`. Seq 0 and an empty stream are allowed only when Room has no row. Do not send again while the same socket is still receiving frames for that cursor. `flush` must not treat an empty coordinator board as an empty chat when Room has rows, and must not send `resume` on a timer. `noteHostConversation` must not zero a cursor Room already stored. `requestLiveSync` must not run on an already-live socket. Delete the epoch/cursor-only `encodeResume` once those callers are gone.

Acceptance: a coordinator test with a live phase, an empty `content` board, and a Room cursor of seq 50 sends nothing for several flush ticks. A test that the desktop conversation id arrives does not emit stream `""` / seq 0 when that cursor exists. A test that `enterForeground` while already in the foreground and already live sends no resume. `ProtocolV3FixtureTest` still accepts the catalogue resume fixture.

### 1.2 Keep the socket up when the screen sleeps during a plan
Status: complete

`MainActivity` registers `ACTION_SCREEN_OFF` and calls `leaveForeground`. `onStop` does the same. `LanSession.leaveForeground` sends `bye` reason `background` and closes the socket. A plan that outlasts the screen timeout therefore always shows Offline, with the phone still on the desk and the radio still associated. There is no foreground service, no wake lock, and no Wi-Fi lock in `AndroidManifest.xml`. After the bye, Android may also freeze the process; the host then hits `MonitorDeadSessionMs` (30 s) even if the bye was lost.

Leaving the app (`onStop` because another activity is in front, and this is not a configuration change) may still send bye. The backlight going off must not. While a plan or a turn is running, or while the monitor task is still the resumed task, hold the TLS session across screen-off. A foreground service with a connected-device or data-sync type, plus a Wi-Fi lock, is what keeps the radio and the process awake. Do not add a second socket. The chip stays Live or Busy. When the user actually leaves the app, bye and the current backoff stay.

Acceptance: a session test can drive `leaveForeground` from a screen-off flag separately from `onStop`. Screen-off while `planRunning` does not close the owned socket and does not send bye. `onStop` still does. The manifest declares the service and the lock permission the implementation uses, and no other new permission.

### 1.3 One thread owns the TLS socket
Status: complete

`SslSocketConnector` builds a blocking `SSLSocket` (`soTimeout` 1 s, `keepAlive` true, `tcpNoDelay` never set). `readUntilClose` then runs `readFrames` and `ConnectionWriter.run` as two coroutines. `readFrames` calls `input.read`. `writeBytes` calls `output.write` and `flush` on the other thread, under `socketLock` only. `SSLSocket` is not safe for a concurrent read and write. During a plan the phone writes an ack about every 250 ms while the host writes a continuous stream. A write that blocks because the TCP window is full (the host is inside `HandleResume`, or not reading) holds the SSL engine; the reader never reaches `noteInbound`. Thirty seconds later `inboundIsDead` and the host's `CheckTimeoutsLocked` both close the link. The chip goes Offline. Idle, the two threads rarely overlap, so the same phone looks fine until a plan starts.

The host already avoids this: `TMonitorLinkThread.ServiceOnce` polls, reads, then writes one quantum, on one thread.

Fix: one connection thread for one socket. It reads with the 1 s timeout, writes at most one frame, then checks the heartbeat. It never calls `getInputStream` and `getOutputStream` from two threads. Set `tcpNoDelay` so an ack is not held for a following bulk write. If a write is still in progress when the dead-session clock expires, close that socket from the same owner; a blocked write must not hide the reader for 30 s. Do not add a second TLS stack or an HTTP client. Ping and pong stay on the control lane and are answered from this thread, not from the UI.

Acceptance: extend `LanSessionTest` with a connector whose write blocks until a read is attempted. The session must still record inbound bytes and answer a ping. A second test closes the socket when a write outlives `DeadSessionMs`. The existing silent-peer test still closes at 30 s and does not treat a 1 s read timeout as a dead host.

### 1.4 Do not drop events and then close a live socket
Status: complete

`AccountedEvents` holds 512 KiB. Past that, `offer` does not queue the event, sets overflow, and returns success. `LanSession.onFrame` sends one `refusedEvents` entry and keeps reading. Those events are never applied and never acked. The host has already counted them against `credit_window_bytes` and will not move the log until an ack. The replay the refusal asks for is dropped the same way while the window stays full. `SyncResumePolicy` then emits `SyncEffect.Reconnect`. `onSyncEffect` calls `session.reconnect()`, and `startLoop` increments the epoch and closes the socket that was still carrying control frames.

The file header says a slow collector is a failed delivery, not a dropped frame. The code drops the frame and continues.

Fix: when the 512 KiB window is full, stop reading further log events (leave them in the TCP window) so the host's own credit pause applies. Do not discard a seq that has not been committed. `SyncEffect.Reconnect` may close the socket only after inbound has already stopped, not while `LinkPhase.Live` and frames are still arriving. Ack only a committed cursor, which is already the rule. A gap still resumes in place, with the backoff already in `SyncResumePolicy`, and does not call `startLoop` on a healthy socket.

Acceptance: a unit test fills `AccountedEvents` and shows the next event is not dropped and not acked. A coordinator or applier test that a gap fires `Resume` and not `Reconnect` while the link phase is Live. After the window drains, the held event is applied in order.

### 1.5 A Wi-Fi callback must not latch the link off
Status: complete

`WifiLanWatch.onLost` can run while a roam or a capabilities change briefly makes `wifiPresent` false. `onWifiLost` sets `lanAvailable` false. `mayReconnect` requires that flag, and `noteActivity` returns immediately when `mayReconnect` is false, so a touch does not retry. Only `enterForeground` and `onWifiAvailable` set the flag back. If the network never left, Android does not send another `onAvailable`. The next real close (1.1 or 1.2) then waits on `wakes` with the banner "Waiting for Wi-Fi" until the screen is turned off and on. The chip shows Offline the whole time, on a radio that is up.

`onWifiLost` does not close a live socket. The bug is recovery, not the first drop.

Fix: `lanAvailable` false is a hint, not a latch. A touch, the 30 s in-use retry, and a failed connect attempt all try the saved endpoint. Confirm loss with a second sample before showing "Waiting for Wi-Fi". If `allNetworks` still has Wi-Fi, do not call `onDown`. Do not require `NET_CAPABILITY_INTERNET` or a validated default route; a desk LAN often has neither.

Acceptance: a watch test with `onLost` and `wifiPresent` still true does not call `onDown`. A session test with `lanAvailable` forced false and a touch calls the connector again without an `onAvailable`.

### 1.6 Time a partial frame on the monotonic clock
Status: complete

`readFrames` stamps `FrameAssembler.partialExpired` with `System.currentTimeMillis`. The dead-session check uses `clock.nanoTime`. A step of the wall clock (NTP, a manual change) can expire a partial frame that is only a few hundred milliseconds old and close the link with `ReadEnd.PeerClosed`. That reconnects in the middle of a plan snapshot. The protocol's 10 s partial-frame limit is a duration, not a civil time.

Fix: pass the same monotonic milliseconds `clockMs` already uses into `offer` and `partialExpired`. A backward step must not expire the frame. A forward step of the wall clock must not either.

Acceptance: a `FrameAssembler` or session test advances the wall clock across a partial frame and does not close. Advancing the monotonic clock by `PartialFrameMs` still closes.

### 1.7 An in-use retry is not Offline
Status: complete

`connectionChip` returns Offline for every phase that is not Live and not the narrow syncing case. `LinkPhase.Connecting`, the "Reconnecting" banner, and "Waiting for Wi-Fi" all print Offline. `linkChanged` also clears `catchingUp` on every disconnect, so the syncing exception does not survive the drop that needs it. The user reads a 1 second backoff, or a handshake still in progress, as a dead link.

Fix: while `reconnectable` is true and the app is in use, the chip says Reconnecting (or Connecting once the attempt has started), not Offline. Offline is for a paused, unpaired, or idle-until-touch link, and for a real Wi-Fi loss after 1.5. Do not invent a fourth label. Busy still wins when the phase is Live and a plan or turn is running.

Acceptance: extend `ConnectionChipTest`. Disconnected plus the reconnecting banner and a reconnectable session is not Offline. Paused, and idle-until-touch, still are.

## 2. Dead or obsolete code

Only symbols with no production caller, or stubs whose only result is empty. Do not delete a catalogue type an incoming frame can still carry. Do not delete `settleFinishedTurn` or `noteSocketClosed`; the coordinator still uses them.

### 2.1 Remove the catalogue-2 screen reducer
Status: complete

`applyIncoming` never calls `reduceMonitor`. The live screen is `MonitorCoordinator.incoming` plus Room. `reduceMonitor`, `mergeApplied`, `applyLink` and `connectionLabel` remain in `MonitorViewModel.kt` and are called from `MonitorReducerTest` only. They still describe snapshot, status and plan frames the catalogue-3 host does not send as those types. Keeping them implies a second screen owner and hides the real resume path.

Delete those four functions and the private helpers that exist only for them. Retarget or delete the `MonitorReducerTest` cases that only drive them. Keep tests that cover behaviour the coordinator still implements, and move those assertions onto the coordinator if they are not already there.

Acceptance: a search of `app/src/main` finds no `reduceMonitor`, `mergeApplied`, `applyLink` or `connectionLabel`. `:app:testDebugUnitTest` passes. The coordinator tests still cover send, steer, unsaved edits, and a live-to-disconnected chip.

### 2.2 Remove the empty coordinator stubs
Status: complete

These always return empty or null, and the callers ignore that result:

- `collectMissing` returns `emptyList()`. `MonitorViewModel` applies it for `MonitorEffect.Prefetch`.
- `requestTurnFetch` returns `emptyList()`. `MonitorViewModel` calls it for a visible turn index.
- `turnForImage` returns null. Image placement already falls through to the live turn index.
- `revealHeldLink` returns null and has no caller.
- `holdingLink` is always false. `requestedTurnEntries`, `inFlightImageKeys`, `loadedImageKeys` and `bitmapKeyEntries` are always empty.

Delete the stubs and the call sites. Do not replace them with new fetch logic in this item. Body fetch stays in `ScreenFetch`.

Acceptance: the package tests compile and pass. No remaining reference to those names under `app/src/main`.

### 2.3 Delete the epoch/cursor-only resume encoder
Status: complete

Depends on 1.1. `encodeResume` in `Messages.kt` writes `epoch` and `cursor` and not the catalogue-3 fields. After 1.1 nothing sends it. `decodeResume` stays if a test or the host-error path still reads an old payload; do not remove a decoder an inbound frame can still hit. Delete `encodeResume` and any test that only round-trips that shape.

Acceptance: `encodeSyncResume` is the only resume encoder in `app/src/main` and `protocol/src/main`. The golden resume fixture still passes.

## 3. Simplifications

### 3.1 One resume cursor, owned by the session
Status: complete

Depends on 1.1. Resume is currently decided in `flush`, `resumeNow`, `followHostConversation`, `requestLiveSync`, `queueStoredResume`, hello, and `onSyncEffect`. The UI should not encode a resume. The session exposes one operation, `resumeFromRoom(conversationId, streamId, seq)`, and refuses a second call for the same triple while that socket is live. The ViewModel tells it the cursor when Room emits, and tells it to resume on hello and on a gap. That is the whole API.

Acceptance: a search of `MonitorViewModel.kt` and `MonitorCoordinator.kt` finds no `encodeSyncResume` and no `encodeResume`. The tests in 1.1 still pass against the session method.

### 3.2 One applier job, not on the main dispatcher
Status: complete

`SyncApplier.start(viewModelScope)` runs on the main dispatcher. `tick` holds the applier mutex and calls Room. The reader's apply coroutine also calls `offer`, which flushes the same mutex from `Dispatchers.IO`. A plan batch therefore contends the main thread with Compose, and an ack posted with `Dispatchers.Main.immediate` waits behind that Room work. Credit stalls, which is how 1.4 starts.

Run the tick loop on `Dispatchers.IO`. `offer`, `offerFrame` and `noteRefused` are already called off the main thread; keep them there. `onSyncEffect` may post the resulting ack, state row, or resume to the main thread, but it must not do the transaction there. One job owns the 50 ms flush. Do not add a second applier.

Acceptance: a test or a debug assertion that `tick` is not entered on the main dispatcher. An existing applier test still commits a 50 ms batch and emits one ack.

### 3.3 The chip has one input
Status: not started

Depends on 1.7. `disconnected`, `LinkPhase`, `catchingUp`, `pairedElsewhere` and the banner can disagree. `applyLink` is not on the live path (2.1). `linkChanged` writes `disconnected` and the banner; the chip then ignores the banner.

Drive the chip from the link phase, the reconnectable flag, and busy. The coordinator may keep `disconnected` as a derived value for buttons, but it must be `phase != Live && !reconnectable`, not a flag that a later state frame can leave true while the socket is up. Delete any remaining copy that sets `disconnected` without going through `linkChanged`.

Acceptance: the 1.7 chip tests, plus a coordinator test that a Live status clears `disconnected` and a later chrome update does not set it again.

## 4. Performance

These are the costs that grow while a plan streams. They also delay acks, so they belong in the same robustness work. Do not rewrite the markdown parser or the JSON codec beyond the items below.

### 4.1 Do not rebuild the conversation or redecode images on every append
Status: not started

`watchScreen` collects turns, blocks, images, repairs and the conversation row on the main `viewModelScope`. Every Room emission, which a plan produces about every 50 ms, calls `documentFromRows` on the full block list and copies every body into a new `WireTurn` graph. It then launches `loadStoredImages`, which reads and decodes every image file again and merges them into `bitmapsState`. There is no cancellation of the previous decode. `observeBlocks` has no incremental query; it returns every body in the conversation.

Fix: collect on `Dispatchers.IO`. Publish only the changed turn to the UI. Decode an image when its id or file length changes, not when an unrelated block appends. Cancel the previous screen collection when the conversation id changes, which `watchScreen` already does; also cancel an in-flight decode for an id that was replaced. Keep the existing bitmap byte cap.

Acceptance: a fake store that emits two block updates and one unchanged image list decodes that image once. The UI state after the second append reuses the unchanged turn instances (identity, not a deep copy).

### 4.2 Do not reparse the whole live body on every token
Status: not started

`MarkdownText` does `remember(source) { parseMonitorMarkdown(source) }`. A streaming thought or answer changes `source` on every batch, so the whole body is parsed again, and the `Column` inside the row is rebuilt. A long plan thought makes this the main-thread cost beside 4.1.

Fix: for a live block, parse on a short trailing window or debounce to one parse per frame, and keep the already-parsed prefix when the new body starts with the old body. A finished block still parses once. Do not change the markdown dialect. Tables and code groups keep their current look.

Acceptance: a pure test that appending to a previously parsed body does not re-walk the unchanged prefix. `MonitorMarkdownTest` still passes for a full document.

### 4.3 Count UTF-8 without copying the block
Status: not started

`utf8Length` in `FrameCodec.kt` calls `strictUtf8Bytes`, which allocates a byte array of the whole string. `holdAppend`, `prefixHash`, and the applier call it on the live body as that body grows. A multi-hundred-kilobyte thought therefore allocates a full copy on every append, on top of the Room write.

Fix: a length walk that does not allocate, used by the hot path. Keep `strictUtf8Bytes` for the codec, where the bytes are the payload. Invalid UTF-16 surrogates still count as the replacement length the codec would write, or the call fails the same way it does now; do not silently shorten a body.

Acceptance: a protocol test that `utf8Length` matches `strictUtf8Bytes().size` for an empty string, a BMP string, an emoji, and a string past 100 KiB. The append-hold tests still place the next offset at that length.
