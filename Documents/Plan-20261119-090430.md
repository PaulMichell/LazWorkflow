## 1. Correctness and responsiveness

### 1.1 Prevent repeated polling from starving plan revision publication
Status: complete

High priority. In `Source/LazAssistantTools/AssistantPlanDocument.pas`, `Execute` clears `HasJob` before hashing. While the read is in progress, an identical request can pass both checks in `Request` (line 274), increment the generation and queue the same read. `Serve` then discards the completed hash. When hashing takes longer than the polling interval this can repeat indefinitely. The same-stamp branch in `ProjectAssistantForm.pas` (line 2764) depends on publication to notice an edit that preserves length and timestamp.

Track the running request separately from the pending request under the existing lock. Coalesce identical requests and preserve supersession when the requested file or stamp changes. Include the resolved file path in both request and publication identity. The current cache compares the caller’s path, so switching projects with identically named plans can briefly return the previous project's revision.

Verify with a deliberately delayed hash and repeated polls. Require one read and eventual publication. Then change the requested stamp mid-read and confirm only the latest revision is published. Switch between two project roots with matching relative paths, sizes and timestamps but different contents.

### 1.2 Keep account refresh and window closure responsive
Status: complete

High priority. `StartPlanUsageRefresh` in `Source/LazAssistantTools/AssistantSettingsForm.pas` retrieves a token before starting its worker (line 950 vicinity). `GetValidAccessToken` in `GrokOAuth.pas` (line 902) can refresh an expired token synchronously. Once the worker starts, closing settings calls `ReleasePlanUsageRefresh`, which waits on the UI thread for the account query to finish (line 875). Either delay can make the IDE appear frozen.

Give one background operation ownership of token refresh and usage lookup. Coordinate access to the shared OAuth client's mutable token state. Detach the closing form from the operation, and retain worker ownership until completion or cancellation, including during package shutdown. Check the corresponding token acquisition in `ProjectAssistantForm.StartAccountUsageWorker` when moving this work.

Verify using a delayed provider with a refreshable expired token. The settings window should repaint during refresh, close while the query is pending, and reopen without receiving the previous window's completion.

## 2. Optimisation and reuse

### 2.1 Remove the second account-label refresh on each Codex timer tick
Status: not started

In `AssistantSettingsForm.pas`, `PlanUsageTimerTimer` calls `ShowCodexPlanUsage`, which already calls `NotifyOpenProjectAssistantFormsAccountUsage`. On the ordinary tick with no active worker, the timer calls the same notifier again. Each call walks every open form and reapplies the usage label to each assistant window (`ProjectAssistantForm.pas`, line 9999).

Separate rendering the selected connection's label from notifying other windows. Give the timer one notification point and preserve refreshes initiated outside the timer. Verify with two assistant windows, both provider selections and a pending Grok lookup. Count at most one notification pass per tick and check the final labels.

### 2.2 Avoid copying the unsent suffix after each partial monitor write
Status: not started

In `Source/LazAssistantMonitor/AssistantMonitorLink.pas`, `WriteQuantum` (line 1069) deletes the accepted prefix after every successful TLS write. Repeated short writes on a large frame can repeatedly move most of the remaining bytes. The receive loop in the same unit already advances an offset and defers compaction.

Measure the short-write case first. If copies contribute materially, keep the frame buffer with a send offset until the frame completes. Advance only on successful writes, preserving TLS retry arguments, outstanding-write flags and the point at which the goodbye frame is marked sent. Exercise alternating short writes and would-block returns in the monitor link tests. Compare delivered bytes, frame order and CPU time against the current implementation.
