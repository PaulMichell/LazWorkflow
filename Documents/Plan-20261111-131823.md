## 1. Findings and intended behaviour

The strongest explanation for remaining offline during a long plan is the phone's inactivity policy: `LanSession.appIdle()` considers only the last interaction, and `runLoop()` parks retries after 120 seconds. The screen-off hold preserves an existing socket but does not override that retry policy. A drop after prolonged passive monitoring can therefore remain offline until interaction. This path is confirmed in source; it is not yet a confirmed diagnosis of the reported device incident.

Other high-priority findings are coroutine/thread ownership mismatch, incomplete failure supervision, blocked sync recovery, and connection-local state surviving automatic reconnects. On the desktop, a new TLS connection retires the current controller before application authentication. Keep the existing threaded carrier, control-priority outbox, durable Room cursor, command ledger, certificate pinning and bounded backoff; repair their lifecycle and recovery rules.

Success means a running plan survives transient loss without restarting either app, re-pairing, losing committed content, or executing commands twice. Distinguish transport connected, authenticated, synchronising, current, retrying and user-action-required states. Heartbeat traffic alone must not prove that application sync is healthy.

Kotlin connection filenames refer to `Source/KotlinMonitorApp/app/src/main/kotlin/computing/michell/monitor/connection/`; data and UI filenames refer to the sibling `data/` and `ui/` directories. ## 2. Repair phone connection lifecycle first

### 2.1 Keep retrying during active plan and turn monitoring
Status: complete

Priority: critical for the reported symptom. Evidence: `LanSession.kt` around lines 880–971 (`runLoop`, `appIdle`), lines 774–791 (`leaveForeground` screen-off hold), and `ui/MonitorViewModel.kt` lines 1115–1140. `appIdle()` uses only `lastActivityMs`; neither plan activity nor `holdingAcrossSleep` prevents retry parking.

Introduce an explicit monitoring demand supplied by the model: running plan, running turn, or an intentional screen-off monitoring hold. Preserve this demand through a transient disconnect until resynchronisation establishes that execution ended. While demand exists, continue capped, jittered retries regardless of touch age. Retain idle parking when there is no monitoring demand and retain intentional background/disconnect behaviour. Do not fake touch timestamps on every frame.

Acceptance: advance the monotonic clock beyond two minutes, drop the link during a plan, restore the host/Wi-Fi, and observe automatic recovery without touching the screen. Repeat with the screen off. Confirm idle non-monitoring sessions still stop retrying and explicit disconnect stays disconnected.

### 2.2 Replace OS-thread identity checks with serial connection ownership
Status: complete

Priority: high. Evidence: `LanSession.kt` around lines 1217–1274 assigns `socketOwner = Thread.currentThread()` in `serviceLink`; `writeBytes` around lines 1411–1413 refuses a different thread. The same coroutine suspends in `delay(50)` and in `onFrame` → `applyHostStates` → `ledger.applyHost` (Room). `Dispatchers.IO` does not guarantee resumption on the same thread. After a migration, `writeBytes` returns false and `serviceLink` ends the link as `WriteFailed`, so this can cause spurious drops as well as lost writes. The finally block can also fail to clear `socketOwner` after migration.

Make connection ownership an actor/context invariant rather than a physical thread identity. Route all writes, including opening hello/auth/resume, catalogue commands and background bye, through that owner. Prevent the `offerCommand` fallback from writing directly during writer setup/teardown. Use a dedicated dispatcher only if required by the socket implementation and justify its lifecycle; otherwise one serial coroutine is sufficient. Keep a separately controlled close path capable of unblocking blocking I/O.

Acceptance: force suspension and dispatcher migration while delivering frames and applying command states; writes must continue successfully with no concurrent stream writers and no stale owner after close.

### 2.3 Make child failure and cancellation end the owned connection reliably
Status: complete

Priority: high. Evidence: `readUntilClose` creates a `SupervisorJob`, starts serving/applying/framing/refusing children, then joins serving. The outer exception handler only publishes Disconnected. Failure of a sync child need not stop the socket; failure of serving can leave `readEnd` as Continue. `runLoop` lacks an encompassing owned-link cleanup/retry boundary: if `readUntilClose` throws, `closeLink()` is skipped, the loop job ends and `link` stays non-null, so `noteActivity()` returns early and a touch no longer starts a retry (only a foreground return or Wi-Fi callback restarts the loop). `attempt` catches `Exception`, including coroutine cancellation, around opening a blocking socket.

Define explicit outcomes for I/O failure, sync-worker failure, cancellation, terminal authentication failure and intentional pause. Propagate unexpected child failure to the connection supervisor, close exactly its owned socket in a finally path, cancel/join its workers, and schedule a retry when permitted. Rethrow CancellationException. Ensure a socket returned during cancellation is closed even if withContext cannot deliver its result. Make opening cancellable/bounded and prevent predecessor joins from indefinitely blocking a user-requested reconnect.

Acceptance: inject exceptions into decoder, ledger, applier and connector paths; no live socket may remain with dead workers and no Disconnected state may lack either a pending retry or an explicit pause reason. Verify socket/resource counts after repeated connect/cancel cycles.

### 2.4 Give every physical connection a distinct generation
Status: complete

Priority: high. Evidence: `epochCounter` changes in `startLoop`/`disconnect`, but automatic attempts within `runLoop` reuse its epoch. `events`, `syncFrames`, `refusedEvents` and `chunks` are session fields; `chunks.reset()` occurs at loop start/disconnect rather than each automatic reconnect. Deferred work and partial assembly can therefore outlive the socket which produced them. Catalogue writes additionally check socket identity, which must be preserved.

Separate reconnect-loop lifetime from physical-connection generation. Allocate a connection context for each successful open, including writer, assembler, transient queues, last-I/O times and close outcome. Tag downstream work/results with that generation and reject stale completion. Preserve durable Room content and the command ledger; discard or reconcile uncommitted transient data using the durable cursor. Specify how already-committing transactions finish safely before the next baseline is applied.

Acceptance: disconnect mid-chunk, mid-baseline, with queued state and while a command result is delayed. Reconnect automatically and confirm no old frame mutates new connection state, no mixed assembly occurs, and no accepted command is replayed twice.

## 3. Recover application progress and control traffic

### 3.1 Allow forced recovery when sync is stuck despite live heartbeats
Status: complete

Priority: high. Evidence: `data/SyncApplier.kt` emits Reconnect from `giveUp` only after `SyncApplyRetries` (3) event-batch failures, and `SyncResumePolicy` emits it after four waits. A `SnapshotEnd` baseline commit failure returns no effect and does not emit Reconnect. `reconnectAllowed` refuses when linkLive and framesArriving are true; `LanSession.reconnect()` uses that gate, including the `hold=true` Resume path. `framesArriving()` also returns true while event reads are paused. `resumeFromRoom()` drops an identical cursor on the same epoch, and also drops a later cursor for the same non-empty conversation (`seq > sentResumeSeq`), despite the port comment that a later cursor may send again. `writeResume` records the cursor as sent even when `offerControl` fails. Repeated gap resumes can therefore be consumed without a retry frame or a new link.

Separate an opportunistic UI refresh from a forced recovery after bounded lack of durable progress. Track committed cursor/baseline progress independently from ping receipt. Permit explicitly bounded same-cursor retries for a sync gap, or replace the connection once a deduplicated resume has made no progress. Reconcile the later-cursor refusal with the port comment, and do not record a resume as sent unless its frame was actually accepted for write. Reset the recovery budget only on relevant application progress. Preserve protection against gratuitous reconnects during healthy transfers.

Acceptance: deliver pongs continuously while withholding baseline completion or making Room apply fail. Recovery must occur within its documented budget and resume from the last committed cursor. Test repeated identical gap requests and successful progress resetting the budget.

### 3.2 Bound pressure without blocking heartbeat processing or dropping essential messages
Status: complete

Priority: high. Evidence: `ConnectionActor.kt` holds an event that exceeds the 512 KiB budget, but `admitHeld` cannot admit an event larger than the whole budget. `serviceLink` stops socket reads while held events exist; `inboundIsDead` then returns false, while the heartbeat path can still close the connection. `InboundDelivery.offer` drops non-coalesced messages when full; `onFrame` ignores the publish outcome, including for HelloOk that triggers the screen-owned resume. In `InboundDelivery`, coalesced replacements bypass the budget test and `messageBytes` counts String length rather than UTF-8 bytes (the `AccountedEvents` event credit already uses `utf8Length` of the wire JSON). `syncFrames`, writer lanes and refused-events queues are unbounded.

Define a bounded policy for each traffic class. Essential handshake/session/approval transitions must not disappear behind bulk data. Handle a single oversized event explicitly through supported chunking, rejection/resume or a bounded single-event allowance; never hold it forever. Maintain control processing under bulk pressure with bounded decoding and protocol credit, or close/recover deterministically when that is impossible. Account actual wire bytes and coalesced replacements. Scope queues to the connection and propagate queue rejection to a visible recovery path. Move authentication/resume sequencing into the session coordinator where practical, leaving UI observation independent.

Acceptance: stall the consumer/Room, exceed the budget, send Unicode-heavy content and one over-budget event, then restore consumption. Memory remains bounded, essential messages remain effective, control deadlines remain enforceable, and the latest plan/cursor is recovered without restart.

### 3.3 Remove the one-read-timeout delay before each queued outbound frame
Status: complete

Priority: medium, performance and responsiveness. Evidence: `serviceLink` reads first and polls only one outbound frame per iteration; socket reads time out after 1000 ms. With an otherwise quiet peer, a queued command can wait for that read timeout, and a backlog can advance at approximately one frame per timeout. `ConnectionWriter` prioritises controls but cannot wake the blocking read.

Use a bounded outbound drain and a wakeable I/O arrangement. Choose a safe design consistent with the socket library: separately owned reader/writer with one serial writer, or a wakeable transport loop. Preserve control priority, write watchdogs, bounded queues and read fairness. Avoid simply reducing read timeout to a busy polling interval.

Acceptance: benchmark command/pong latency with an idle peer and during a bulk burst; record baseline and after-change p50/p95, wake rate and CPU. Target sub-250 ms local command dispatch under a healthy LAN and no starvation of reads or control frames.

## 4. Harden desktop admission and phone network recovery

### 4.1 Authenticate a replacement before retiring the live desktop controller
Status: complete

Priority: high. Evidence: `Source/LazAssistantMonitor/AssistantMonitorLink.pas` `BecomeController` is lines 716–750 and is called from `RunLink` at line 1137, straight after TLS `Handshake`. Line 726 is `PrepareReplace`, not the call of `BecomeController`. That call starts replacement before hello/auth/pair, and it runs before `AcceptLink`. `AcceptLink` is only the busy/disabled admission check, not authentication. A later admission failure therefore does not undo `StartReplace`. `AssistantMonitorLan.pas` calls StartReplace on the current controller; the phone treats bye/replaced as Paired elsewhere and pauses. Since TLS does not request client authentication, an unauthenticated candidate can disrupt a valid session. This is a confirmed ordering issue; whether it caused the reported incidents needs logs.

Keep a candidate in a bounded independent pre-authentication state. Validate its application credentials before atomically transferring controller ownership. A failed or timed-out candidate must leave the live controller untouched. Distinguish authorised takeover from same-client transient reconnection, retaining intentional single-controller semantics. Ensure late retirement/close callbacks cannot clear the newly adopted session. Audit concurrent candidate handshakes and existing retained-link ownership while changing admission.

Acceptance: connect an idle TLS client, send invalid auth, and race multiple candidates while a phone monitors a plan. The valid phone remains connected until an authorised takeover; exactly one controller survives and late old-link close does not reset it.

### 4.2 Use the actual Wi-Fi network and separate opening deadlines
Status: complete

Priority: medium. Evidence: `WifiLanWatch.kt` observes Wi-Fi including networks without Internet, but only sends Boolean up/down callbacks. `SslSocketConnector` uses an ordinary Socket and does not bind it to the observed Android Network. Consequently the availability policy and actual route may differ when mobile data/VPN/default routing is active. It also applies the 1-second steady-state read timeout before `startHandshake`, making TLS opening unusually sensitive to delay. These are source-supported risks requiring Android/device verification.

Pass a usable network identity to the connector and use the Android Network socket/binding API for the selected LAN route where appropriate. Handle replacement/loss by identity, rather than trusting a stale Boolean. Keep endpoint-only and pinned TLS rules unchanged. Give TCP connect, TLS handshake and authenticated session setup separate bounded deadlines; restore the steady-state read policy after opening. Clear watcher state on stop/restart and test stale callback delivery.

Acceptance: recover on a Wi-Fi LAN without Internet while mobile data is enabled, across AP roam and Wi-Fi toggle. Test a handshake delayed beyond one second but within its allowed budget, and a permanently stalled handshake. Validate VPN interaction explicitly rather than assuming a route policy.

### 4.3 Verify screen-off lifecycle and expose failed hold activation
Status: complete

Priority: medium, device investigation. Evidence: `MonitorHoldService.kt` acquires a Wi-Fi lock and starts a foreground service, but the session remains owned by the ViewModel. `MonitorViewModel` decides the hold from current UI state and lifecycle callbacks; hold-service startup errors are swallowed. This does not establish a particular Doze defect, but can make the UI assume a hold that Android did not grant.

Record whether the hold service actually became active, and test screen-off/onStop ordering, process recreation, Android background restrictions and Doze on the target phone. Tie hold lifetime to explicit monitoring demand from item 2.1. Add CPU wake management or move ownership into the service only if measured lifecycle behaviour requires it; avoid an unconditional permanent wake lock. Release all locks/service state when demand ends or the user disconnects.

Acceptance: monitor a long plan with screen off, temporary network loss and subsequent restoration; reconnect automatically where Android permits execution. On wake, always recover without process restart. Report platform suspension separately from authentication or host failure.

## 5. Diagnostics and verification

### 5.1 Add correlated connection and progress diagnostics
Status: complete

Log loop generation, socket generation, transition reason, attempt count, next retry deadline, monitoring demand, network identity, last received frame age, last committed progress age, queue bytes and worker exit reason. Desktop logs should distinguish TLS candidate, authenticated controller, takeover and old-controller retirement. Preserve the original failure reason across the retry banner. Terminal pin/authentication/revocation failures must remain distinct and must not be bypassed by automatic recovery. Make queue acceptance distinct from actual socket write and durable host command acknowledgement; `sendCatalogue` currently labels queue admission as Written.

Acceptance: a single captured incident identifies whether the app is intentionally idle, awaiting user action, retrying, blocked in opening/I/O, or receiving heartbeats without sync progress.
