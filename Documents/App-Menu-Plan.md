# App Menu Plan

Generated by Lazarus Project Assistant.

Add a menu button to the left of the "Assistant Monitor" caption in the phone app, and open a panel from the left edge in the same way Gmail opens its navigation drawer. The panel switches seven things the desktop already switches: the work target, the operating mode, a prior conversation, the active plan, the model, the reasoning level, and the tool permissions.

This is the Kotlin monitor in `Source/KotlinMonitorApp`, plus the host commands it needs in `Source/LazAssistantMonitor` and `Source/LazAssistantTools`. Do not add a drawer to the Lazarus form. The desktop combos and the footer menus stay as they are.

`Documents/Assistant Monitor Design.md` still says the phone must not change the target, the model, an archived conversation, the effort, or the approval mode. This request overrides those lines only. Skills, OAuth, API keys, folder browse, package selection, export, and delete stay on the desktop. The phone does not get a second conversation store, a second model list, or a filesystem picker.

The on-screen caption stays "Assistant Monitor". Do not rename it.

## 1. Drawer

The shell is `MonitorShell` in `Source/KotlinMonitorApp/app/src/main/kotlin/computing/michell/monitor/MainActivity.kt`. The caption row is `MonitorHeader`: the title has weight 1, and the settings icon sits on the right. Settings replaces that row with its own back bar. The pager already owns horizontal swipes between Conversation and Plan.

`ic_menu.xml` is already the three-line icon. Material 3 is already a dependency. Do not add an icon library or a navigation-compose dependency.

### 1.1 Menu button

Status: complete

Put an `IconButton` on the start side of `MonitorHeader`, immediately left of the "Assistant Monitor" text. Use `painterResource(R.drawable.ic_menu)` and content description "Menu". The settings icon stays on the end. On screen the row reads: menu, Assistant Monitor, settings.

Drop the row's start padding from 16dp to 4dp so the menu icon uses the same inset as the settings icon. The title keeps `weight(1f)`, one line, and ellipsis. The button is absent while Settings is open, because that screen replaces the header. Do not add a second menu button to the settings bar.

### 1.2 Left flyout

Status: complete

Open a Material 3 `ModalNavigationDrawer` from the start edge. Use the default sheet width so a strip of the page stays visible on the right, the same proportion Gmail uses. Scrim the page. Close on scrim tap, on system back, and after a row is chosen.

Set `gesturesEnabled` to false. An edge swipe would fight `HorizontalPager`. The menu button is the only open gesture. That is a deliberate difference from Gmail.

`BackHandler` closes the drawer before the settings back handler and before the activity finishes. Opening Settings closes the drawer first. An approval sheet still sits above the pages; do not open the drawer while `approvalOpen` is true.

The drawer is a sibling of the pager, not a page inside it. Conversation and Plan both remain underneath.

### 1.3 Seven sections

Status: not started

Add `AppMenu.kt` next to the other screens. The drawer scrolls. Its header is one line: the current target display from the existing target frame, ellipsis if needed. Then seven sections, in this order: Target, Mode, Conversation, Plan, Model, Reasoning Level, Tool Permissions.

Each section is a label and a list. The current row uses the primary colour, the same mark `PlanRowLine` already uses for the selected plan item. Every row is one line with ellipsis. An empty section shows one quiet sentence and no tappable row.

Choosing the current row closes the drawer and sends nothing. Choosing another row closes the drawer and sends the command. Do not paint the new check before the host frame arrives. A refusal uses the existing banner, not a new dialog.

While `disconnected` is true, every row is disabled and the last lists stay on screen.

## 2. Mode and plan

Mode and the active plan are already on the wire. The drawer calls those paths. It does not add a second command.

### 2.1 Mode leaves Settings

Status: not started

The drawer Mode section lists `ModeChoices` from `ConversationScreen.kt`: Chat, Inspect, Document, Plan, Build. The selected row is `modeCaption(ui.view.mode)`. A row is enabled only when `view.canChangeMode` is true and the link is up, which is the same rule as `setMode`.

A different row calls the existing `MonitorViewModel.setMode`. That already sends `set_mode`, and the host already runs `RemoteSelectMode`. Do not add a mode message.

Remove `ModeCombo` from `SettingsScreen`. Settings keeps the connection fields and the thinking and tool switches. The phone then has one mode control.

### 2.2 Active plan uses the existing choice list

Status: not started

`plan` already carries `choices` (`path`, `caption`). The phone already stores them on `MonitorUi.planChoices`. `openPlan` already sends `select_plan` and refuses a disconnected link, a disabled mode change, the current path, and a path that is not in the list.

The drawer Plan section lists those captions. The selected row is `planPath`. A tap calls `openPlan`. Do not add a plan picker to `PlanScreen`. That screen stays the item list, with Run, Stop, New, and Remove.

`applySnapshot` clears `planChoices` and the following `plan` frame fills them again. Keep that. `PushSnapshot` already calls `PushPlan`.

## 3. Target project

The desktop list is `RefreshTargetChoices`: one "Current Project" row whose path is empty, then recent folders up to `AssistantRecentTargetLimit` (10), captioned by `TargetFolderCaption`. `TargetChoiceChanged` calls `ApplyTarget`. A package target is not a row in that combo.

The phone today receives only `target` (`kind`, `display`, `root`). There is no choice list and no select command.

### 3.1 Host choices and select_target

Status: not started

Add a host-to-client `targets` frame and a client-to-host `select_target` command. Catalogue version stays 1.

`targets` payload: `current` (the selected path, empty when the target is the open project) and `choices`, each `{path, caption}`. Build `choices` with the same rows and the same limit as `RefreshTargetChoices`. Do not include a package row. Do not include the browse action.

`select_target` payload: `path`. An empty path means Current Project, the same value `ApplyTarget` already accepts. The message id stays in the existing safe-id set. Do not run that check on the path.

Split the desktop modal out of the remote path. `ApplyTarget` calls `RunAssistantModal` when `SelectFolder` fails. The remote helper must not call that dialog. Return the same `Note` as `ErrorText`. On failure, do not publish a target change.

Refuse while `FSending` or `FReviewInProgress`, before any call that could stop a stream. The phone needs a sentence, so review returns "Wait for the current review to finish." Sending returns "Wait for the current reply to finish." A path that is not in the current choice list returns "That target is no longer in the desktop list." Choosing the target that is already selected is success and sends no further publish.

On success, call the same `SelectFolder` and `BindToActiveProject` path the combo uses. `BindToActiveProject` reloads the store and does not publish `asnSnapshot`. After a successful bind, publish `asnSnapshot` so the phone drops the previous project's turns. Keep the existing `asnTarget` publish so the caption updates with the target frame.

`TAssistantMonitorBridge.DispatchCommand` handles `select_target`. `CommandBlocked` treats it like `select_plan` while a turn is sending, and also while `PlanAgentRunning`, because a target bind stops in-flight work. The form still checks review.

### 3.2 Phone target section

Status: not started

Store `targetChoices` on `MonitorUi`. Reduce a `targets` frame into that list and remember `current`. A `target` frame whose `root` changed already clears `planChoices`. Clear `targetChoices` and the conversation list on that same root change. Do not clear the model, reasoning, or permissions lists. Those belong to the connection, not the folder.

The section shows the choice captions. Empty `path` is "Current Project". When the live target is a package, or otherwise not in the list, no row is checked and the drawer header still shows `targetDisplay`. Tapping a row sends `select_target`. Rows are disabled while disconnected, sending, or plan-running.

## 4. Prior conversations

The desktop list is `HistoryCombo`, filled by `ListHistory`. Each `TConversationHistoryItem` has `ArchiveId`, `Title`, and `IsCurrent`. An empty archive id is the open conversation. `HistoryComboChange` calls `ActivateArchive`, then `ApplyLoadedConversationToUi`. The phone's turn list is not this list. `snapshot.turns` is the current conversation only.

### 4.1 Host history and select_conversation

Status: not started

Add `conversations` and `select_conversation`. Catalogue version stays 1.

`conversations` payload: `current` (archive id, empty for the open conversation) and `choices`, each `{id, title, current}`. Use `ListHistory` titles, not a new naming scheme. Cap the frame at 40 rows. Always include the current row, then the newest archives. If rows remain, set `truncated` true. The phone shows "Older conversations stay on the desktop." when that flag is set.

`select_conversation` payload: `id`. An empty id is the open conversation and is a success no-op. Do not call `ActivateArchive` for that id.

Refuse while `FSending`, with the sentence `HistoryComboChange` already uses: "Stop the current reply before switching History." Do not add a plan-running refusal. The combo does not have one. An unknown id returns "That conversation is no longer in History." A failed `ActivateArchive` returns `LastError`, or "Could not open conversation." if that string is empty.

`HistoryComboChange` shows those failures with `RunAssistantModal`. The remote helper returns `ErrorText` and does not show a dialog. On success it calls `ActivateArchive` and `ApplyLoadedConversationToUi`. That helper does not publish `asnSnapshot`. The remote success path must publish `asnSnapshot`, then the new `conversations` frame, so the phone replaces the transcript instead of keeping the previous archive on screen.

This does change the desktop conversation. That is the point. It is not `RemoteTurn`, which must still leave the desktop selection alone.

### 4.2 Phone conversation section

Status: not started

Store the history rows on `MonitorUi`. The selected row is the choice whose `current` flag is true, or whose id equals `current`. A tap sends `select_conversation`. Rows are disabled while disconnected or sending.

Do not replace the turn list on the Conversation page. Do not move New into the drawer. An unsent draft stays, which is what the desktop composer does when History changes.

A snapshot still replaces turns. Clear the history rows when the target root changes, and fill them again from the following `conversations` frame.

## 5. Model

The desktop list is `FillModelFooterMenu`, opened from the status-footer model label. Grok uses `CollectXaiKnownModelIds` plus the known fallback ids. Codex uses `CollectCodexModelIds` on the cached model JSON. Other backends add only `FActiveModel`. Choosing a row calls `ApplySamplingChange`, which writes the active connection and calls `NotifyOpenProjectAssistantFormsConnectionChanged`. That reloads through `UpdateStatusFooter`, which already publishes `asnStatus` with `model`.

The phone view already shows `model` and `backend`. It cannot change them.

### 5.1 Host list and set_model

Status: not started

Add `models` and `set_model`. Catalogue version stays 1.

`models` payload: `current` (the model id), `backend`, `choices` as `{id, caption}`, and `note`. Build `choices` with the same ids `FillModelFooterMenu` already collects. Do not call `ListAvailableModels`, and do not call a Codex or compatible list endpoint while building this frame. A drawer open must not block the IDE on a network refresh. Grok captions use `XaiModelDisplayText`. Other captions are the id.

When the backend has no list beyond the current id, `choices` contains that one id and `note` is "The rest of this list is in desktop Settings." Otherwise `note` is empty. No selected connection uses an empty `choices` and the note "No connection is selected."

`set_model` payload: `model`. The id must be in the list just built. Otherwise return "That model is not in the list." The same id as `FActiveModel` is a success no-op.

`ApplySamplingChange` shows a modal when the IDE path is missing, when no connection is selected, when work is in progress, and when the save fails. The remote helper returns those sentences as `ErrorText` and does not show a dialog. Refuse while `FSending`, `FPlanAgentRunning`, or `FReviewInProgress`, with "Wait until the current work finishes before changing the model, effort, or permissions."

On success, save through the same connection write `ApplySamplingChange` uses, including the effort adjustment that function already makes when the new model rejects the stored effort. Then call `NotifyOpenProjectAssistantFormsConnectionChanged`. After that reload, push `models` and `reasoning` as well as the status frame, so both lists match the saved model.

Do not add a phone control for skills.

### 5.2 Phone model section

Status: not started

Store the model rows, backend, and note on `MonitorUi`. The selected row is the id equal to `view.model`. A tap sends `set_model`. Rows are disabled while disconnected, sending, or plan-running.

If `note` is not empty, show it under the list in the quiet body style. Do not add a Refresh button.

A status frame that changes `view.model` moves the check. Do not clear this list on a target change.

## 6. Reasoning Level

The desktop list is `FillEffortFooterMenu`, opened from the status-footer effort label. The stored value is `FActiveEffort` on the form and `ReasoningEffort` on the active connection. Grok also copies it to `AssistantChatConfig.ThinkingLevel`. A choice calls `ApplySamplingChange` with the effort flag, which is the same save as a model change.

The phone status field `effort` is a caption (`Low`, `High`, `XHigh`, `Default`, or an em dash). It is not the stored id. Codex stores an empty effort for "Model default", while `EffortBarCaption('')` returns "Default". Do not select a row by comparing that caption.

### 6.1 Host list and set_reasoning

Status: not started

Add a host-to-client `reasoning` frame and a client-to-host `set_reasoning` command. Catalogue version stays 1. Do not reuse the status field `effort` as this frame.

`reasoning` payload: `current` (the stored id, empty when Codex is on model default) and `choices`, each `{id, caption}`. Build the rows with the same rules as `FillEffortFooterMenu`.

Grok includes `low`, `medium`, `high`, and `xhigh` only when `XaiModelAllowsEffort` allows that level for `FActiveModel`. Captions are Low, Medium, High, and XHigh. If none are allowed, include all four, which is what the footer does. Codex starts with id `""` and caption "Model default", then adds `CollectCodexEffortIds` for the active model, captioned by `EffortBarCaption`. If that collect fails and an effort is already stored, the list is that one stored level. Any other backend has an empty `choices` and `note` "This connection does not set an effort level." No selected connection uses an empty `choices` and the note "No connection is selected."

`set_reasoning` payload: `level`. An empty level is legal and means model default. Missing `level` is a decode failure, not model default. The id must be in the list just built, including the empty id when that row exists. Otherwise return "That reasoning level is not in the list." The same stored effort is a success no-op. Compare with the stored id, not with `EffortBarCaption`.

The remote helper uses the effort branch of `ApplySamplingChange` and does not show `RunAssistantModal`. Refuse while `FSending`, `FPlanAgentRunning`, or `FReviewInProgress`, with the same sentence as a model change. On success, save the connection, copy the Grok thinking level when that backend is active, and call `NotifyOpenProjectAssistantFormsConnectionChanged`. Then push `reasoning` after the status frame.

`CommandBlocked` treats `set_reasoning` like `set_model`.

### 6.2 Phone reasoning section

Status: not started

The section label is "Reasoning Level". Store the rows and the note on `MonitorUi`. The selected row is the choice whose id equals `current`, and an empty id is a real row when the host sent one. A tap sends `set_reasoning`. Rows are disabled while disconnected, sending, or plan-running.

If `note` is not empty, show it under the list and do not invent rows. Do not move the check because `view.effort` changed. That string is a caption. The `reasoning` frame is the check.

Do not clear this list on a target change. A model change can shrink the allowed levels, so replace the list only from the next `reasoning` frame.

## 7. Tool Permissions

The desktop list is `FillPermissionsFooterMenu`, opened from the status-footer permissions label. The stored value is `FActiveApproval`, one of `ask`, `auto`, and `always`. An empty stored value is shown as `ask`. A choice calls `ApplySamplingChange` with the approval flag.

This is not the tool-approval sheet. `approval_requested`, `approval_decision`, and `approval_closed` stay as they are. The drawer must not allow or deny a pending tool.

The phone status field `approval_caption` is the short word Ask, Auto, or Always. The footer menu uses longer sentences, and the Codex sentences differ from the others. The drawer uses the menu sentences. Do not select a row by comparing the short caption.

### 7.1 Host list and set_permissions

Status: not started

Add a host-to-client `permissions` frame and a client-to-host `set_permissions` command. Catalogue version stays 1. Do not name the command `set_mode`. That name is the operating mode.

`permissions` payload: `current` (`ask`, `auto`, or `always`), `backend`, and `choices`, each `{id, caption}`. An empty stored approval is sent as `ask`. Build the three rows with the same captions as `FillPermissionsFooterMenu`.

For Codex the captions are "Ask before file changes and builds", "Auto: allow project tools", and "Always: allow registered tools". For every other backend they are "Ask — confirm each write/compile", "Auto — allow project tools", and "Always — never prompt (like Build always-approve)". No selected connection uses an empty `choices` and the note "No connection is selected." Do not add a fourth value.

`set_permissions` payload: `approval`. The only legal values are `ask`, `auto`, and `always`. Anything else returns "That permission is not in the list." Choosing the value already stored is a success no-op. An empty stored value counts as `ask`, so choosing `ask` in that case does not write.

The remote helper uses the approval branch of `ApplySamplingChange` and does not show `RunAssistantModal`. Refuse while `FSending`, `FPlanAgentRunning`, or `FReviewInProgress`, with the same sentence as a model change. On success, save the connection and call `NotifyOpenProjectAssistantFormsConnectionChanged`. Then push `permissions` after the status frame.

`CommandBlocked` treats `set_permissions` like `set_model`. It must not accept this command on the approval-decision path.

### 7.2 Phone permissions section

Status: not started

The section label is "Tool Permissions". Store the rows and the note on `MonitorUi`. The selected row is the choice whose id equals `current`. A tap sends `set_permissions`. Rows are disabled while disconnected, sending, or plan-running.

If `note` is not empty, show it under the list and do not invent rows. Do not move the check because `view.approvalCaption` changed. The `permissions` frame is the check.

Do not clear this list on a target change. Do not wire a row to `allowApproval` or `denyApproval`.

## 8. Catalogue, follow-up frames, and tests

New types are additive. Both catalogues change in the same pass. Do not bump `v`. A version mismatch rejects the session.

### 8.1 Frames, busy rules, and snapshot follow-up

Status: not started

Add the ten types to `TMonitorMessageKind` and `MessageKind`, with snake-case names `targets`, `select_target`, `conversations`, `select_conversation`, `models`, `set_model`, `reasoning`, `set_reasoning`, `permissions`, and `set_permissions`. Decode them into typed inbound values the way `target` and `plan` already decode. A host frame the phone cannot apply must not close the socket.

`HandleLocked` accepts the five commands only after auth, in the same case list as `select_plan`. `CommandBlocked` uses the refusals in sections 3.1, 4.1, 5.1, 6.1, and 7.1. Unknown types still become `error` / `unknown_type` and do not change session state.

`PushSnapshot` already ends with `PushPlan`. After that, push `targets`, `conversations`, `models`, `reasoning`, and `permissions`. `applySnapshot` clears those phone lists, and the following frames fill them, which is how `planChoices` already works.

Also accept `refresh` text `menu_choices`, beside the existing `plan_choices` text, and push those five lists plus the plan. The phone sends that only when it opens the drawer, the link is live, and a list is still empty. Do not send it on every open.

`asnTarget` pushes `targets`. A successful conversation switch pushes `conversations` after its snapshot. A successful model save pushes `models` and `reasoning` after status. A successful reasoning or permissions save pushes that one frame after status. Do not invent a second observer kind.

### 8.2 Tests

Extend `Tests/AssistantMonitorSessionTest.lpr` so the five commands are accepted while live, and so `select_target`, `set_model`, `set_reasoning`, and `set_permissions` are `host_busy` while a turn is sending. `select_conversation` is `host_busy` while sending and is not refused only because a plan run is active. `set_permissions` must not be handled as `approval_decision`.

Add a JVM test beside the existing monitor reducer tests. A snapshot clears the five lists. The following frames restore them. A target root change clears choices and conversations and leaves models, reasoning, and permissions. Choosing the current id encodes nothing. A status caption for effort or approval does not move the drawer check.

Do not add Robolectric or a device test. Run the codec and session programmes through `Tests/RunAssistantTests.pas`, and the protocol and app unit tests with the Gradle wrapper in `Source/KotlinMonitorApp`.
