## 1. Overview

Goal: let the test runner and the assistant's `lazarus_start_tests` tool build and run named test programs with heaptrc (`-gh`), under valgrind, or with extra compiler defines such as `DEBUG`. - **3.3** (cross-thread link and session fields) needs a `-dDEBUG` run of Chaos, Lockup, Link and Socket, so the `StartReplace` thread assertion is compiled in.

Where things stand now:

- `Tests/RunAssistantTests.pas` (677 lines) builds each test with a fixed `fpc -v0 -gl -Cr -Co -FU<out> -FE<out>` command in `RunSuite`, the same flags in `Restricted`, and the monitor package through `lazbuild --opt=` in `RunMonitorPackage`. It runs each binary directly through `RunCommand`. Its options are `--lazarus-root`, `--output-dir`, `--library-dir`, `--gui`, `--package-check`, `--compile-only`, `--independent` and `--only`.
- The tool path goes broker → adapter → settings. The broker (`AssistantToolBroker.pas` ≈ 1311–1335) reads `only` and calls `TestCommand`, then `Approve` with the full command text, then `StartTests`. The adapter is `TAssistantIDEWorkspace.TestCommand`, `StartTests` and `TestStatus` (`AssistantIDEWorkspace.pas` ≈ 516–685). The settings unit's `ApplyTestOnly` (`AssistantTestSettings.pas` ≈ 85–189) appends `--only` pairs and a temporary `--output-dir`, and only does so for the repository runner. `TestStatus` reapplies the same selection to detect a changed command.
- `ApplyTestOnly` names the output directory after the build job and the test names. A later run with different flags would reuse ppus compiled with other defines, and FPC does not recompile a unit when only the defines change.

Constraints:

- House style from `Documents/free-pascal-engineer.md`. Units stay under 1000 lines.
- The new options apply only to the repository runner, like `only`. A user's own test command is never rewritten.
- No shell. Every argument is validated and passed as one argv entry.
- If heaptrc or valgrind reports a problem, or valgrind is not installed, the test fails with a clear message. It is never skipped quietly.
- Output stays in temporary directories, never under `Source/`.
- The approval dialog shows the full command, including the new flags.

Success criteria:

- `instantfpc Tests/RunAssistantTests.pas … --only AssistantMonitorLockupTest --heaptrc` passes on clean code and fails on a planted leak or use-after-free probe. The same holds for `--valgrind`.
- `--define DEBUG` compiles the tests and the monitor package with `DEBUG`, and the run says so in its output.
- `lazarus_start_tests` accepts `memory_check` and `defines`, shows them in the approval command, and reports stale correctly.
- Items 3.1 and 3.3 of `Plan-20261105-130659.md` can be closed using these runs alone.

Out of scope: the internal `run_tests` tool in `AssistantTools.pas` (≈ 758), which takes no parameters; the GUI tests under valgrind; and Windows, where valgrind does not exist.

Using what 2.1 established:

- `--heaptrc` adds `-gh` (and any companion flag from 2.1) to the test program builds only, not to package builds. When the binary runs, `HEAPTRC` is set in the child's environment as 2.1 decided. `RunCommand` gains an optional environment list: copy the current environment into `Proc.Environment` and add the entries. After the run, `CheckHeapReport(LogText)` fails the test if the "no unfreed blocks" line is missing or non-zero, or if a corruption or double-release line appears. The failure message names the matching line.
- `--valgrind` adds the build flags from 2.1. It runs `valgrind --error-exitcode=99 --leak-check=full --errors-for-leak-kinds=definite --track-origins=yes --log-file=<out>/<Test>.valgrind.log <binary>`. If `ResolveExecutable('valgrind')` is empty, it fails at start-up with "valgrind is not installed". The valgrind log is appended to the test's log, so a single file holds everything.
- `--heaptrc` and `--valgrind` cannot be combined. Each needs at least one `--only`, and neither may be used with `--independent`, `--package-check` or `--gui`; these combinations exit 2 with a message.
- Under valgrind, the run timeout is multiplied by the slowdown factor from 2.1, capped at 3600 s. Say this in the usage text.
- The `Build flags:` line from 2.2 includes the mode.
