# LCL Use Review Plan

Generated by Lazarus Project Assistant.

Desktop code in this project stays on the LCL. A feature is not made portable by writing a Win32 body, a GTK body, and a Cocoa body next to the feature. If the LCL already has the facility, use it and name the facility that was checked. If it does not, the platform calls go in one unit whose interface is platform-neutral. Callers never use `Windows`, `ShellApi`, `WinInet`, `BaseUnix`, `gtk_*`, or `QWidget_*`.

This review covered `Source/` (LazAssistantTools, LazRepositoryTools, LazStyledText, LazWorkflowCommon, Tools) and the small `{$IFDEF WINDOWS}` branches in `Tests/`. `{$IFDEF FPC}` mode blocks, Pascal-source scans of the word `IFDEF`, and `DebugDisableAutoSizing` are not platform APIs and are out of scope.

Already on the LCL, and not to be "improved" with widgetset units:

- `LCLIntf.OpenURL` in `GrokOAuth.pas`, `AssistantSettingsForm.pas`, and `AssistantCodexSettings.pas`.
- `TClipboard` plus `RegisterClipboardFormat` in `ProjectAssistantForm.pas`. The Qt note there is an LCL ownership workaround, not a Qt call.
- `LCLIntf.ShowCaret` / `DestroyCaret` in `StyledControls.pas`.
- `SpellMemo.pas`, which paints without a widgetset.

Do not weaken the security properties while removing platform units. `TFileStream`, `FileExistsUTF8`, and `DeleteFileUTF8` follow symlinks and can replace an existing entry. They are not substitutes for `O_NOFOLLOW`, `O_EXCL`, or an atomic publish. Moving a path to the waste bin is not `DeleteFile`. Making the Codex runtime run on Darwin is out of scope; removing `BaseUnix` from that unit is in scope.

LCL 5.99.0.0 is the widgetset this IDE builds against. Where a note says "re-read the LCL", use the sources for that installation, not an older wiki page.

## 1. Use the LCL and LazUtils facilities that already exist

These branches are host tests around facilities Lazarus already provides. No new unit.

### 1.1 Command key in styled text
Status: complete

`StyledControls.pas` `TCustomStyledText.KeyDown` sets `CommandKey` from `ssCtrl`, then `{$IFDEF DARWIN}` ors in `ssMeta`.

LCL facility: `ssModifier` in `Controls`. On Darwin it is the Command key; elsewhere it is Ctrl. Confirm that mapping in this LCL's `controls.pp` before editing. The current Darwin behaviour also accepts Ctrl. Preserve that without an ifdef:

`CommandKey := (ssModifier in Shift) or (ssCtrl in Shift);`

On non-Darwin `ssModifier` is `ssCtrl`, so the expression is unchanged. Do not add a Cocoa or Carbon unit.

### 1.2 Path, drive, and executable-name branches
Status: not started

Replace host branches with LazUtils / SysUtils. No behaviour change.

- `AssistantPlan.pas` `ProjectRelativePath` uses `SameText` only on Windows. The same unit already uses `CompareFilenames`. Use that for both arms and delete the ifdef. Keep the slash normalisation.
- `AssistantProjectPaths.pas` `IsStopDir` treats a two-character `X:` path as a stop on Windows only. `ExtractFileDrive` is empty on Unix and is the drive on Windows. Stop when the path is empty, `/`, the home directory, or equal to its drive. No `WINDOWS` test.
- `AssistantTools.pas` `FindLazbuildExecutable` appends `.exe` under `WINDOWS`. Use `ExeExt`.
- `Tests/RunAssistantTests.pas` `OutputBinary` does the same. Use `ExeExt`.
- `GitService.pas` rewrites `\` to `/` only on Windows. Always rewrite `PathDelim` (and a literal `\`) to `/`. Git paths in this UI are slash-separated on every host.
- `AssistantHarness.pas` `BuildUserInfo` maps `WINDOWS` / `DARWIN` / else to a display name. Use `{$I %FPCTARGETOS%}`. That is a compiler target name, not a widgetset call.

`FileNameCaseSensitive` is already used in `GitService.MergeGitFileEntries`. Do not add another case policy.

### 1.3 Compact diff font
Status: not started

`GitDiffView.pas` `ApplyCompactEditorFont` sets `Consolas` on Windows and `Courier New` elsewhere.

LCL facility: `TFont.Pitch := fpFixed`. The widgetset chooses a fixed font. `ApplySynEditIDEFont` in the same unit already copies the IDE editor font without a platform name.

Stop assigning `Font.Name` in the compact path. Keep `Pitch := fpFixed`, size 9, and `fqCleartypeNatural` (that quality value is an LCL enum; the widgetset maps it). If the IDE font helper can be applied without the side effects its comment describes, prefer that and do not invent a font-name table.

### 1.4 Detached Claude sign-in
Status: not started

`AssistantClaudeClient.pas` `SpawnDetached` is two implementations: `FpFork` / `FpExecv` / `FpWaitPid` on Unix, and `CreateProcess` with `CREATE_NEW_CONSOLE` on Windows. The third arm fails. The only caller is `StartClaudeSignIn`.

Facility: `TProcessUTF8` in `UTF8Process` (LazUtils), which is the Lazarus wrapper around `TProcess`. FPC 3.3.1 has `poNewConsole` and `poDetached`. `poNewConsole` is the `CREATE_NEW_CONSOLE` flag. Do not call `CreateProcess` or `FpFork` from the client unit.

Required behaviour, which the current Unix code gets from a double fork: the sign-in starts in its own console, the IDE does not wait, the IDE does not keep a zombie, and the sign-in is not killed when the IDE exits. Try `TProcessUTF8` with `InheritHandles := False` and `[poNewConsole, poDetached]`, no `poWaitOnExit`.

If that does not orphan the child on Unix, put the double-fork in `ProcessSession` (section 3) and call that. Do not leave `BaseUnix` or `Windows` in `AssistantClaudeClient.pas`.

### 1.5 Directory listing
Status: not started

`DirectoryListing.pas` has its own Unix scanner (`FpOpenDir`, `FpLStat`, `FpStat`) because it must report `faSymLink` (`$400`), which the old DOS bit `$40` is not. The non-Unix arm uses `FindFirstUTF8` / `FindNextUTF8`.

LCL / LazUtils facility: `FindFirstUTF8`. Before keeping the Unix scanner, compare it with `FindFirstUTF8` on a regular file, a directory, a symlink to a directory, and a dangling symlink. If the attributes and sizes match, delete the `BaseUnix` arm and use `FindFirstUTF8` on every host.

If they do not match, keep this unit as the only directory scanner. Say that in the unit header, including the date and the LCL version checked. Do not add another `FpOpenDir` call site.

## 2. File-drop extension

`AssistantFileDrop.pas` is the clearest case of a feature implemented as one body per widgetset.

The public procedures are already neutral: `ArmControlFileDrop` and `ReleaseInputFileDrop`. Call sites are only `ProjectAssistantForm.pas` (input panel, attachment strip, input memo). Cocoa is a no-op because `TCocoaWSCustomForm.SetAllowDropFiles` registers the content view and AppKit walks up.

The implementation calls `gtk_drag_dest_set`, `gtk_selection_data_get_uris`, `DragAcceptFiles`, and `QWidget_setAcceptDrops` / `QObject_hook_hook_events`. The unit header records why: `TWin32WSCustomForm.SetAllowDropFiles` arms the form HWND only, Qt arms the main window only, and GTK3 has no `SetAllowDropFiles`. Child native windows therefore never receive the drop, so form-level `AllowDropFiles` is not enough for those three widgetsets.

### 2.1 Confirm the LCL gap, then delete or split
Status: not started

Re-read `SetAllowDropFiles` in the LCL 5.99 sources this IDE uses: Win32 `win32wsforms`, GTK3 `gtk3wsforms`, Qt5 and Qt6 `*wsforms`, and Cocoa `cocoawsforms`. Also check whether `TWinControl` grew an `AllowDropFiles` of its own.

If a widgetset now delivers a file drop on a child `TWinControl` to the form `OnDropFiles`, delete that widgetset's arm. If all of them do, delete `AssistantFileDrop` and the three `ArmControlFileDrop` calls. `AllowDropFiles` and `OnDropFiles` are then the whole feature.

If a widgetset is still form-only, keep the neutral procedures and move that widgetset body out of the public unit:

- `AssistantFileDrop.pas` — interface and the Cocoa no-op. Implementation uses must not name `gtk3widgets`, `Windows`, `qt5`, `qt6`, or `qtwidgets`.
- `AssistantFileDropGtk3.pas` — current GTK3 arm.
- `AssistantFileDropWin32.pas` — current `DragAcceptFiles` arm.
- `AssistantFileDropQt.pas` — current Qt5/Qt6 arm. The Qt5 versus Qt6 unit names may stay inside this one unit.

Add the new units to `Packages/LazAssistantTools.lpk`. GTK2 is not a target; do not add a GTK2 arm. Do not call widgetset functions from the form.

## 3. Process-session extension

`TProcess.Terminate` signals one process. It does not kill a session, and it does not decode a Unix wait status. Those calls are copied today.

- `AssistantCodexTransport.pas` uses `BaseUnix`, `Unix`, and `Syscall` for `fpSetsid`, `fpKill(-pid)`, `fpFcntl` (`O_NONBLOCK`), and `SIGPIPE`. The public methods are already neutral. `Start` returns "qualified for Linux only" on other hosts.
- `AssistantBuildJob.pas` repeats `fpSetsid` and `fpKill(-pid)` under `LINUX`, and uses `fpStat` for the executable fingerprint (that stat moves in section 4).
- `GitService.pas` uses `WIFEXITED` / `WEXITSTATUS` on `Proc.ExitStatus`.

### 3.1 Add ProcessSession
Status: not started

Add `Source/LazWorkflowCommon/ProcessSession.pas` and register it in `Packages/LazWorkflowCommon.lpk`.

Platform-neutral interface, no `BaseUnix` or `Windows` in the interface uses:

- `StartInOwnSession(Process: TProcess): Boolean` — the `OnFork` / `setsid` behaviour, or the Windows equivalent inside the implementation.
- `TerminateSession(Process: TProcess)` — term, short wait, kill. Kills the group on Unix. Does not call `TProcess.Terminate` and then also `fpKill` from the caller.
- `ProcessWasSignalled(Process: TProcess): Boolean` and a decoded exit code, if `TProcess.ExitCode` on FPC 3.3.1 is not already that decode. Check `process.inc` before wrapping it. If `ExitCode` is enough, do not wrap it.
- `SetPipeNonBlocking(Handle): Boolean` for the Codex stdin pipe.
- `SpawnDetached(Executable, Args, out ErrorText): Boolean` only if section 1.4 cannot do this with `TProcessUTF8`.

Unix implementation (Linux and Darwin share it; do not write a second Darwin copy) stays in the implementation uses. Windows implementation stays there too. A host the implementation does not support returns false and a short error. No form, package, or client unit gains a `BaseUnix` uses clause.

### 3.2 Point the three callers at ProcessSession
Status: not started

- `AssistantCodexTransport.pas`: delete `BaseUnix`, `Unix`, and `Syscall`. `ChildFork`, `Stop`, and the non-blocking setup call `ProcessSession`. Keep the product sentence that the runtime is qualified on Linux only, as one early exit in `Start`. Do not paste the syscall block back under `DARWIN`.
- `AssistantBuildJob.pas`: delete the `LINUX` fork and `fpKill` block. Session setup goes through `ProcessSession`. Leave the stat check to section 4.
- `GitService.pas`: delete `WIFEXITED` / `WEXITSTATUS` and the `BaseUnix` uses entry that exists only for them. Use `TProcess.ExitCode`, or `ProcessSession` if section 3.1 found that `ExitCode` hides signal death. The Windows uses entry for `CreateFile` / `MoveFileEx` moves in section 4, not here.

## 4. Safe file access

There is no LCL call for "open this path, do not follow a symlink, fail if the entry exists." The project reimplements that in several units, and two of them also call the Windows API for an exclusive create plus replace.

Call sites:

- `AssistantFileCreation.pas` — Linux-only `openat`, `mkdirat`, `linkat`, `unlinkat`, plus a libc `external` block. `CreateNewProjectText` is already the neutral entry. Other hosts get "supported on Linux only."
- `AssistantImages.pas` — `fpOpen` with `O_NOFOLLOW` and `O_EXCL` (`ReadOpenNoFollow`, `WriteExclusive`).
- `AssistantProjectPaths.pas`, `AssistantCodexProfile.pas`, `AssistantCodexQualification.pas`, `WorkflowSettings.pas` — `fpChmod` to `&600` or `&700`. On Windows the chmod is skipped.
- `AssistantBuildJob.pas`, `AssistantSymbolTools.pas`, `AssistantIDEWorkspace.pas` — `fpStat` / `fpLStat` to require a regular file or to reject an existing entry. `CanCreateFiles` is `{$IFDEF LINUX}`.
- `GitService.pas` `RestoreRemotes` — `fpOpen` `O_EXCL` or `Windows.CreateFile` `CREATE_NEW`, then `fpChmod` or `MoveFileEx`.

`AssistantIDEWorkspace.CreateFile` already calls `CreateNewProjectText`. The `LINUX` test in `CanCreateFiles` is a second copy of that limit.

### 4.1 Add SafeFileAccess
Status: not started

Add `Source/LazWorkflowCommon/SafeFileAccess.pas` and register it in `Packages/LazWorkflowCommon.lpk`.

Interface uses: `SysUtils` and `Classes` only. Suggested surface, names may follow the house style if a collision appears:

- `CanCreateNewText: Boolean` — true only where the atomic no-follow publish is implemented.
- `CreateNewText(Root, RelativePath, Text, out ErrorText): Boolean` — move the contract from `AssistantFileCreation`: reject absolute paths, `..`, and symlinks; publish with `linkat` so an existing entry, including a dangling symlink, is not replaced. The Linux body moves here. Implement the same POSIX calls for other Unix hosts in this unit, not in the workspace. If a host cannot meet the contract, return false and the existing error text. Do not fall back to `TFileStream.Create`.
- `ReadAllNoFollow(Path, ExpectedSize, out Data, out ErrorText)` and `CreateExclusiveNoFollow(Path, Data, out ErrorText)` — the image-store contract, including the symlink error strings.
- `ProtectOwnerOnlyFile(Path)` and `ProtectOwnerOnlyDirectory(Path)` — Unix `fpChmod` `&600` / `&700`. On Windows keep today's behaviour (no mode bits) and return true. Do not invent an ACL layer in this pass.
- `IsRegularFile(Path, MaxBytes): Boolean` — `fpStat` and `FPS_ISREG`, or the Windows equivalent, inside this unit.
- `TryExclusiveCreate(Path, out Handle, out ErrorText)` and `ReplaceWithExclusiveFile(...)` — the git config lock. `MoveFileEx` and `CreateFile` stay in this implementation.
- `NullDevicePath: String` — `NUL` on Windows, `/dev/null` elsewhere. `GitService` uses this in the untracked diff command. It is a git argument, not an LCL file open.

`AssistantFileCreation.pas` becomes a one-line forwarder to `CreateNewText`, or is removed if every caller can use `SafeFileAccess`. Prefer the forwarder if package uses lists already name `AssistantFileCreation`.

## 5. Waste bin

`GitPathUtils.MovePathToWasteBin` is the recycle-bin feature written three ways: `SHFileOperationW` via `ShellApi` on Windows, `gio trash` / `trash-put` / `trash` via `TProcess` elsewhere, and `osascript` Finder on Darwin. The only caller is `ManageRepositoryForm.pas`.

LCL facility checked: `LCLIntf.OpenDocument` and `OpenURL` open a file or URL. They do not move it to the waste bin. The Lazarus wiki still documents `SHFileOperation` for trash and limits that article to Windows. There is no LCL trash API in the facilities used by this project.

### 5.1 Move the waste bin behind its own interface
Status: not started

Add `Source/LazWorkflowCommon/WasteBin.pas` with `MovePathToWasteBin(FullPath, out ErrorText): Boolean`. Register it in `Packages/LazWorkflowCommon.lpk`.

`GitPathUtils.pas` keeps `GitProjectStartPath`, `GitIdeStartPath`, and `ConfirmGitPathAction`. It calls `WasteBin` and drops `ShellApi` and the `WINDOWS` uses entry. `AppendFinderWasteBinArguments` moves with the implementation; it is not a public Git helper.

The implementation may still call `SHFileOperationW`, `gio`, and `osascript`, because that is the gap. Those calls stay in `WasteBin.pas` only. Do not shell out from the form. Do not replace a failed trash with a permanent delete.

A later Pascal implementation of the FreeDesktop trash spec may replace `gio` inside this unit. That is not required to close this item.

## 6. HTTPS and spell bindings

Neither has an LCL equivalent. Both already have a neutral front. The leak is platform API and `{$IFDEF WINDOWS}` in the shared units and in the settings UI.

### 6.1 One HTTPS transport in the public unit
Status: not started

`AssistantHttps.pas` is the public transport (`HttpsGet`, `HttpsGetBytes`, `HttpsPostForm`, `HttpsPostJson`, `HttpsPostJsonStream`). On Windows it prefers WinINet (`Windows`, `WinInet`, `InternetCloseHandle`, `LoadLibrary` / `FreeLibrary` for OpenSSL DLLs). Elsewhere it uses `fphttpclient` and `opensslsockets`.

LCL has no HTTP client. `TFPHTTPClient` is the cross-platform stack already in this unit. Do not add `NSURLSession`, libsoup, or a third client.

Move the WinINet procedures and the OpenSSL DLL preload into `AssistantHttpsWinInet.pas`. `AssistantHttps.pas` must not use `Windows` or `WinInet`. The public signatures stay. `THttpsStreamControl.Abort` remains the cancel operation; `AssignHandles` / `StealNativeHandles` must not be how other units see an `HINTERNET`.

Keep WinINet as the Windows fallback until a Windows run shows OpenSSL streaming is enough. Do not delete it in this item. New HTTPS behaviour goes through the fpHTTP path first. Update the unit size note if the split drops `AssistantHttps.pas` under 1000 lines, or refresh the reviewed date if it does not.

Register the new unit in `Packages/LazAssistantTools.lpk`. It must compile on Linux; the WinINet body is inside `{$IFDEF WINDOWS}`.

### 6.2 Spell settings stop branching on Windows
Status: not started

The engine split is already the right shape: `SpellEngine`, `SpellEngineHunspell`, `SpellEngineAspell`, `SpellEngineWindows`, `SpellHunspellWindows`. There is no LCL spell checker. Do not fold the COM `ISpellChecker` binding into a form.

- `SpellCheckerConfig.pas` tries `sekWindows` first only under `{$IFDEF WINDOWS}`.
- `SpellEngineHunspell.pas` `LoadSpellLibrary` calls `LoadLibraryExW`, `GetLastError`, and uses `Windows`. `DynLibs.LoadLibrary` is already the cross-platform loader used for the other arm.

Add `AvailableEngineKinds` (or the equivalent) on `SpellEngine`. `SpellEngineWindows` contributes `sekWindows` only when `WindowsSpellAvailable` is true, which it already returns false for on non-Windows. The frame fills the combo from that list. The config auto-order uses the same list. Delete the `WINDOWS` tests in the frame and the config unit.

Move `LoadLibraryExW` into `SpellHunspellWindows.pas`. `SpellEngineHunspell.pas` drops the `Windows` uses entry. Library file-name tables in the Hunspell and Aspell units may stay; they are search names, not API calls. `DynLibs` stays the loader for every name that does not need `LOAD_WITH_ALTERED_SEARCH_PATH`.
