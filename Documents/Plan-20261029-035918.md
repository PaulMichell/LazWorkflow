## 1. Overview

### Goal

Make the link between `LazAssistantMonitor` (the IDE host) and `KotlinMonitorApp` (the phone) fast, lossless and
self-healing. Conversation content must survive any disconnection and resume where it stopped, without truncation. The
phone must keep a durable local copy that can be reviewed with no connection.

### What is wrong now (from reading the code, 29 October 2026)

The slowness and the "stuck on busy" lock-up come from several faults that make each other worse.

1. **The host only does I/O four times a second.** `TMonitorListenThread` services sockets from `TInetServer.OnIdle`
   (`AssistantMonitorLan.pas:1146`). That runs once per `AcceptIdleTimeOut` (250 ms) when no new connection arrives.
   Each pass makes at most one `SSL.Read` of 16 KiB and one `SSL.Write` of one frame (`ServiceAccepted`, `:1031`). That
   gives a ceiling of about four outbound frames per second. A resume answer is a catchup, a status, a plan and five
   menu lists, so it needs at least two seconds before any patch gets through.
2. **Patches are produced faster than they are drained.** `PumpMirror` runs every 150 ms (`AssistantMonitorBridge.pas:218`),
   which is about 6.7 frames a second against a drain rate of 4. The carrier queue is a single FIFO capped at 32
   (`MonitorOutboundCap`) with no priorities. Once it is full, `Send` fails with "queue is full". Pongs, approvals and
   errors then wait behind bulk frames.
3. **Replies are dropped silently.** When the bulk lane is full, `QueueSend` drops bulk frames (snapshot, catchup,
   plan, transcript) and only increments `FFramesDropped` (`AssistantMonitorSession.pas:607`). `SendHostJson` ignores
   the result. If a catchup snapshot does not fit at any compaction level, the bridge logs a warning and sends nothing
   (`AssistantMonitorBridge.pas:796`).
4. **The phone can stop applying updates for good.** When a patch cursor skips ahead, `applyPhonePatch` sets
   `resumeOnce` and then ignores every later patch until a catchup arrives (`PhoneMirror.kt:110`). Only one resume is
   sent (`MonitorCoordinator.kt:332`). The stall detector (`stallResume`) is reset by every patch that *arrives*, even
   one that was ignored (`noteMirrorProgress`, `:276`), so it never fires while the host keeps streaming. If the single
   resume reply is lost (cause 3) or deferred, the phone keeps the last flags it applied (`busy = true`) and shows
   "busy" while discarding everything else. Only a reconnect clears this. This is the most likely mechanism for the
   reported lock-up. Item 2.2 confirms it with a test.
5. **Live delta content can be lost.** `PumpMirror` records `FSentBlocks := Turn.Blocks` as soon as a patch is queued.
   If that patch is still unsent when the next pump replaces it (`ReplaceLivePatch` reuses the reserved cursor), the
   replacement carries only the newer delta. Blocks that changed only in the replaced patch never reach the phone.
6. **Streaming costs grow with the square of the answer length.** A dirty block is resent with its whole body every
   150 ms. A 20 000-character answer is sent again many times while it grows.
7. **Commands depend on the IDE main thread being free.** Commands reach the IDE through `TThread.Queue`. The sweep
   answers `host_busy` if one is still unclaimed after 5 s, or while a modal dialog is open
   (`AssistantMonitorBridge.pas:266,1544`). The session also moves to `mssBusy` when it accepts a send, before the IDE has
   accepted it. A slow IDE therefore looks like a busy host.
8. **Two protocols run at the same time.** The legacy Snapshot/Transcript/Status frames and the newer
   epoch/cursor Patch/Catchup mirror are both sent. This doubles traffic and gives the phone two sources of truth to
   reconcile. Much of the complexity in `MonitorCoordinator`/`MonitorViewModel` (`applied` vs `screen`, `transcriptBroken`,
   the link grace period, and the issues in `Source/KotlinMonitorApp/REVIEW.md`) comes from this.
9. **Accept and the TLS handshake block the I/O thread.** The accepted socket stays blocking during the handshake, and
   `IOTimeout` is 0. A phone that drops off Wi-Fi in the middle of a handshake freezes servicing of the existing
   controller.
10. **The phone's reader waits for the UI.** `LanSession.onFrame` waits on `InboundDelivery.publish` for up to 45 s
    while the collector is slow (`LanSession.kt:755`). Pongs are written from the same loop, so a slow UI delays them.
11. **The offline cache cannot resume.** `OfflineStore` rewrites a whole JSON document on each save and does not store
    the epoch or cursor. After an app restart the phone always needs a full snapshot. A catchup snapshot is compacted:
    thinking and tool bodies are cut to 240 characters, and only 30 turns are included (`CompactCatchupSnapshot`). The
    identity `conversationId = "current"` can also put different conversations into the same cache file.

### Target design (researched)

The design follows established patterns for intermittently connected clients: an append-only log with offsets (Kafka
consumer offsets, SSE `Last-Event-ID`), QoS-1 commands with client IDs and duplicate detection (MQTT persistent
sessions), prioritised multiplexing with small chunks (HTTP/2, RFC 9113), single-threaded non-blocking OpenSSL I/O
(an `SSL` object must not be read and written from two threads at once), and Android's offline-first architecture, where
the local database is the single source of truth.

- **One protocol: a per-conversation event log.** Each conversation has a stable ID and a host *stream ID*, which is
  regenerated when the host loses its log. Every content change is a log event with a gap-free sequence number:
  turn opened, block opened, block appended (`offset` + text), block replaced, block closed, turn closed, plan changed,
  and so on. Status (busy, can-send, model and similar) is a separate *state channel*, where the latest value wins and
  no history is kept. Every snapshot carries the full state, so a lost status frame can never leave "busy" showing.
- **Resume by offset.** The phone stores `(streamId, seq)` in the same database transaction as the content it applied.
  On connect it sends `resume(conversationId, streamId, seq)`. The host replays from its log, or sends a paged,
  full-fidelity snapshot followed by the tail of the log. Nothing is ever compacted by truncating text.
- **The host keeps a model off the IDE thread.** A thread-safe `MirrorLog` holds the event log and a materialised
  conversation model built from the same events. Resume, snapshot, turn fetch and acknowledgements are answered on the
  connection thread without waiting for the IDE.
- **The transport is a real event loop.** One connection thread per controller uses non-blocking OpenSSL with
  `poll`/`select` and a wake-up signal. It drains every ready read and keeps writing until `WANT_WRITE`. The outbox is
  prioritised and byte-budgeted (control > state > log > bulk) and splits large items into 32 KiB frames, so a pong or
  an approval is never behind a snapshot. Both sides send heartbeats every 10 s and treat the link as dead after 30 s.
- **Commands are acknowledged and idempotent.** Each command has a client-generated ID and is kept in a persistent
  outbox on the phone. The host answers `queued` at once from the connection thread, then `accepted`, `rejected(reason)`
  or `done`. A duplicate-detection table answers `duplicate` for IDs it has already seen. After an ambiguous disconnect,
  the phone asks which IDs the host has. It re-sends only those the host never received. It never automatically re-sends
  a prompt the host accepted (this keeps the "no automatic replay of a turn that ran a tool" rule).
- **On the phone, the database is the source of truth.** A Room database stores conversations, turns, blocks, images
  (files) and the outbox. The network layer writes to it in batched transactions. The UI only observes database flows,
  so live view and offline review are the same screen. This removes the `applied`/`screen` dual state.

### Constraints

- House style per `Documents/free-pascal-engineer.md`; new Pascal units stay under 1000 lines. The existing
  `AssistantMonitorLan.pas`, `AssistantMonitorSession.pas` and `AssistantMonitorBridge.pas` are already over that limit,
  so this work splits them rather than growing them.
- TLS, pairing, HMAC auth and fingerprint pinning keep their current security properties.
- Protocol version moves to catalogue 3, with a clear "update the app or the IDE" rejection on mismatch. There is no
  long-lived dual stack.
- Claude connector rules still hold: no automatic replay of a turn that ran a tool.

### Success criteria (measured by item 9.2)

- Time from IDE change to phone screen: p95 < 150 ms on a LAN while a turn streams.
- Pong round trip < 100 ms while a 2 MiB snapshot is being sent.
- Resume after a 60 s disconnection: phone shows the current state within 1 s for a backlog up to 2 MiB.
- Chaos test: 1000 random disconnects, delays and duplicate deliveries end with the phone database identical to the
  host model, and no stuck "busy" state.
- The phone shows any cached conversation with no network, including thinking and tool bodies in full.

## 4. Host transport redesign

Replace polling from `OnIdle` with a connection event loop and a prioritised outbox. Split `AssistantMonitorLan.pas`.

### 4.1 Connection thread with non-blocking I/O
Status: not started

New unit `AssistantMonitorLink.pas`. The listen thread only accepts. It makes the socket non-blocking straight away and
hands it to a `TMonitorLinkThread`. That thread runs `SSL_accept` without blocking, under a 10 s handshake deadline, then
loops on `fpPoll`/`select` over the socket plus a wake-up handle: a pipe or eventfd on Unix, and a loopback socket pair
on Windows. The thread is signalled whenever the outbox gains data. All reads and writes on one `SSL` object happen on
this thread only. `WANT_READ`/`WANT_WRITE` retries follow OpenSSL's non-blocking rules: retry the same call with the
same buffer. A new controller replaces the old one cleanly. The old link gets `bye(replaced)` and closes, which removes
the `busy` rejection path that leaves the phone reconnecting in a loop.

### 4.2 Prioritised, chunked, byte-budgeted outbox
Status: not started

New unit `AssistantMonitorOutbox.pas` with four lanes: control (pong, ack, approval, error), state (latest status,
coalesced by key), log (sequenced events, never dropped, kept until the phone acknowledges them), and bulk (images, turn
fetch, snapshot pages). Items larger than 32 KiB go out as chunked frames, and the writer moves between lanes at chunk
boundaries, so control is delayed by at most one chunk. The budget is counted in bytes. When the log lane is over budget,
the link closes and the phone resumes from the log rather than losing events. Use a ring buffer in place of the
`Delete`/shift arrays.

### 4.3 Heartbeat and dead-link detection
Status: not started

Both sides send `ping` after 10 s without sending anything and treat 30 s without receiving anything as a dead link. The
host answers pong from the connection thread at once (control lane). Enable TCP keepalive on the socket as a backstop.
Share the timing constants through the protocol spec (5.1).

### 4.4 Command intake off the IDE thread
Status: not started

The connection thread decodes each command, records its ID in the duplicate-detection table (last 256 IDs with their
results), and acknowledges `queued` at once. The bridge runs it on the IDE thread and posts `accepted`/`rejected`/`done`
through the outbox. Approval decisions stay on the connection thread, as they are today.

Status: not started

New unit `AssistantMonitorMirror.pas`: a thread-safe log of events per conversation (bounded by bytes, default 8 MiB,

### 5.4 Append deltas for streamed blocks
Status: not started

`PumpMirror` emits `block_append {blockId, offset, text}` when a block body has grown by appending, and `block_replace`
only when an earlier part changed. The phone checks that `offset` equals the length it has stored. On a mismatch it asks
for that block (`block_get`) and does not guess. Streaming traffic becomes proportional to the new text.

### 5.5 Acks and flow control
Status: not started

The phone sends `ack {conversationId, streamId, seq}` after each committed database batch (at most every 250 ms). The
host keeps log events until they are acknowledged, and sends at most 512 KiB of unacknowledged log data ahead of the
last ack (a credit window), so a slow phone slows the host instead of filling queues.

Rewrite `LanSession.kt` as three coroutines under one supervisor per connection. The reader decodes frames into an
unlimited, byte-accounted channel to the `SyncApplier` and answers ping at once through the writer. The writer drains
lane-priority channels (control, then commands, then acks). The heartbeat follows 4.3. Use a reusable compacting frame
buffer (REVIEW O4). The 45 s publish wait in `InboundDelivery` goes away.

### 7.2 Network- and lifecycle-aware reconnect
Status: not started

Register a `ConnectivityManager.NetworkCallback`. Reconnect at once when Wi-Fi becomes available, reset the backoff,
and cap the backoff at 10 s with jitter on a LAN. Connect while the app is in the foreground. Close with `bye` when it
moves to the background, and resume on return. Keep the saved TLS pin rules (REVIEW B1) as they are.

### 7.3 Outbox replay rules
Status: not started

User commands go into the `outbox` table first. On reconnect, the phone sends `resume` with its unacknowledged command
IDs. The host replies with the state of each one (unknown, queued, accepted, done or rejected). Only `unknown` commands
are re-sent. A prompt the host has accepted is never re-sent automatically. If its outcome cannot be known, the draft is
offered back with a "Not delivered — Retry" action.
