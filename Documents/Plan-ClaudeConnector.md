# Claude connector

Generated by Lazarus Project Assistant.

Make the Claude connection a first-class assistant backend: Claude Code runs on the user's Claude subscription, streams its answers into the IDE, keeps its own session, and works on the project through the IDE's Lazarus tools with approvals shown as IDE dialogs.

The review behind this plan, with the evidence and design detail each item refers to, is `Documents/ClaudeConnectorReview.md` (cited below as "review §n"). Work is on branch `claude-connector`. Captured Claude Code output for tests is in `Tests/Fixtures/Claude/`.

## 1. Constraints and decisions

These hold for every item:

- Claude turns run on the Claude subscription, never per-use API billing. Never read or copy Claude sign-in files. Never add `--bare`, `--max-budget-usd`, or `--betas`. The child environment drops billing variables, and `claude auth status` is checked once per executable per IDE session, then trusted (decision of 28 October 2026).
- A Claude turn that has run a tool is never replayed automatically.
- Code follows `Documents/free-pascal-engineer.md`. The `F` prefix is only for the private field behind a `Property`; new code in an old-convention unit may match its surroundings, and existing fields are not renamed as part of this work.
- Ask mode must not deny silently: approvals appear as IDE dialogs.
- Claude gets the IDE's own Lazarus tools through MCP, reversing commit `cd69058`.
- Tests run through `Tests/RunAssistantTests.pas` (see `CLAUDE.md`). Known baseline failures in `AssistantSettingsTest` are not caused by this work.

### 2.10 Hold each turn to its conversation mode
Status: complete

Commits `a80d314` and `5699d05`. Found by trying the connection in the IDE: Chat mode could change code, because every turn had Claude Code's full tool set. Each turn now gets a `TClaudeToolScope` that the form maps from its mode:

| Mode | Scope | Claude Code arguments |
|------|-------|-----------------------|
| Chat | `ctsNone` | `--tools=` and `--strict-mcp-config`: no tools, no MCP servers |
| Inspect (and any other) | `ctsRead` | `--tools=Read,Grep,Glob` and `--strict-mcp-config` |
| Document, Plan | `ctsMarkdown` | `--tools=Read,Grep,Glob,Edit,Write`, `--allowedTools=Edit(**/*.md),…` and `--strict-mcp-config` |
| Build | `ctsProject` | Claude Code's own tools; the approval setting picks the permission mode |

Options are passed as `--option=value` so an empty list cannot swallow the next option. Only the project scope applies the approval setting. The same work fixed the Claude model list not being read back from the connection settings. The scope type keeps the client free of IDE units, so its test stays headless.

## 3. Lazarus tools over MCP

Claude Code reaches the IDE's `TAssistantToolBroker` through an MCP server inside the IDE (review §11.2). The broker is already backend-neutral: it runs on the IDE thread, works on editor buffers, publishes `ToolsJson`, runs `Execute(RunId, Tool, Arguments)`, scopes writes with `BeginRun(TAssistantWriteScope)`, and asks through `OnApproval`. The Codex path (`FCodexBroker` in `ProjectAssistantForm`) shows how it is driven.

Verified with a stub server against the real Claude Code (review §12.1): `--tools "Read,Grep,Glob"` combines with MCP tools, `--allowedTools "mcp__lazarus__*"` runs them without a prompt, a bearer token in the `--mcp-config` headers reaches every request, the default tool-call timeout is about 60 s and `MCP_TOOL_TIMEOUT` extends it, and a server that blocks while a call is pending stops the next session from connecting.

### 3.1 MCP message layer
Status: not started

New pure unit (no sockets, no IDE units), for example `AssistantMcpProtocol`. It parses one JSON-RPC request and builds its response:

- `initialize`: echo the client's `protocolVersion`, `capabilities: {"tools": {}}`, and `serverInfo` name `lazarus`.
- `notifications/initialized` and other notifications: no response body (HTTP 202).
- `tools/list`: the broker's tools as MCP tool objects (`name`, `description`, `inputSchema`) converted from `ToolsJson`, which already carries those three fields in a `"type":"function"` wrapper. Claude Code names MCP tools `mcp__<server>__<tool>`, so with the broker's `lazarus_` names and a server called `lazarus` the result would be `mcp__lazarus__lazarus_read_buffer`. Either strip the `lazarus_` prefix in the MCP listing (and restore it on `tools/call`) or call the server `ide`; pick one and use it in 4.1's `--allowedTools`.
- `tools/call`: name and arguments handed to a caller-supplied executor; the result becomes `content: [{"type":"text","text":…}]`, with `isError` for a tool failure.
- `server/discover` and any unknown method: JSON-RPC error -32601. Claude Code tolerates it.

Done when unit tests cover each method from recorded request text, and a malformed request gets a JSON-RPC parse error rather than an exception.

### 3.2 Loopback HTTP listener with a per-run token
Status: not started

An HTTP endpoint for MCP's streamable HTTP transport (plain JSON responses are enough), bound to `127.0.0.1` on a free port. A new random bearer token for each run; requests without it get 401. Each request is served on its own thread so a pending tool call never blocks `initialize` or `tools/list` from the same or a later session. The listener starts with a Claude run and stops when the run ends or is cancelled.

Write the `--mcp-config` JSON (`{"mcpServers":{"lazarus":{"type":"http","url":…,"headers":{"Authorization":"Bearer …"}}}}`) to an owner-only temporary file, never on the command line, and delete it when the run ends.

Done when a scripted HTTP client in a test can initialize, list, and call through the listener, a wrong token is refused, and a deliberately slow call does not block a second client.

### 3.3 Run tool calls on the IDE thread through the broker
Status: not started

A `tools/call` arriving on a listener thread is queued to the IDE thread, runs `Broker.Execute`, and its result is handed back to the waiting request. Cancel (Stop, or the run ending) releases any waiting request with an error.

The broker run's write scope comes from the turn's `TClaudeToolScope` (item 2.10), so there is one mapping from mode to permissions, not two that can drift: `ctsNone` → `awsNone`, `ctsRead` → `awsReadOnly`, `ctsMarkdown` → `awsMarkdown`, `ctsProject` → `awsProject`. This matches what `LaunchStoredCodexRun` does for the same modes. With `awsNone` the broker lists no tools, which agrees with Chat having none.

Done when a test drives a call from a listener thread into a broker with a test workspace adapter and gets the result, and Cancel unblocks a waiting call.

### 3.4 Keep a call open while the user decides
Status: not started

A broker tool that needs approval raises `OnApproval` on the IDE thread and the request waits for the answer. Claude Code is started with `MCP_TOOL_TIMEOUT` (for example 30 minutes) in its environment so it does not abandon the call. The listener keeps serving other requests while the dialog is open. Declining returns a tool error that tells Claude the user declined.

Done when an approval left open for longer than 60 s still completes the call, and a decline reaches Claude as a tool error, not a dropped connection.

## 4. Claude runs with the Lazarus tools

### 4.1 Launch Claude Code with the Lazarus server
Status: not started

When a Claude turn whose scope is not `ctsNone` starts, the form starts the listener and broker run, and `MCP_TOOL_TIMEOUT` is added to the scrubbed environment. Extend `AppendClaudeModeArguments` (item 2.10) rather than adding a second argument builder, keeping the `--option=value` form:

- `ctsNone`: unchanged (`--tools=`, `--strict-mcp-config`, no server).
- Every other scope: `--tools=Read,Grep,Glob`, `--mcp-config=<file>`, `--strict-mcp-config`, and one `--allowedTools=` list naming the Lazarus tools. Emit a single list: it is not yet verified whether a second `--allowedTools=` adds to the first or replaces it.
- `ctsMarkdown` drops Claude Code's own `Edit` and `Write` and the `Edit(**/*.md)` rule, and `ctsProject` drops Claude Code's full tool set: the broker's write scope now enforces Markdown-only or project writes, on editor buffers, with its approvals. One write path, not two.

The temporary config file and the listener are cleaned up on finish, cancel, and failure. Update the 2.10 tests for the new arguments. Lazarus calls then reach the trace (item 4.3) as `mcp__<server>__<tool>`; show them under a readable name, for example by dropping the `mcp__<server>__` prefix in the tool block title.

Done when a real turn lists the Lazarus tools in its `init` event and can read a file through them, and an attempt to write without a Lazarus tool is reported by Claude as impossible rather than performed.

### 4.3 Show Claude's tool calls and thinking in the trace
Status: blocked
User action: With Show tool use and Show thinking on, run a Claude turn that reads and edits, and check the trace shows narration, each call with its result, and a thinking note, in order; then turn both off and check only the answer remains. Mark this item complete if it does.

Widened from the Lazarus tools only to every tool call, because Build mode uses Claude Code's own tools today. Found in the IDE: with Show tool use and Show thinking on, everything Claude reported still appeared in Assistant reply blocks.

What Claude Code sends, checked against the real program: every tool call (`tool_use` with id, name and input) and its result (`tool_result` with content and an error flag), and the text Claude writes between calls. It does not send its reasoning. In print mode a thinking block always has empty text, with or without partial messages or the `showThinkingSummaries` setting. Only `thinking_tokens` events give an estimated size while a model call thinks.

Implemented, the same way Codex tools are shown:

- `AssistantClaudeStream` records each call in order (`TClaudeToolStep`: id, name, bounded input, bounded output, error, done, and the text and thinking lengths when it was made), and builds a thinking channel of notes: `Thinking… about N tokens.` while live, `Thought for about N tokens.` once the thinking block arrives.
- The worker publishes a copy of the calls and the thinking notes with each snapshot.
- `ApplyClaudeToolSteps` puts the text and thinking written before each call into the trace, adds a tool block, and starts new answer and thinking slices, as `PollCodex` does for a serviced tool. A block is finished with its result, opened and marked failed on an error. The footer stays on Running while a call waits.
- A successful `Edit`, `Write` or `MultiEdit` of the active plan file counts as a plan write, so the progress list refreshes when the turn ends in any mode (part of item 4.4).

The code is done and was checked against the real program outside the IDE. What remains is the look in the IDE above, which only a person can do. The run order matters: an item marked in progress is always taken first, so this item is blocked rather than in progress.

Done when, with Show tool use and Show thinking on, a Claude turn that reads and edits shows its narration, each call with its result, and a thinking note, in order, while the turn runs; and with both options off, only the answer text.

### 4.4 Plan status changes from Claude follow the completion rule
Status: not started

The completion rule (commit the finished work, then set Status complete, then commit the plan) is enforced in `WriteMarkdownFile` and `ReplaceInMarkdownFile` through `PlanCompletionBlocked` and `NotePlanCompletionWrite`, and the turn-end commit is `RevertUncommittedPlanCompletion`. A Claude turn that edits the plan file with Claude Code's own `Edit` bypasses all of it, so an item can become complete with nothing committed. The progress list is also rescanned at turn end only in Build mode or after the assistant's own plan write, so a Plan- or Document-mode Claude edit does not show until something else refreshes it.

Item 4.3 already refreshes the progress list at turn end when a Claude Code edit touched the active plan. Until 4.1, Claude edits plans with its own tools in every mode except Chat and Inspect. After 4.1 the edits arrive through the broker's buffer writes, which do not call those plan functions either. Route a broker write to a registered plan file through the same completion check and note, or have the form compare the plan before and after a Claude turn and apply the same rule. Refresh the progress list after any Claude turn that changed the active plan.

Done when a Claude turn that sets an item complete without a commit is refused or reverted exactly as an assistant turn is, and the progress list shows a Claude plan edit without switching modes.
