# Plan: Replace the remote monitor with a pulse-and-fetch link

Generated by Lazarus Project Assistant.

This plan replaces the remote monitor on both sides. The current implementation is removed first and the replacement is built in its place, so there is never a period with two monitors installed. Until section 7 is finished there is no working phone link; that is accepted.

What stays:

- The phone screens: `ConversationScreen`, `PlanScreen`, `ApprovalSheet`, `TraceCards`, `MonitorMarkdown`, the menus and Settings, and dictation.
- The desktop's existing `FillMonitor*` and `Remote*` methods on `TProjectAssistantForm` and the hooks in `AssistantSessionObserve`, which already give a clean read and command surface.
- The certificate minting in `AssistantMonitorTls`, the approval waiter in `AssistantMonitorApproval`, and the Remote Monitor options dialog layout.

What goes: the whole catalogue 3 protocol. That means the event log, the materialised mirror, lanes, credit windows, acks, chunking, snapshots, resume, the phone's Room sync applier, and its latched connection states.

Why. The current monitor is about 18,000 lines of Pascal and 20,000 lines of Kotlin (plus 12,000 of tests) for a link that mirrors one window. It keeps three copies of history (the `.jsonl` files, the in-memory mirror log, and the phone's Room rows built from deltas) and reimplements reliable delivery on top of TLS. `Documents/Plan.md` and `Documents/Plan-20261122-022435.md` trace the recent stalls to that machinery:

- a full credit window that stops the phone reading;
- deferred appends behind a fetch cap of two;
- pause and terminal latches that only a new process clears.

In about three months there have been 352 monitor commits. Fixes now add rules that interact.

The replacement in one paragraph. The desktop is the only source of truth. Stored turns come from the conversation files, and the live turn comes from a small snapshot that the IDE thread publishes. The desktop sends a pulse: a small JSON state record with version numbers, the activity label and its start time. A pulse is level-triggered state, not an event, so a lost or repeated pulse is harmless. The phone compares each pulse with its Room cache and fetches what it needs: the conversation list, a page of turns, one turn, or the tail of one item. It chooses how often to follow the running item. Images, commands and the pulse use separate HTTPS requests on separate workers, so Stop and Steer are never queued behind a download. Every read is idempotent and every command carries a phone-generated id. A dropped connection loses nothing, because the next request catches up.

Success criteria:

- A two-hour plan run with long tools stays current on the phone with no app restart, no manual reconnect, and no stuck Busy.
- After a Wi-Fi drop, the phone catches up within one pulse wait (10 s) of the network returning.
- Stop reaches the desktop within one second of the tap, even while a large image or history page is downloading.
- With the desktop offline, the phone can review cached conversations and the plan, and can queue prompts. Queued prompts are sent once and never twice, including across an IDE restart.
- The phone screens look and behave as before, apart from the removed model, reasoning, target and permission controls.
- The desktop package is under 4,000 lines and the phone's non-UI code is under 5,000 lines, excluding tests.

Out of scope for now:

- Model, reasoning, target and permission switching from the phone. The command design below must make adding them back a host handler plus a capability flag, with no protocol change.
- A relay for use away from the LAN. Nothing below may assume that the phone and desktop share a subnet beyond the TLS endpoint the phone is given.

Conventions for every item:

- Pascal follows `Documents/free-pascal-engineer.md` and the unit size rule in `CLAUDE.md`.
- New Pascal tests go under `Tests/` and are registered in `Tests/RunAssistantTests.pas`.
- Kotlin keeps the existing header comment style.
- Scratch output goes in `Temporary/`.
- Commit each finished item with a `Monitor:` (desktop) or `Monitor app:` (phone) subject prefix.

The package keeps its name, `LazAssistantMonitor`, and its folder, so the IDE installation does not change. The phone keeps its application id and Kotlin package `computing.michell.monitor`. The listener keeps port 56122 and the existing compile-time check against `GrokOAuthRedirectPort`.

## 1. Design contract: transport and identity

All traffic is HTTPS/1.1 to one listener on the desktop. The certificate is the self-signed certificate minted by `AssistantMonitorTls`, and the phone pins its SHA-256 fingerprint as before. Every request except `pair` carries `Authorization: Bearer <token>`. JSON bodies are UTF-8. Paths are versioned under `/v4/`.

Identity:

- `epoch` is a random id minted when the listener starts. It changes on IDE restart.
- `rev` is a 64-bit counter within an epoch. It goes up whenever anything the phone could show changes.
- Conversation ids are the persisted monitor ids from `TAssistantConversationStore` (the identity file), so they survive archiving.
- Turn ids are `TConversationTurn.Id`. The live turn already has the id it will be stored under, so moving from live to stored is a version change on one id, not a move.
- Item ids are trace block ids (`TTraceBlock.ID`, a GUID persisted in `TraceJson`). Item revisions are `TTraceBlock.Revision`, which is only meaningful within one epoch.
- Stored turns get a content `etag`: FNV-1a 64 of the stored JSON line, using `AssistantPlanHashFold`. A stored turn's etag stays valid across epochs, so a cached turn is never fetched again unless it changes.
- Image ids are the image store ids. A stored image never changes under its id, so it is cached by id indefinitely.

Errors use HTTP status codes with a JSON body `{"reason": "...", "message": "..."}`:

- 400 `protocol`
- 401 `auth` (unknown token)
- 403 `revoked`
- 404 `not_found`
- 409 `busy` or `unsaved_edits`
- 413 `too_large`
- 503 `no_session` (the assistant window is closed), with `Retry-After`

Conversation lists, turns and the plan send `ETag` and honour `If-None-Match` with 304.

## 2. Design contract: the pulse

`GET /v4/pulse?after=<rev>&epoch=<epoch>&interval=<ms>` is a long poll. The desktop answers at once if its epoch differs or its rev is above `after`. Otherwise it waits until a change arrives, or for 10 seconds, and then answers with the current pulse.

`interval` is the shortest gap the phone wants between answers. It is clamped to 150–10,000 ms and defaults to 250. The host holds a change back until that long after its previous answer, so a streaming answer produces at most one pulse per interval and never a backlog. The phone treats a link as down after 20 seconds with no answer.

Shape (about 600 bytes):

```json
{ "epoch": "…", "rev": 18234, "server_time": "2026-11-24T10:15:02.120Z",
  "status": { "available": true, "busy": true, "sending": true, "plan_running": true,
    "mode": "build", "phase": "tool", "status_text": "…", "activity": "Running build",
    "activity_since": "2026-11-24T10:11:36.004Z", "turn_started_at": "…",
    "can_send": false, "can_steer": true, "can_stop": true, "can_change_mode": false,
    "stop_pending": false, "remote_approval": true, "error_text": "",
    "usage_caption": "", "usage_hint": "" },
  "conversation": { "id": "…", "title": "…", "etag": "…", "turn_count": 37 },
  "live": { "turn_id": "…", "turn_index": 37, "rev": 96,
    "item": { "id": "…", "kind": "thinking", "state": "running", "rev": 95, "bytes": 18400 } },
  "plan": { "path": "Documents/Plan.md", "etag": "…", "running": true, "item": "3.2" },
  "lists": { "conversations": "<etag>", "plans": "<etag>", "tasks": "<etag>" },
  "approval": { "id": "…", "tool_name": "run_build" } }
```

`live` is null when no turn is running. `approval` is null when nothing is waiting. The phone shows "Thinking… 3:26" from `activity` and `activity_since`, corrected by `server_time` against its own clock, and ticks the timer locally, so the timer needs no traffic. What the phone fetches in response to a pulse is its own decision; the rules are in item 6.4.

## 3. Design contract: reads, images and commands

Reads:

| Request | Answer |
|---|---|
| `POST /v4/pair` | Takes `{code, client_id, client_name}` and returns `{token, host_name, fingerprint}`. The only call without a token. |
| `GET /v4/hello` | Host version, epoch, limits, and `capabilities`: the command types this host accepts. |
| `GET /v4/conversations` | `[{id, title, created_at, turn_count, etag, current}]` |
| `GET /v4/conversations/{id}/turns?from=N&max_bytes=B` | Stored turns from index N in order, with their items and bodies, up to about B bytes (default 512 KiB), and `next`. |
| `GET /v4/turns/{turn_id}?bodies=0\|1` | One turn, live or stored. `bodies=0` gives only the outline: item ids, kinds, states, revisions and byte lengths. |
| `GET /v4/items/{item_id}?from=N&check=H` | `{id, rev, state, total_bytes, start, text}`. Returns only the tail after byte N when the 64 bytes before N still hash to H. Otherwise returns the whole item with `start` 0. |
| `GET /v4/plan` | `{path, title, etag, running, rows}` as `TAssistantMonitorPlanRow`. |
| `GET /v4/plan/document` | The plan Markdown preview (`ReadMonitorPlanPreview`). |
| `GET /v4/plans`, `GET /v4/tasks` | Plan and task choices. |
| `GET /v4/images/{id}` | Display-size image bytes with their content type. `Cache-Control: immutable`. |
| `GET /v4/approval` | The waiting approval: tool, summary and mode caption. |

Byte offsets are UTF-8. The host moves `start` back to a character boundary if needed, and the phone uses the returned `start`.

Commands are sent as `POST /v4/commands` with `{id, type, args}`. `id` is a UUID that the phone makes once, when the user acts, and reuses on every retry. The answer is synchronous: 200 `{state: "done" | "accepted"}`, or a 4xx reason. `accepted` means the desktop has taken the command and the pulse will show its effect.

The first command set, each mapping to an existing `TProjectAssistantForm.Remote*` method:

- `send {text, save_first}`
- `steer {text}`
- `stop`
- `approval {tool_id, decision: allow | deny}`
- `set_mode {mode}`
- `new_conversation`
- `select_conversation {id}`
- `select_plan {path}`
- `new_plan {title}`
- `close_plan`
- `run_plan {save_first}`
- `stop_plan`
- `work_on_plan {section}`
- `run_task {task_id, note, save_first}`
- `insert_task {task_id, note}`

`select_target`, `set_model`, `set_reasoning` and `set_permissions` are left out. Adding one back later needs three things: a host handler, its name in `capabilities`, and a phone control that is shown only when that capability is present.

Duplicates:

- The desktop stores the `send` id with the turn it starts (item 5.2), so a resent prompt is recognised even after an IDE restart.
- Other commands are recorded in a bounded in-memory table.
- `stop`, `stop_plan` and `approval` are naturally idempotent.

Priority: `stop`, `steer`, `stop_plan` and `approval` never wait behind other work. They are decided on the HTTP thread, which sets `stop_pending` (or stores the approval decision) under a lock and queues the form call to the IDE thread at once. If the IDE thread is inside a modal (`AssistantModalDepth > 0`), the queued call runs when the modal closes. The pulse shows `stop_pending` until then.

## 5. Desktop host

### 5.1 Prove the HTTP stack and the off-thread store read

Status: not started

Two assumptions carry the desktop design. Prove both before writing the host.

The first is that `fphttpserver.TFPHttpServer` from FPC 3.3.1 can do all of the following:

- serve HTTPS with the certificate and key that `AssistantMonitorTls` mints (DER from `i2dX509Bio` and `i2dPrivatekeyBio`);
- run in threaded mode;
- hold a long-poll request open on one thread while another request is served.

If `CertificateData` cannot take the existing DER, convert it in memory and record how. Use `AssistantHttps.EnsureOpenSSLReady` to load OpenSSL. Check SIGPIPE handling on Linux and macOS, as the old `AssistantMonitorLink` did (see the reference worktree).

The second is that stored turns can be read from the `.jsonl` files and converted to `TAssistantMonitorTurn` on a non-IDE thread, without touching `TAssistantConversationStore`'s in-memory array or any LCL object. Find the parse path (`ParseTurnLine`, and the trace JSON decode in `AssistantTrace`) and confirm that it has no form, LCL or global mutable state. If it has, record the smallest change that would allow a thread-safe reader.

Write the findings at the end of this item. Keep the spike programs in `Temporary/`.

Acceptance: a throwaway program serves `GET /ping` over HTTPS with the minted certificate while a second request blocks for 10 seconds. `curl` with the certificate accepts it, and the concurrent ping answers at once. A second throwaway program parses a real `conversation.jsonl` on a worker thread and prints turn ids, item ids and body lengths that match what the form shows.

### 5.4 Publish the host snapshot from the IDE thread

Status: not started

Add `AssistantMonitorSnapshot`. On the IDE thread, a coalescing timer builds an immutable snapshot 100 ms after a `TouchAssistantMirror` wake or an observe notice, with a 1-second backstop. The snapshot holds:

- the status fields of the pulse, from `FillMonitorView`;
- the current conversation's identity, title, turn count and etag;
- the live turn, from `FillMonitorTurn(MonitorLiveTurnIndex)`, with every item's id, kind, state, revision and body;
- the plan path, etag and running item;
- the list etags;
- the current approval, from `CurrentAssistantApproval`.

The builder compares the new snapshot with the previous one. If anything differs, it increments `rev` and publishes the new snapshot under a lock as a reference-counted object. HTTP threads only read published snapshots. Bodies are reference-counted `AnsiString`s, so publishing does not copy text. Confirm that `IsMultiThread` is set so that the reference counts are atomic.

The snapshot never builds JSON on the IDE thread. A long build must not drop the next change: if a build is running, set a dirty flag and build again when it finishes. The old `FPumping` early exit dropped the tick instead.

Acceptance: a new `AssistantMonitorSnapshotTest` drives a fake form source and checks the following. Fifty changes in 100 ms produce one or two revs, not fifty. A change made during a build is published by the next build. Two threads reading snapshots while the IDE thread publishes run under heaptrc with no leak and no crash.

### 5.8 Accept commands, with priority for Stop and Steer

Status: not started

Implement `POST /v4/commands` as section 3 describes, in a new `AssistantMonitorCommands`.

Ordinary commands are queued to the IDE thread with `TThread.Queue`. The HTTP thread waits up to 5 seconds for the form's answer, so it can return `done` or a 409 (`busy` or `unsaved_edits`). If the wait runs out, it answers `accepted`. Respect `AssistantModalDepth` as the old bridge did.

`stop`, `steer`, `stop_plan` and `approval` take the priority path: decide on the HTTP thread, record the decision under a lock, queue the form call at once, and answer without waiting for the IDE thread. `approval` stores its decision with `StoreAssistantApprovalDecision` and `SignalAssistantApprovalWait`, and uses the kept `AssistantMonitorApproval` waiter.

Duplicates: `send` and `run_task` check `TurnForClientCommand`, and answer `done` with the turn id if the command is already known. Other commands use a 256-entry table. The `capabilities` list in `/v4/hello` names exactly the command types that have handlers.

Acceptance: `AssistantMonitorCommandsTest`, with a fake form, checks the following:

- `send` with the same id after a simulated restart, where the id is found in the store, starts no turn.
- `stop` answers within 50 ms while the fake IDE thread is blocked for 3 seconds, and the pulse shows `stop_pending` until the queued call runs.
- `unsaved_edits` gives 409.
- An unknown type gives 400 `protocol`.

## 6. Phone network and sync engine

### 6.1 HTTP client, pinning and Wi-Fi binding

Status: not started

Add OkHttp to the app module. In a new package, `computing.michell.monitor.net`, build three `OkHttpClient`s for the pulse, reads and commands. They share one pinning trust manager and one Wi-Fi socket factory, but each has its own dispatcher. Images use their own client (item 6.5).

Pin the SHA-256 of the leaf certificate with the rules from the old `LanSession` (in the reference worktree): an empty pin trusts the endpoint, and a pin that is not 64 hex characters is refused. Bind sockets to the Wi-Fi `Network` from a small `WifiRoute` helper that samples the network before every request rather than caching it until a callback. Store pairings by endpoint (address and port), each with its pin, client id and token. The token goes in `EncryptedSharedPreferences`.

Acceptance: unit tests with `MockWebServer` over TLS check:

- a good pin connects;
- a wrong pin fails with a pin error that the UI can name;
- an empty pin trusts the endpoint;
- a malformed pin is refused before connecting;
- a command posted while a 5-second image response is in flight completes in under 200 ms.

### 6.2 Link state with no latches

Status: not started

Add `PulseLoop`: one coroutine that repeats the pulse request. The link state is one of:

- `Connected`: a pulse arrived within 20 s.
- `Retrying`: with the next attempt time.
- `Unpaired`: after a 401 or 403.
- `PinMismatch`
- `Stopped`: the user disconnected, or the app is in the background with nothing to watch.

Backoff is 1, 2, 4 and 8 seconds with jitter, then 15 seconds. A touch, a return to the foreground, a Wi-Fi change or a Reconnect tap cancels the wait and tries at once, in every state except `Unpaired`, `PinMismatch` and `Stopped`. Nothing else blocks a retry. There is no pause flag, no terminal flag and no "replaced" latch: a second phone has its own token, and both may watch.

Acceptance: `PulseLoopTest` with a fake clock checks:

- a 503, a timeout and a reset each retry on the schedule;
- a touch during backoff retries at once;
- a 403 stops, and only a new pairing restarts it;
- a pin mismatch stops, and only accepting the new pin restarts it;
- a thousand random failures followed by success always reach `Connected`.

### 6.3 Room schema and cache

Status: not started

- `conversation`: id, title, etag, turn count, current flag.
- `turn`: id, conversation id, index, etag, prompt, mode, created at, outcome, duration, error text, client command id.
- `item`: id, turn id, ordinal, kind, state, title, tool name, body, revision, epoch, byte length.
- `image`: id, turn id, item id, name, size, local path.
- `plan`: path, title, etag, rows JSON, document text.

Port the retention rule from the old `Retention.kt` (in the reference worktree): a conversation cap and an image byte budget, with the same defaults.

Acceptance: DAO tests on JVM SQLite insert, replace by id, and query in order. A retention test removes the oldest conversations and images beyond the limits, and never removes the current conversation or unsent outbox rows.

### 6.4 Sync engine: act on a pulse

Status: not started

Add `SyncEngine`. It compares each pulse with Room and schedules fetches through a single-flight queue keyed by resource, so the same URL is never requested twice at once. Fetches are prioritised in this order:

- The live item's tail, when the item rev differs, at the cadence set in item 6.6.
- The live turn's outline, when the live turn rev differs.
- The current conversation's new stored turns, when its etag or turn count differs, using `turns?from=<cached count>`. When the live turn becomes stored, fetch it once by id and replace the live rows.
- The plan, when its etag differs. The plan document only while the plan screen is open.
- The conversation, plan and task lists, when their etags differ.
- Approval details, when `approval.id` changes.
- Older history pages, only when the user scrolls to them.

On an epoch change, keep every stored turn whose etag still matches, treat live revisions as unknown, and refetch the live turn outline and the current conversation's turn count.

Every fetch writes Room in one transaction, and the UI observes Room. A failed fetch is tried again on the next pulse that still shows a difference. There is no separate repair path.

Acceptance: `SyncEngineTest` with a fake server checks:

- a pulse with unchanged etags fetches nothing;
- 100 pulses during streaming never have more than one item request in flight;
- live-to-stored makes one turn fetch and leaves no live rows;
- an epoch change keeps cached stored turns;
- a fault script that drops every third response, reorders pulses and repeats old pulses ends with Room exactly matching the fake host.

### 6.6 Follow the running item at an adaptive rate

Status: not started

Add `ItemFollower`. While the conversation screen is visible and following the head, it requests the live item's tail as soon as a pulse shows a new item rev, but no more often than once per `followMs`.

`followMs` starts at 250 ms. It doubles, up to 2 seconds, when a fetch takes more than half the gap or the app reports memory or battery pressure. It returns to 250 ms when fetches are quick again. The pulse `interval` follows the same value.

With the screen off, the app in the background, or the reader scrolled away from the head, the follower asks for `interval=5000`, fetches no item text, and fetches each item once when its `state` stops being `running`. A finished turn always gets one final fetch, so the cache matches the desktop.

Acceptance: `ItemFollowerTest` with a fake clock checks:

- a fast host gets about four fetches a second;
- a slow host backs off to one fetch every 2 seconds;
- scrolling away stops tail fetches;
- a closing item always gets its final fetch.

### 6.7 Commands, outbox and offline prompts

Status: not started

Add `CommandSender` on the command client. Every user action first writes a command row with a UUID, then sends it.

`stop`, `steer`, `stop_plan` and `approval` go straight to the network and never go behind the outbox. If the link is down they fail visibly, because a delayed Stop would be wrong.

`send` and `run_task` go through the outbox, in order:

- The first queued prompt is sent when a pulse shows `can_send`.
- Each later prompt waits until the previous prompt's turn has finished.
- A 409 `unsaved_edits` raises the existing save question. Yes resends with `save_first`, under the same id.
- A 409 `busy` waits for the next `can_send`.
- A queued prompt can be edited or deleted until it is sent.

Other commands are sent once, and their result is reported.

Acceptance: `CommandSenderTest` checks:

- three prompts queued offline are sent in order, one at a time, after reconnection;
- a connection reset after the server has accepted a prompt resends it with the same id and starts no second turn (using a fake host with the duplicate rule);
- Stop is sent while a send waits in the outbox;
- the save question round trip keeps the id.
