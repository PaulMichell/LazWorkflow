# Preserve monitor pairings when switching hosts

Generated by Lazarus Project Assistant.

In the Android monitor, `LanSession.connect` copies the saved TLS fingerprint when the address or port changes, clears the client ID and session token, and saves the modified record before connecting. A phone paired with Linux can therefore reject the MacBook’s certificate before pairing begins.

## 1. Store and select pairings per endpoint

### 1.1 Preserve existing pairing data during migration

Status: complete

Trace the connection store and the keys used for conversation history. Store the fingerprint, client ID and session token together for each endpoint, keyed by trimmed address and port. Track the selected endpoint separately. Migrate an existing installation’s record under its saved endpoint and preserve its history associations. Make migration safe to repeat across app restarts. If an earlier failed switch already overwrote the original address, treat the pin’s origin as uncertain and provide an explicit recovery path for the affected endpoint that preserves conversations. Never infer ownership of a certificate from a failed connection.

### 1.2 Bind connection attempts to the selected endpoint

Status: complete

Update `LanSession.connect` and its reconnect and pairing paths to load the selected endpoint’s record. An unseen endpoint starts with empty credentials and follows the existing first-connection trust and pairing flow. A known endpoint must match its recorded certificate even when a pairing code is supplied. Commit pairing results only to the endpoint that completed the handshake. Ensure an old worker or delayed retry cannot apply credentials or connection state after a host switch.

## 2. Verify host switching and certificate enforcement

### 2.1 Exercise migration, switching and failure recovery

Status: complete

Verification on 22 November 2026 used the Android debug APK on an API 35 emulator. In Settings, two loopback TLS fixtures represented Linux and MacBook at the same address on different ports with independently generated certificates. The MacBook fixture rejected a wrong code and accepted the correct code. A third endpoint accepted an empty code. Switching back authenticated with the original Linux token. Redirecting the Linux port to the MacBook certificate produced “TLS pin mismatch.” even with a pairing code. Restoring the Linux certificate allowed authentication again. After a force-stop and cold launch, both listeners verified authentication using their own credentials.

JVM tests exercised migration and overwritten-address recovery with a saved Linux answer in a Room database. Reopening the database preserved the answer under the Linux identity and kept it out of the MacBook history. The pending-switch test delivered the old pairing reply during a port change. These scenarios ran outside the emulator. The desktop session test independently checked the optional-code policy, including rejection of a missing or wrong fingerprint and a typed wrong code.
