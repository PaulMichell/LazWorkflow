## 1. Overview

This plan acts on the review of commits `aab9ba0` to `5c6f036`, which added macOS (Cocoa) support. That work moved the conversation surface to paint straight onto the control canvas. It drew the smooth graph markers, ref cards and status pills at the screen's backing scale. It also guarded the settings connection list against Cocoa's re-entrant clicks, and ported the SIGPIPE handling to Darwin.

The review found one likely regression on Windows (flicker in the conversation view), some remaining Cocoa re-entry, a few small faults, and costly marker drawing on Retina screens.

Success criteria:

- The conversation view does not flicker on Windows and stays sharp on Retina.
- Choosing, adding or removing a connection loads it once on Cocoa.
- Scrolling the history graph on a Retina Mac is no slower than before the Cocoa work.
- All Mac fixes still build on Linux and Windows. Every test that passed before these changes still passes. Failures listed in `CLAUDE.md` are already known and are not counted.

Constraints: follow `Documents/free-pascal-engineer.md`. Commit each item on its own with an area prefix (`Styled text:`, `Settings:`, `Graphics:`, `Process:`). Commit only the files the item touches.

## 3. Drawing performance

### 3.1 Skip supersampling for pixels fully inside or outside a shape
Status: complete

On Retina, `DrawCoverageCircle` in `CanvasUtils.pas` processes 4× the pixels, at 64 samples each. Every sample runs `Sqrt` and `UnderColor` (which loops over the strokes). That is about a million samples per history repaint for 40 visible rows. `DrawSmoothRoundRect` now takes 4×4 samples per pixel, which costs 4× as much at 1x and 16× at 2x.

- In `DrawCoverageCircle`, compute the distance from each pixel's centre first. If the pixel is more than `0.7072 + SmoothCoverageWidth / 2` from both the outer and the inner edge, its coverage is the same throughout. Fully outside: write alpha 0. Fully inside the band: write the edge colour. Skip the sample loop.
- In `DrawSmoothRoundRect`, use the same test with `RoundRectDistance` at the pixel centre, against both the outer edge and the border's inner edge.
- Write pixels through a scanline or `TLazIntfImage.SetPixel`-style fast path, not the `Colors[]` setter. Do this only if it stays simple. Otherwise leave it.

Check: the rendered output must match the old output exactly. Add a small test, or extend an existing one if one covers `CanvasUtils`. The test should render a disk, a ring and a round rectangle at scales 1 and 2, both with and without the early skip, and compare the pixels. For timing, add a temporary log of the paint time for one history repaint. Keep any timing script under `Temporary/` and do not commit it.

### 3.2 Investigate blending markers by alpha and caching them
Status: complete

Now that markers are drawn from an 8-bit alpha bitmap, partial coverage could be written as the edge colour with `Alpha = coverage`, and the widgetset could composite it. That would remove the need to model the strokes underneath (`TSmoothStrokeArray`, `StrokesNear`). It would also let markers be cached by colour, radius, ring and scale, instead of building a bitmap per marker on every paint.

This is an investigation; decide before building it:

- Find out how LCL handles partial alpha on Win32 (`AlphaBlend` expects premultiplied pixels), GTK2, GTK3, Qt and Cocoa. The current code uses all-or-nothing alpha with RGB set to 0, which avoids the question.
- If every target widgetset composites straight alpha correctly, write a follow-up plan item for the change and the cache. If any does not, record that here and leave the stroke model in place.

Earlier findings (2026-11-17, from this repository only; no LCL source was read):

- Every marker goes through `BlitSmoothImage` (`CanvasUtils.pas`): `TBitmap.LoadFromIntfImage`, `Transparent := False`, then `Canvas.Draw` at 1x or `StretchDraw` at backing scale. So the question is how each widgetset's `StretchMaskBlt` (or equivalent) treats a 32-bit bitmap whose alpha is between 0 and 255, at 1x and when stretched.
- Commit `a22e1a8` chose binary alpha because "Cocoa premultiplies on upload, and a second multiply would darken partial-alpha edges". If Cocoa really premultiplies once, then straight alpha written by us would come out right there. That commit did not test it, so it still needs checking.
- Questions to answer in the LCL source: (1) Win32 `StretchMaskBlt`: does it premultiply a straight-alpha DIB before calling `AlphaBlend` with `AC_SRC_ALPHA`, or pass the pixels through unchanged? (2) GTK2: is an alpha bitmap drawn as a `GdkPixbuf` with full blending (straight alpha), or only through a 1-bit mask? (3) GTK3: does it convert straight alpha to Cairo's premultiplied ARGB32? (4) Qt5/Qt6: is the `QImage` format `ARGB32` (straight) or `ARGB32_Premultiplied`? (5) Cocoa: does `TCocoaBitmap` declare non-premultiplied data, or premultiply it on upload?
- A cache is only possible once the stroke model is gone, because the pre-blended fringe depends on the lane lines that cross each marker.

Findings from the LCL source (2026-11-18, `/home/paul/Projects/FreePascal/Lazarus/lcl`). The path checked is the one `BlitSmoothImage` takes. `TLazIntfImage.Create(0, 0, [riqfRGB, riqfAlpha])` asks the widgetset for its native 32-bit description with no mask, because `riqfMask` is absent (`include/intfbaselcl.inc` `RawImage_QueryDescription`). `TRasterImage.Draw` (`include/rasterimage.inc:232`) then calls `StretchMaskBlt` with mask 0, because the bitmap is not `Masked`, and with the canvas `CopyMode`, which is `SRCCOPY`.

1. Win32: correct. `StretchMaskBlt` (`interfaces/win32/win32winapi.inc:3697`) runs `CreatePremultipliedBitmap` on every call. That function copies the DIB, multiplies RGB by alpha for 0 < alpha < 255 and zeroes RGB at alpha 0. It then calls `AlphaBlend` with `AC_SRC_ALPHA`, both at 1x and stretched. The premultiplied copy is made on every blit, so a cache still pays one `GetBitmapBytes` and `CreateDIBitmap` per draw on Windows.
2. GTK2: correct, with one condition. `RawImage_CreateBitmaps` (`interfaces/gtk2/gtk2lclintf.inc:296`) stores a 32-bit image as an RGBA `GdkPixbuf` with alpha. When the bitmap is first selected into its canvas DC, `TGtkDeviceContext.SelectBitmap` (`gtk2devicecontext.inc:1028`) keeps that pixbuf on the DC. `StretchCopyArea` (`gtk2widgetset.inc:4156`) then draws it with `gdk_draw_pixbuf`, which blends straight alpha fully. When stretched, it first scales with `gdk_pixbuf_scale_simple(GDK_INTERP_HYPER)`. The condition: `SelectBitmap` also turns the GDI object into a pixmap with a 1-bit mask thresholded at `$80` (`gdk_pixbuf_render_pixmap_and_mask`), and the variant record loses the pixbuf pointer. If the bitmap's canvas DC is ever freed and made again, through `FreeCanvasContext` (for example after setting `Transparent`, `BeginUpdate`/`EndUpdate` or a new handle), later draws use the binary mask. Today every marker gets a new bitmap, so it always takes the pixbuf path. A cache must keep each bitmap's canvas DC alive and never change the bitmap after its first draw.
3. GTK3: correct. `TGtk3DeviceContext.SetImage` (`interfaces/gtk3/gtk3objects.pas:4538`) paints the straight-alpha RGBA pixbuf into a `CAIRO_FORMAT_ARGB32` surface with `gdk_cairo_set_source_pixbuf`, which premultiplies. `StretchMaskBlt` (`gtk3winapi.inc:5837`) draws that surface with the Cairo `OVER` operator.
4. Qt5/Qt6: correct. `RawImage_CreateBitmaps` (`interfaces/qt5/qtlclintf.inc:643`, the same in `qt6`) uses straight `QImageFormat_ARGB32`, and `QPainter` composites it correctly. The one exception is macOS when the raw image carries a mask. Then the format is declared `ARGB32_Premultiplied` although the data is straight, and partial alpha would come out wrong. Our image has no mask, so it is not affected. Keep it that way.
5. Cocoa: correct. The standard description is `$AARRGGBB` (`cocoautils.pas:1044`), which maps to `cbtARGB`. `TCocoaBitmap.Create` copies the data, and `CreateHandle` calls `PreMultiplyAlpha` exactly once (`cocoagdiobjects.pas:1544`, `1658`). The `NSBitmapImageRep` is then declared premultiplied, which matches. So the premise of `a22e1a8` does not hold: straight alpha written by us is multiplied once, not twice. A second multiply would only happen if we wrote premultiplied data. One trap: `PreMultiplyAlpha` skips `cbtBGRA` and `cbtABGR`, which it byte-swaps but does not multiply. An image built from a non-native BGRA description would therefore be wrong on Cocoa. Keep using the queried native description.

Decision: every target widgetset composites straight alpha correctly on this path, so the stroke model can go. The follow-up is item 3.4. The GTK2 DC lifetime, the Win32 copy per blit and the two macOS traps are carried into it as constraints.

### 3.3 Turn off SIGPIPE per pipe on macOS
Status: complete

`WritePipeNoSignal` in `Source/LazWorkflowCommon/ProcessSession.pas` makes four or five signal system calls on every write. macOS 10.13 and later supports `fcntl(fd, F_SETNOSIGPIPE, 1)`, where `F_SETNOSIGPIPE = 73`. After that, `write` returns `EPIPE` without raising SIGPIPE.

- Where the session creates the pipe it writes to the child's stdin, set `F_SETNOSIGPIPE` on the write end under `{$IFDEF DARWIN}`.
- In `WritePipeNoSignal`, use a plain `fpWrite` on Darwin when the flag was set. Keep the current mask-and-`sigwait` path as the fallback if `fcntl` fails, and for handles the session did not create.
- Leave the Linux and other Unix paths unchanged.

Check: build with the test runner on Linux. The Darwin path needs a Mac build (item 4.1).
