# Opus Improvements

How to make plan runs on Opus finish items instead of leaving them blocked, and how to cut the tokens they use. The evidence comes from the plan run on `Documents/Plan-20261105-130659.md` (items 3.2 to 3.6), on 2026-11-06.

## 1. Why items end as blocked

Each item from 3.2 onwards ended as `blocked`, with a User action that asks you to build, test or commit. There are four causes. Two of them are settings that can be changed today.

### 1.1 The build tool has nothing to build

Every `start_build` call failed with:

> Build input is missing or not a regular file: /home/paul/Projects/LazWorkflow

The selected target is the repository folder, not a `.lpi` or `.lpk` file. So the assistant could not compile anything. The plan says "Each commit compiles on its own", and the run instructions say a clean compile does not complete an item. With no compile possible, the honest status was `blocked`.

**Change:** make the target a buildable file, for example `Packages/LazAssistantMonitor.lpk` for this plan, or a test project. Then `start_build` works, and the assistant can fix its own compile errors before it commits.

### 1.2 No configured tests and no shell

Opus has no shell in this harness. The only way it can run a test is `start_tests`, and that runs only the command set in **Settings → Target tests**. None was set, so no test could run. Every acceptance check that says "the test passes" stayed open.

**Change:** set Target tests to the runner, with the test list for the current plan, for example:

```sh
instantfpc Tests/RunAssistantTests.pas --lazarus-root /home/paul/Projects/FreePascal/Lazarus \
  --only AssistantMonitorMirrorTest --only AssistantMonitorSessionTest --only AssistantMonitorLinkTest \
  --output-dir /tmp/laz-plan-tests
```

If Grok's runs had a shell, or a test command, that alone would explain much of the difference in completed items. Check which tools each model is given in Build mode.

### 1.3 Uncommitted work from early items blocks every later item

Items 2.1 to 2.4 left edits that were saved but neither compiled nor committed, in shared files:

- `AssistantMonitorSession.pas`
- `AssistantMonitorSync.pas`
- `AssistantMonitorBridge.pas`
- `AssistantMonitorMirror.pas`
- `AssistantMonitorFrames.pas`
- the mirror and session tests
- `RunAssistantTests.pas`

The git tool stages whole files only (`add -- path`). So any later item that touches one of these files cannot be committed by itself. Committing it would also commit the earlier, unverified work. That happened to 3.2, to the session half of 3.3, to the runner registration for 3.4, and to 3.6. One stalled item spreads to every item after it that shares a file.

**Changes, from most to least effective:**

1. Commit the open 2.x work now, once 1.1 and 1.2 let you verify it. This unblocks 3.2, 3.3, 3.4 and 3.6 together.
2. Let the git tool stage part of a file. For example, allow `apply --cached` with a patch the assistant writes, or `add -p` driven by a patch. Then each item can be committed on its own even when files overlap.
3. Write the rule into the plan header: an item must be committed before the next item that edits the same file starts. If an item cannot be committed, the run stops and does not go on to the next item.

### 1.4 A decision is needed: commit without a compile, or stop

This run was not consistent. Item 3.1 (in an earlier session), and the link half of 3.3, 3.4 and 3.5 were committed without a compile, because those files were clean. Items 3.2, 3.6 and the session half of 3.3 were not. Every item was still marked `blocked`, because nothing was compiled or tested. The memory note *plan-status-runner-order* asks for `blocked` with a User action when an item waits on a person, so that is the intended outcome. Without a working build, though, it means every item stops.

**Change:** add one line to the plan header or to `CLAUDE.md` that sets the policy. Either:

- "If the build tool is unavailable, commit the change, mark the item `complete`, and list the checks still owed." This finishes more items, but the build is checked later.
- or "If the build tool is unavailable, stop the run and say so." This stops early instead of producing a row of blocked items.

Both are better than the current mix.

### 1.5 Large source files cannot be edited safely

The Lazarus tools can change a source file only by replacing the whole buffer. For `AssistantMonitorSession.pas` (3,300 lines, about 100 KB, with uncommitted 2.x edits), the assistant chose not to retype the whole file. With no compiler to catch a slip, that was too risky. This left the session half of 3.3 undone.

**Change:** add an exact-text replace tool for source buffers, like `update_markdown` but for `.pas` and `.lfm` files. It would take the old text and the new text, and fail if the old text is missing or appears more than once. This is also the largest token saving (see 2.1).

## 2. Why the runs use so many tokens

These are the main costs in this run, largest first.

### 2.1 Every edit sends the whole file three times

To change a few lines, the assistant has to:

1. read the whole buffer (`read_buffer` or `open_buffer`);
2. send the whole new text (`replace_buffer`);
3. receive the whole new text back, because `replace_buffer` echoes it.

Sizes in this run:

| File | Size | Lines changed |
|---|---|---|
| `AssistantMonitorLink.pas` | 30 KB | about 60 |
| `AssistantMonitorLan.pas` | 31 KB | 26 |
| `AssistantMonitorForm.pas` | 16 KB | 10 |
| `AssistantMonitorBridge.pas` | 47 KB | about 20 |
| `AssistantMonitorMirror.pas` | 42 KB | about 40 |

The Bridge echo, at 50 KB, was too large for the tool result to display. Roughly 95% of the tokens for each edit were file text that did not change.

**Changes:**

- Add the exact-text replace tool from 1.5. A 20-line change then costs about 20 lines.
- Make `replace_buffer` and `apply_changes` return the revision and a short diff summary, not the full text.
- Let `open_buffer` return a revision without the text, for callers that have already read the file with `read_file` line ranges.

### 2.2 The conversation keeps growing from item to item

Each plan item arrived as a new message in the same conversation. Every file dump, grep result and diff from the earlier items stayed in the context and was paid for again on each later call. By 3.6, every tool call carried the full text of Link, Lan, Form, Mirror, the runner and the plan.

**Change:** start each plan item in a fresh conversation, or have the Run Plan driver compact the conversation between items. The item prompt already carries everything the next item needs: the plan section, the file paths and the rules.

### 2.3 The plan file is long and gets longer

The plan was 522 lines when this run started. Each finished item added a long *Done* block, so the plan the next item reads is bigger. Both the full-plan reads and the item prompt pay for it.

**Changes:**

- Read only the active `###` section. Add a `read_markdown_section` tool, or use `read_file` with a line range.
- Keep item notes short in the plan, for example one line with the commit hash and the checks still owed. Put the long reasoning in the commit message, where it already is.

### 2.4 Effort and thinking level

Opus thinks before it answers, and much of this plan is routine: guards, locks, ordering, small tests. A lower effort setting for the routine items, with higher effort kept for the design items (5.x, 6.7, 6.8), would cut tokens with little loss of quality.

### 2.5 Fixed cost at the start of every item

Each item pays the same fixed cost before any work: the system prompt, the tool schemas, `CLAUDE.md`, the memory index, and the first part of the 57 KB `free-pascal-engineer.md`.

**Changes:**

- Keep a one-page summary of the house rules and link it from `CLAUDE.md`, so the full skill file is read only when it is needed.
- Remove tools that Build mode never uses during a plan run, to shorten the tool list.

### 2.6 Smaller costs

- Searches with no limit returned many lines that were not needed, for example 20 KB of `.State` matches. Set `head_limit`, or search one file.
- Full diffs were read to check that a change was clean. `git diff --stat` and then a diff of the one hunk would do.

## 3. Comparison with Grok

This report has no Grok session to measure against, so these points are likely causes, not measured ones:

- **Tools:** a shell or a configured test command for Grok would explain the difference in finished items (1.1 and 1.2).
- **Per-token price and output length:** Grok may cost less per token and write shorter output. Opus wrote long plan notes and long commit bodies, as the house rules ask.
- **Thinking:** Opus thinks before each answer, and those tokens are counted (2.4).
- **Context:** if Grok's runs start each item fresh, or keep less context, they avoid the growth described in 2.2.

To compare like for like, run one plan item on each model from a fresh conversation, with the same tool set and the same Target tests, and record the tokens in and out.

## 4. Suggested order

1. Set the build target to the package and set Target tests (1.1 and 1.2). With these, the assistant can verify its own work.
2. Commit the open 2.x work, then rerun the blocked 3.x items (1.3).
3. Choose the commit-without-compile policy (1.4).
4. Add the exact-text replace tool, and stop the full-text echoes (1.5 and 2.1). This gives the largest token saving and removes the risk of editing big files.
5. Start a fresh context for each item and read only the item's section (2.2 and 2.3).
6. Lower the effort setting for routine items (2.4).
