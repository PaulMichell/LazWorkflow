# Improve status bar centring and readability

Generated by Lazarus Project Assistant.

Improve the LazWorkflow Project Assistant status footer so its items form a balanced, readable line at normal and narrow window widths. Centre the complete visible middle group, align all items vertically, and keep changing status messages from crowding neighbouring text.

This plan is based on source inspection. Implementation and visual verification remain to be done in Build mode.

## 1. Current layout and intended result

The shared footer lives in `Source/LazWorkflowCommon/StatusFooterFrame.pas` and `StatusFooterFrame.lfm`. It is used by Project Assistant, Manage Repository, and the Markdown viewer.

Observed in the current source:

- `LayoutCentrePair` centres `ModelLabel` against the whole footer, then appends `CentreLabel` and optional `UsageLabel` to its right. The complete group is consequently weighted to the right until it is forced left by the available-space clamp.
- The layout always reserves a 16-pixel scaled gap after the model, even when the model caption is empty. This also affects the other windows, which use `SetAll` without a model caption.
- Labels autosize to their full captions. Clamping the starting position does not make an over-wide group fit, and unrestricted left/right captions can consume the middle area.
- The frame has a fixed scaled height of 22 pixels. Side labels fill that height while middle labels receive individual vertical positions.
- `ProjectAssistantForm.RefreshCentreStatus` currently combines context and account allowance in `CentreLabel`, deliberately leaving `UsageLabel` hidden. Keep this single presentation of the account figures.

The intended on-screen order, left to right, is optional left information and skills; a centred model/settings and context/allowance group; then session or activity status at the right edge. In repository and Markdown windows, their existing left, centre, and right meanings remain intact.

## 3. Keep long and changing captions readable

### 3.1 Bound text and handle narrow widths
Status: not started

Measure captions using each label's actual font. Give left and right groups content-sized widths with limits so long paths, skill lists, or work messages cannot consume the entire footer. Start with maximum allocations of one quarter of the usable width for the left group and one third for the right; the middle group receives the remaining space after gaps. Unused side space stays available to the middle group.

Within the assistant's middle group, preserve the short context/allowance figure where possible and shorten the longer model/settings caption first. If the context/allowance caption itself exceeds the available width, truncate it visibly too. Keep the row single-line and never use overlapping labels or smaller text as a fallback.

Use a visible ellipsis for truncated text, with Unicode-safe measurement and shortening. Prefer middle ellipsis for paths and end ellipsis for prose. Retain the complete original caption separately from its displayed form so resizing wider restores it correctly.

Provide the complete value in the hover hint without losing existing explanatory hints. Keep clickable regions within the displayed label's bounds, and keep the optional `UsageLabel` hover-only. Hidden and empty items consume no space.

Reserve enough right-side width for representative elapsed-time text during an active phase so each timer tick does not repeatedly move the centre group. Recalculate only when text metrics, visibility, font, scale, or available width require it.

Acceptance: long model names, paths, skill captions, and work messages remain distinguishable; truncation is obvious; full values remain available on hover; resizing restores full captions; ordinary elapsed-time updates do not make the layout jump.
