# Assistant recovery and plan reports

Generated by Lazarus Project Assistant.

The assistant stops too often, and a stopped plan does not say what the user must do next. This plan keeps a turn alive when the fault is recoverable, says so in the conversation, and ends every Run Plan with a status report.

Four failures are in the current code:

- An access violation or other exception still ends the turn. `TAssistantActor.Execute` posts the exception and finishes. `TIdeToolDispatch.ExecuteOnMain` logs it and does not retry. A fault before `FDone` is set becomes a timeout. The IDE may survive; the task does not.
- Connection loss retries only when `IsTransientNetworkError` matches a fixed phrase list. The wait is a hard-coded 30 seconds in `WaitForReconnect`. Credit and quota failures are not in that list, so they finish the turn. `AssistantReconnectTest` already expects socket errors to retry without a cap, and HTTP 401 to fail once.
- A completed model reply with no tool call, an empty reply, `response.incomplete`, or the tool-round cap all return Ready. The cap text tells the user to send a follow-up. Nothing sends that follow-up.
- A plan item with no `Validation:` line is marked blocked and `StopRunPlan` ends the whole run. The note says to add evidence or set the item in progress. It does not say what evidence. If only blocked items remain, the runner says the packages are complete.

Recovery notes are always shown. They are not a setting. Intervals and retry counts are settings.

Assumption: a mutating tool (write, replace, git, compile) is not replayed after an exception. The HTTP round is safe to replay because `DoHttpRound` already discards the partial stream. A tool fault is returned to the model so the turn continues. Read-only tools may be retried once inside that cap.

## 1. Recovery policy

### 1.1 Classify a fault before the turn ends
Status: complete

Add `AssistantRecovery`. It owns the decision. `AssistantActor` and `ProjectAssistantForm` call it. Do not grow those units with the policy text.

Classify each fault as one of:

- Ignore: cancel, a callback after detach, or a paint and layout failure that does not own the turn.
- Retry the last action: one HTTP round, or one read-only tool, when the attempt is still inside the fault-retry cap.
- Continue the turn: a tool fault, including an access violation inside `ExecuteAssistantToolForMode`. Return a tool error that names the class and the area. Do not replay a write, replace, git, or compile.
- Stop: the same site is already over the cap, the service is gone, the user pressed Stop, HTTP 401, or a malformed request that is not a disconnect.

`ReportPluginException` stays the log. It is not the user report.

### 1.2 Keep the turn alive unless the fault is terminal
Status: complete

`TAssistantActor.Execute` must not finish the turn on the first access violation. The site that failed applies the classification from item 1.1.

`TIdeToolDispatch.ExecuteOnMain` must set `FDone` and a non-empty error on every exception path, including a fault before the inner tool call. The waiter must not sit until timeout and then abandon a dispatch that already failed.

A terminal stop uses one conversation note: the area, the exception class, the message, and that the task has stopped. No partial tool recipe and no second retry after that note.

### 1.3 Report every recovery in the conversation
Status: not started

Each ignore, retry, or continue posts one system note before the next attempt. The note names the fault and the resolution, for example a retry of the HTTP round, a tool error handed back to the model, or a paint fault that was ignored.

The status phase uses the same sentence. Add those phrases to `IsAssistantProgressStatus` so a late snapshot cannot be stored as `**Error:**`.

One note per wait or retry. Do not post on the 50 ms poll.

## 2. Connection loss and credits

### 2.1 Retry a lost connection until Stop
Status: not started

Keep the loop in `DoHttpRound`. Widen `IsTransientNetworkError` to cover HTTP 502, 503, and 504, an empty socket close, and the disconnect phrases the HTTPS layer already returns. HTTP 401 stays a single attempt, as `AssistantReconnectTest` requires.

`WaitForReconnect` stays a virtual method with no arguments so the existing test override still compiles. `DoHttpRound` sets a wait field before the call. The default wait is 30 seconds, taken from the setting in item 5.1, snapshotted when the turn starts.

There is no attempt cap for a lost connection. Stop still interrupts the wait, as the current cancel test requires.

Post one conversation note when the wait starts, and one when the call resumes.

### 2.2 Wait out of credits until reset, or one hour
Status: not started

Do not use the 30 second interval for a credit failure.

Treat the call as out of credits when the status is 402, or when the status or body says credits, quota, spending, billing, or insufficient credit. A short 429 rate limit is not that case: wait for `Retry-After` when the header is present, otherwise use the connection interval.

Read a reset time from the error JSON (`resets_at`, `reset_at`, `retry_after`), from `Retry-After` when it is a future time, and from the last account-usage snapshot. `TAccountUsageSnapshot` has no reset field today. Add `ResetsAt` and `HasReset` there, filled by the parsers that already read `resetsAt` and the Grok billing window. Do not scrape the hint text.

If the reset is in the future, wait until that time, then retry. Say the clock time in the conversation note. If there is no reset, wait the credit interval from item 5.1, default 60 minutes, then retry. Repeat until the call succeeds or the user presses Stop.

A credit wait must not reach `FinishAssistantReply` and must not `StopRunPlan`.

### 2.3 Use the same wait for a dropped Codex or Claude transport
Status: not started

When a Codex or Claude run ends with a transport or credit error and no assistant answer, do not call `FinishAssistantReply` immediately. Classify it with the same unit and wait as in items 2.1 and 2.2, then retry the turn. Do not change the Codex protocol.

## 3. Unfinished turns

### 3.1 Detect a premature Ready
Status: not started

Before Ready, decide from structure, not from a guess about the prose:

- `response.incomplete`, or chat `finish_reason` `length`, is a truncated reply, not a turn error.
- The tool-round cap is an unfinished turn. Remove the sentence that tells the user to send a follow-up.
- An empty assistant reply after a tool round is unfinished.
- A short explicit deferral ("I can continue if you want", "let me know if you want me to continue", "should I proceed") is unfinished.
- A plan item still in progress, and not blocked with a user action, is unfinished.

A normal reply that has text, is not truncated, and does not defer, is finished. Do not continue it just because it is short.

### 3.2 Continue automatically
Status: not started

On an unfinished turn, inject a continuation in the same conversation, up to the cap from item 5.1, default 3. The continuation says to resume from the last tool results and not to stop until the task is done or a real block is written.

Each continuation is a system note: what stopped, that the assistant is resuming, and the attempt number against the cap.

Do not continue after Stop, after a terminal fault, or after a blocked item that already has a user action.

When the cap is reached, return Ready and say that automatic continuation stopped, and what remains.

### 3.3 Always leave a final summary
Status: not started

When a turn is legitimately finished and the assistant text is empty, build a short summary from the trace: what was asked, which tools ran, and the outcome. Show that text as the assistant message before Ready.

If the model already wrote a summary, keep it. Do not add a second summary.

`RecordCurrentTurn` must not store a successful turn with an empty response.

## 4. Plan runner and blocked items

### 4.1 Do not block an item that lacks a Validation line
Status: not started

`TryAutoCompleteBuildWork` must not mark an item blocked, and must not call `StopRunPlan`, only because `Validation: build` or `Validation: tests` is missing. The work prompt already says a missing Validation line does not block the status change.

Leave the item in progress and let item 3.2 continue it. `CheckAssistantAcceptance` may still report the human-review reason. The runner must not treat that reason as a block.

A failed build or a missing Git commit also stays in progress. Report the reason. Do not mark the item blocked.

### 4.2 Write a user action on every real block
Status: not started

Block only when a person must act:

- `Validation: manual`
- the model set Status to blocked
- unchecked acceptance items remain after the continuation cap

Write a `User action:` line in the item body, immediately after the Status line, in the same edit that sets blocked. Use these sentences, with the item title filled in:

- Manual validation: review the item; if it is acceptable set Status to complete; if more work is required set Status to in progress and run Run Plan again.
- Unchecked items: tick the unchecked acceptance items, or remove the ones that do not apply; then set Status to in progress and run Run Plan again.
- Model block with no action line: the item is blocked and no action was written; open the plan, add what you need to supply, set Status to in progress, and run Run Plan again.

If the model wrote a `User action:` line, keep that line and quote it in the report.

### 4.3 Continue the rest of the plan after a block
Status: not started

A blocked item is skipped, as `FindNextIncompleteBuildSection` already does. It must not stop the run. Remove the `StopRunPlan` call on the human-review path.

The run still stops for a terminal fault, Stop, the package cap, or context at or above 95 percent after compact. It does not stop merely because one item is blocked.

### 4.4 Report plan status at the end of every Run Plan
Status: not started

Every exit from Run Plan posts one conversation report. That includes a clean finish, a user stop, an error, the package cap, and the context limit.

The report has:

- the counts already shown on the plan list: not started, in progress, blocked, complete
- why the run ended
- each blocked item, with its stored user action
- if items remain in progress or not started, the next step, which is Run Plan again unless a terminal fault says otherwise

Do not say that all packages are complete when a blocked item remains. The start dialog must not say that either when the only remaining items are blocked. Say that blocked items need the listed actions, and that no unblocked item is left.

## 5. Settings

### 5.1 Add the recovery controls
Status: not started

On the General page, add a Recovery group between Context and Skills. Stream it in `AssistantSettingsForm.lfm`. Skills stays the client-aligned group. On screen the order is Transcript, Prompt, Context, Recovery, then Skills.

Four edits, with these defaults:

- Reconnect interval, seconds, default 30
- Credit retry when the reset time is unknown, minutes, default 60
- Automatic continuations per task, default 3
- Fault retries per action, default 1

Store them on `TAssistantConfig` beside `auto_compact_context`. Missing keys load the defaults. Snapshot the values onto the actor when the turn starts. Do not read the form from the worker.

Recovery notes stay on. There is no checkbox to hide them.

## 6. Tests

### 6.1 Cover the new decisions without a live server
Status: not started

Extend `Tests/AssistantReconnectTest.lpr`. A socket error still retries with no cap. HTTP 401 still fails once. HTTP 503 retries. A credit body with a future reset waits until that time. A credit body with no reset uses the hourly interval. Stop still interrupts the wait.

Add decision tests for the continuation rules in item 3.1 and for the end-of-run report in item 4.4. An empty successful turn is not stored. A missing Validation line does not produce a blocked status. A manual Validation line produces a `User action:` line and does not stop a later not-started item.

Load and save the four settings keys. A missing key keeps the default.

Run the reconnect test and the acceptance test. The acceptance predicates may stay. The runner behaviour must match item 4.1.
