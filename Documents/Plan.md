# Image output for capable models

Generated by Lazarus Project Assistant.

The assistant can show a project image with `read_image`, but it cannot create one. `write_file` is text only, and image extensions are refused there. A model that can generate pixels has no way to save them into the project. This plan adds that path as a generic capability, switched on for a model profile, never by model name.

This work belongs in the Project Assistant host (LazWorkflow / LazAssistantTools). Ecology Survey Scheduler is only where this plan is stored. Do not add image-generation code to the scheduler.

The previous text in this file was the calendar Allow Edits plan. Restore that document from version control if that work is still open. It is not part of this plan.

## 1. Capability, not a model name

Image writing stays off unless the selected model profile says it can generate images. A preset may set that flag for a known model. The turn loop, the tool list, and the prompt read the flag. They do not branch on a vendor or a model id.

A capable model delivers pixels in one of two ways, stored on the profile as data: a response image part, or a tool prompt that calls that same model's image endpoint. The host writes those bytes. It does not draw a substitute and it does not call a different image service.

### 1.1 Add an ImageOutput flag to the model profile
Status: complete

Store a boolean on the model profile, default false, plus the delivery mode (response part or tool prompt). Settings shows a "Can generate images" control for the selected profile. Turning it on must not select an image product other than the current model. Confirm the profile record and settings form in LazWorkflow before editing them.

### 1.2 Rebuild the tool list and prompt from the flag
Status: complete

On each turn, if ImageOutput is false, omit `write_image` and omit any line that says the model can create image files. If it is true, register the tool and add the short image-output prompt section. Switching model mid-conversation takes effect on the next turn. Plan mode and Document mode never register the tool, even when the flag is on, because those modes do not write files.

### 1.3 Keep provider differences behind one adapter record
Status: not started

Define a provider-neutral generated-image record: bytes, MIME type, width, height, and a turn-local id. Each provider adapter fills that record from its own response. The writer, the path checks, and the tool result use only that record. Adding another capable model is a new adapter plus the flag, not a new tool.

## 2. write_image

One tool name for every capable model. Extra parameters follow the profile's delivery mode. A text description is never saved as a file.

### 2.1 Register write_image only for a capable model in a writing mode
Status: not started

Tool name `write_image`. Required `path` is project-relative. Response-part mode also takes the turn-local image id, optional when the turn has exactly one image. Tool-prompt mode also takes a `prompt` and an optional pixel size, and the adapter calls the selected model's own image endpoint. An incapable model has no such tool, so a hallucinated call is an unknown tool and writes nothing.

### 2.2 Validate the path and the bytes before writing
Status: not started

Reuse the `read_image` sandbox: the resolved path must stay inside the project root, and a symlink that leaves the project is refused. Allow only png, jpg, jpeg, webp, and gif, and require the magic bytes to match the extension. Enforce the same size ceiling as `read_image`. Refuse `.git`, `.assistant`, and build-output paths. If the file already exists, write only when `overwrite` is true. A missing image part, a failed provider call, or a failed check returns an error and creates no file.

### 2.3 Return a result the model must trust
Status: not started

On success return the project-relative path, byte size, width, height, and MIME type. Same honesty rule as `write_file`: the model must not claim the file exists unless this result says the write succeeded. A later `read_image` of that path must show the same bytes.

## 3. Prompt rules

### 3.1 Tell capable models how to save an image
Status: not started

When the flag is on, the prompt says: create still images only with `write_image`; do not use `write_file` or `replace_in_file` for images; prefer PNG for icons and UI art unless the user names another format; pass the generated image through rather than describing a file that was not written.

### 3.2 Tell other models they cannot create image files
Status: not started

When the flag is off, one prompt line: this model cannot write image files; say so, and do not invent a path or a PNG. `write_file` keeps rejecting image extensions in every mode, so a text model cannot smuggle a binary through the text writer.

## 4. Verification

### 4.1 Cover the flag, both delivery modes, and the sandbox
Status: not started

Fixture tests, with no live provider. Flag off: `write_image` is absent and an attempted call fails. Flag on, response part: a fixture PNG and a path create the file. Flag on, tool prompt: a mock adapter returns bytes and the writer saves them, with no network. Refuse path escape, a symlink out of the project, bad magic bytes, overwrite without the flag, and any call in Plan or Document mode. Two adapters must share one writer, and the writer source must not name a provider.

### 4.2 Check a capable model and an incapable model by hand
Status: not started

With the flag on, ask for a PNG icon and confirm the file is a real PNG at the requested project path and that `read_image` shows it. With the flag off, confirm the tool is not offered and the model does not claim a file was written.
