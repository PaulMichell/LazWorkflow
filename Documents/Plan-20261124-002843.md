## 1. What was reviewed

## 2. Bugs

### 2.1 Require a revision and a unique match on native edits
Status: complete

`write_file` and `replace_in_file` tell the model that an existing buffer needs the revision from `read_file`, and that `old_text` must be unique unless `replace_all` is set. The native bodies do not enforce either rule.

`ToolWriteFile` never reads `revision`. `SaveProjectFileText` passes the editor's current text as the expected text, so the check inside `ApplyAssistantEditorText` always succeeds. A write composed from an older read overwrites whatever the user has typed since. A file that is not open is truncated with `fmCreate` the same way.

`ToolReplaceInFile` loads the current buffer, then replaces the first `Pos` hit. It does not count matches. The broker's `ApplyExactReplace` already returns `old_text occurs more than once; set replace_all to replace every match.` The native path should use that function, not a second replace loop.

Grok reaches these bodies through `ExecuteAssistantToolForMode`. ChatGPT reaches them through `DispatchAssistantTool`. Both miss the broker's snapshot check.

Acceptance:

- An existing open editor, or an existing file on disk, is refused when `revision` is missing or does not match the text last read for that path.
- A new file may still be created with an empty revision, matching the broker's create path.
- `replace_in_file` with `replace_all` false fails when `old_text` occurs more than once, and changes nothing.
- The broker's messages stay as they are. Do not add a native-only wording.
- Cover both with a headless test that does not need the IDE form. `AssistantEditorEditsTest` remains the broker test; do not bend it to excuse the native path.

### 2.2 Send ChatGPT tool calls through the same gate as Grok
Status: complete

`TAssistantCodexRun.ServiceOneTool` approves, then calls `DispatchAssistantTool`. It never calls `ExecuteAssistantToolForMode`. The comment says there is one executor. The gate in front of that executor is skipped.

Skipped checks that the Grok path still runs:

- `ToolAllowedInMode`. A hallucinated `run_compile` in Inspect still compiles if the name is known.
- The `write_image` offer check. A call is executed even when this connection was not offered image output.
- `MarkdownEditorToolRefused`. `write_file` and `replace_in_file` on a `.md` path are supposed to fail so the plan goes through `write_markdown` or `update_markdown`. ChatGPT can write the plan file as an ordinary source edit and skip plan registration.
- `CheckTarget` before the dialog, and the second check after approval if the package or project identity changed.

`SaveProjectFileText` still applies `AllowsWrite` and the binary-extension refusal, so this is not a total sandbox bypass. It is a mode and plan-file bypass.

Acceptance:

- After a successful Ask, ChatGPT calls `ExecuteAssistantToolForMode` with `SkipApproval` true. Do not show a second dialog.
- Inspect cannot run `run_compile`, `write_file`, or `delete_path` even if the model names them.
- A `.md` path is refused by `write_file` and `replace_in_file` on ChatGPT, with the same sentence Grok already returns.
- A package target still refuses `add_unit_to_project` before any write.
- Add a unit test on `QueueToolForTest` for the Inspect refusal and the Markdown refusal. Do not require a live Codex process.

### 2.3 Show write_file content in the ChatGPT approval summary
Status: complete

`CodexToolApprovalSummary` reads `path`, `old_text`, `new_text`, and `text`. It does not read `content`. `write_file` and `write_markdown` send the body in `content`.

`MCPApprovalSummary` then sees an empty new text. When the path is present and both sides are empty it reports `change` as `no change`. Ask mode asks the user to allow a write that the dialog describes as a no-op, and the phone waiter receives that summary too.

`replace_in_file` and `update_markdown` are not affected: they use `old_text` and `new_text`.

Acceptance:

- The summary treats `content` as the new text when `new_text` and `text` are empty.
- A `write_file` of a non-empty body does not display `no change`.
- The snippet stays bounded by the existing 100-character cap. Do not put the whole file in the dialog.
- A small test feeds `{"path":"Unit.pas","content":"program x;"}` through `CodexToolApprovalSummary` and asserts the change text is not `no change`.

### 2.4 Keep editor reads on the IDE thread
Status: complete

`grep` and `search_in_project` leave `IdeThread` false. `TAssistantActor.RunOneTool` then runs them on the worker. `ToolSearchInProject` calls `SourceEditorManagerIntf` and `FindOpenEditor` so unsaved buffers win over disk. That is an LCL object used off the IDE thread.

ChatGPT and Claude are safe today: Codex services tools from the IDE timer, and the broker rejects a call whose thread is not `FOwner`. Grok is the broken path. `grep` is in the Plan and Inspect catalogues, so this is a normal Inspect question, not a rare tool.

`read_file` is already `IdeThread`. `list_directory` and `read_image` do not touch the editor manager. Leave those on the worker unless a later read shows they mutate a structure the UI also reads.

Acceptance:

- A Grok `grep` or `search_in_project` never touches `SourceEditorManagerIntf` on the worker.
- Unsaved editor text is still preferred over disk. The overlay can be a short IDE-thread pass after the disk walk; do not mark the whole 8-second walk `IdeThread` if the overlay can be separated.
- If the overlay split is not done in this item, set `IdeThread` true as the correctness fix and leave the walk cost to item 4.1. Say which choice was made in the commit body.
- A worker-thread test is enough if it can assert the dispatch choice from `AssistantToolNeedsIdeThread`. An IDE-thread test of the overlay is optional.

### 2.5 Do not hide source that lives in a folder named lib or units
Status: complete

`IsSkippedSearchDirectory` skips any directory named `lib`, `units`, `backup`, or `temporary`, plus VCS and `node_modules`. The match is the folder name, not the project's unit-output directory. A project that keeps Pascal source in `lib` or `units` is invisible to `grep` and `search_in_project`. LazWorkflow's own `Lib/` output should still be skipped. So should `.git`, `.svn`, `.hg`, `node_modules`, and `__pycache__`.

Acceptance:

- Skip the active project's configured unit-output directory when that path is known.
- When it is not known, skip a `lib` or `units` directory only if it contains no searchable source (no `.pas`, `.pp`, `.inc`, `.lfm`, `.lpr`).
- Keep skipping VCS metadata, `node_modules`, and `__pycache__`.
- A fixture with `lib/Helper.pas` is returned by search. A fixture whose `lib/` contains only `*.ppu` and `*.o` is not walked file by file.
- `backup` and `temporary` may stay skipped. They are local copies, not source trees. Do not special-case this repository's folder names in the matcher.

### 2.6 Report add_to_project failure as a failure
Status: complete

`ToolWriteFile` sets `Result` true after the file is saved, then appends `(add_to_project failed: …)` if `CreateProjectFile` raises. The model is told the tool succeeded and will not retry the project registration. The unit is on disk and missing from the `.lpi`.

Acceptance:

- The file write still stands. Do not delete a file that was just created because project registration failed.
- `Result` is false when registration was requested and failed, and `ErrorText` says the file was written and the project was not updated.
- An already-registered unit still returns success with `Already in project.`
- A non-Pascal path, or `add_to_project` false, is unchanged.

### 3.3 Build the tool table once so a new row cannot be dropped
Status: not started

`ToolAt` is a case on a magic index. `TableCount` is a separate constant, currently 42. `FindAssistantToolSpec` rebuilds every preceding row, including its long description strings, on every lookup. `RenderAssistantToolNames` does that once per offered name, and each lookup starts again at index 0.

A new case added past `TableCount` is invisible. A gap leaves a blank name that the renderer skips. `SpecCount` existed only to return `TableCount`, and nothing called it.

Acceptance:

- Lookup is by name, case-sensitive, matching today's `Spec.Name = Name` comparison. Do not change catalogue spelling.
- Adding a row does not require a second count constant.
- Rendered JSON for Inspect, Plan, and Build is unchanged. Compare a saved catalogue fixture before and after, for both `twkOpenAI` and `twkCodex`.

## 4. Optimisations

### 4.1 Search file text without building a line list first
Status: not started

`ToolSearchInProject` walks up to 2500 files and 20000 directory entries, capped at 8 seconds. For every file it assigns `SL.Text := Editor.SourceText` or `LoadFromFile`, which splits the whole buffer into a `TStringList`, then `MatchSearchLines` walks that list. A 2 MiB unit is copied and split even when the pattern is absent. Open editors are then checked with `Files.IndexOf`, which scans the whole list once per editor.

Do this after 2.4, or as part of it if the disk walk moves to the worker.

Acceptance:

- Match against the raw string, or a single read buffer. Build line numbers from newline offsets. Do not assign `TStringList.Text` for the scan.
- Cap behaviour stays: 50 matches, 2500 files, 2 MiB per file, 8 seconds, 512 characters of a reported line.
- Unsaved buffers still win over disk, on the IDE thread only.
- Editor paths are matched with a case-folded set, not `IndexOf` on the walk list.
- A search of a large fixture returns the same path:line:text lines as today, aside from trailing-blank-line differences that the old `TStringList.Text` round-trip invented. If a fixture depends on that round-trip, keep the reported line text identical and document the one difference.

### 4.2 Do not rebuild the catalogue on a cache hit
Status: not started

`TAssistantService` already stores `FToolsJsonCache` for the active mode. `TAssistantToolBroker.ToolsJson` rebuilds the offer, walks `ToolAt`, and renders JSON on every read. The editor-edits test reads `ToolsJson` once per assertion, and a Claude turn reads it when the run starts. That is not a per-token cost. Do not micro-optimise it beyond the once-built table in 3.3.

No separate work unless 3.3 leaves a measured rebuild on each `ToolsJson` call. If it does, cache the rendered string on `BeginRun` and clear it in `Cancel`.

Acceptance:

- Either no code change, with a one-line note in the commit that 3.3 was enough, or a cache whose key is the run id plus the offer flags.
- A `BeginRun` after `Cancel` must not return the previous scope's JSON.
