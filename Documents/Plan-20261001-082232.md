## 1. Growing chat replies are reparsed on the UI thread

A live answer or thought under 64KB is thrown away and parsed again on every snapshot. That is the common case while the model is writing. Bodies at or above 64KB already keep the last fragment and parse on the worker.

### 1.1 Reuse the worker path for a growing reply
Status: complete

`Source/LazAssistantTools/AssistantConversationLayout.pas`.

`TConversationLayout.Add` (about lines 307–314) keeps `Full` only when `Length(Block.Body) >= 65536`. A smaller body change calls `Invalidate`, which frees both fragments. `PrepareSection` (about lines 596–614) then calls `BuildStyledMarkdown` on the UI thread whenever `LargeBody` is false. `PollParser` (about line 543) drops a finished worker job when the body is still under 64KB and `Version` has moved, so the worker cannot be used for streaming replies even if it is asked.

Symptom: each token of a normal reply reparses and relayouts the whole answer on the UI thread. The 2MB fixture in `Source/Tests/AssistantMarkdownAsyncTest.lpr` does not hit this path.

Cause: the size cut is doing two jobs. It avoids blocking the UI on a huge paste, and it forces small text to stay in lockstep with the source. Streaming does not need lockstep on the calling sync.

Fix: when a markdown section already has a `Full` fragment and only the body text changed, keep that fragment the way the 64KB branch does. Do not drop a finished worker result only because the body is under 64KB. Publish it, then schedule another parse if `Section.Version` is still ahead when the worker is idle. `RequestParse` already gives up while the worker is busy; the idle path must not forget the newer source.

Leave these as they are:

- `Finish` / `CompleteLayout` must still converge to the latest markdown. `AwaitLatest` in the async test waits for `ParsedVersion`, `FullVersion`, width, generation, and `PendingWork`.
- Font, DPI, and width-only reflow must not increment `ParseCount`. That assertion is in `TestFontAnchor`.
- A large replacement must still leave the previous reply's `Full` assigned during the first sync. Do not blank the view.

Add a check to `AssistantMarkdownAsyncTest`: lay out a short markdown answer, append one paragraph, sync once, and assert `Full` is still assigned and `ParsedVersion` is not yet the new version. Then wait, and assert the published text matches `BuildStyledMarkdown` of the new source. Run `AssistantMarkdownAsyncTest` and `MarkdownLayoutTest`.
