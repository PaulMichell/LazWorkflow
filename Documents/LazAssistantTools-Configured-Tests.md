# Configured project test execution

Implemented: 11 September 2026.

ChatGPT can now run a user-configured test command after a successful current build and report its result separately from compilation. This extends the [build/repair evidence workflow](LazAssistantTools-Build-Repair-Evidence.md).

## Settings

Open the assistant's **Settings → Project tests** with a saved project active. Enable the runner, choose its executable and enter one nonempty argument per line. Set a timeout from 1 to 3600 seconds (default 600). The working directory is always the project directory. Relative executable paths resolve there; absolute paths are also supported. Browse selects an existing executable, but settings may be saved before a project-generated runner has been built.

Arguments are passed directly to the process, without a shell or shell quoting. Spaces, quotes and shell-like text are literal. Blank argument lines are rejected because the installed FPC launcher can truncate the argument list at an empty argument. Use no argument lines for a command that takes no arguments.

Choose a runner that returns a nonzero exit code on failure. You are responsible for selecting the intended tests and arguments. No particular FPCUnit runner layout or test discovery convention is inferred. If the project build does not build the runner, build/update that executable explicitly before asking the assistant to run it.

Settings are stored per saved project path under `assistant-tests/` in the Lazarus primary configuration directory, separate from backend connections and normal project files. Merely opening Settings does not persist changes. OK saves the staged command; Cancel discards it. No active saved project means this page is disabled. A project moved to another path needs its test command configured again.

## Tool workflow

1. Save authorized edits explicitly and call `lazarus_start_build` in Build mode.
2. Poll `lazarus_build_status` with its `job_id` until it reports a current `compile_passed` result.
3. Call `lazarus_start_tests` with that ID as `build_job_id`. The tool accepts no model-supplied executable or arguments.
4. When the connection requires approval, review the exact executable, working directory, argument array, timeout, parent build ID and executable fingerprint. Configuration or binary changes during approval invalidate the request.
5. Poll `lazarus_test_status` using the returned test `job_id`. Report the result and available output. After a repair, save, rebuild and start a new test job.

Ask and Plan do not expose these execution tools. Existing connection approval settings apply. Builds and configured tests share the same asynchronous worker implementation and process-group cancellation. A workspace refuses a new build while its test command is running and refuses a second concurrent test command.

## Evidence and outcomes

Test status carries its own `job_id`, `kind: test`, parent `build_job_id`, exact command, executable fingerprint, observed-input manifest, live output and truncation flags. `testsRun` means the process actually started; check `done` and `outcome` before claiming completion.

- `test_command_passed`: the configured process exited zero with no worker error and matching observed inputs/configuration/executable.
- `test_command_failed`: it exited nonzero, independently of the preceding successful compile.
- `running`, `cancelled`, `failed` and `stale`: execution has not established a current passing result.

Before launch, the workspace requires the same successful build and unchanged observed inputs. It repeats these checks after approval. The worker fingerprints the selected executable before and after running; status also rechecks it. The executable must be a regular executable file of at most 64 MiB. Configuration changes, saved source/resource changes, dirty buffers/designers, build-mode changes and replacement builds invalidate previous test evidence.

The command's environment is inherited from Lazarus. The runner can create ordinary test outputs and has the user's process permissions. There is no shell expansion added by the assistant. The model cannot change the configured command through a tool argument; normal authorized project edits can still change project test code, which must be reviewed/built appropriately.

`verified` remains false. This step observes a configured process's exit status; it does not discover/count tests, parse an FPCUnit report, prove that the runner was generated by the parent build, freeze transitive dependencies/interpreters/libraries, or enforce the task's acceptance criteria. An exit-zero command that selects no tests does not prove the desired behavior. Describe the command and evidence accurately.

Build and test results are in memory. Starting/cancelling another assistant run discards current workspace job handles, and IDE restart loses them. Output/input bounds from the build evidence step still apply. Commands support at most 128 nonempty arguments and 32 KiB combined argument text.

## Validation

All 25 assistant regression programs and the full package build passed with range/overflow checks (`/tmp/laz-assistant-configured-tests`). The final malformed-settings regression and result-scope wording were additionally checked with the targeted runner test and package rebuild. No live model request was sent.

Tests cover exact argument persistence and execution, literal shell-like text, project isolation, malformed settings, invalid/empty arguments, disabled runners, non-executable paths, binary fingerprint mismatch, timeout/cancellation, source mutation during tests, separate failed-test outcomes, parent build IDs, approval denial and configuration changes during approval, stale evidence after settings/new builds, UI validation and Save/Cancel behavior. The Project tests page was also captured and visually checked.

After rebuilding/restarting Lazarus, configure your real test runner and ask in Build: “Build this project and run its configured tests. If either fails, inspect the output, propose a repair and rerun the relevant checks. Report the build and test results separately.” Live project/runner acceptance remains to be performed by the user.
