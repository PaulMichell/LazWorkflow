### 2.1 Preserve a saved TLS fingerprint

Also refuse a stored pin that is nonempty but does not normalise to 64 hex characters. Do not fall through to `TrustAllManager` for that record.

### 2.2 Deliver inbound messages without dropping them
Status: complete

Review finding B2, high. `onFrame` calls `inbound.tryEmit` and ignores the result. The shared flow replays 32 and uses the suspending overflow policy, so `tryEmit` fails once the collector is behind. `SessionState.apply` has already run. An approval, transcript part, image part, or snapshot can then be gone from the UI while the session believes it was delivered.

Replace that publish path with an ordered queue the read coroutine actually waits on. Capacity stays bounded (32 is enough). Coalesce only messages whose latest copy supersedes the previous one: Snapshot, Status, Mode, Target, Plan, and Tasks. Never coalesce Transcript, TurnData, ImageData, ImageUnavailable, ApprovalRequested, ApprovalClosed, InsertResult, Error, Rejected, Bye, PairOk, HelloOk, or Ping.

The wait must be visible. If the collector does not take a non-coalesced message within `MonitorLimits.DeadSessionMs`, close the link and publish a disconnect banner. That is a failed delivery, not a silent drop. Do not suspend the only loop that can notice the deadline: the clock check has to run during the wait. Use a monotonic clock (`System.nanoTime`), injected so the test does not sleep. Ping transmission does not count as inbound activity.

Extract the queue so the test calls the same publish operation production uses. Holding the collector after the first event and publishing 64 further non-coalesced events must deliver all 65 in order. A burst of Status while the collector is held must deliver the latest Status, not drop an ApprovalRequested that was published in the same burst.

### 2.3 Bound image assembly as parts arrive
Status: complete

Review finding B5, high. `ImageAssembly.accept` stores every part and only then sums sizes. `partCount` is not capped, the sum is an `Int`, and a different image id resets the only assembler. The review retained six 190,000-byte parts with `partCount = 100` (1,140,000 bytes) without hitting `MaxImageFetchBytes` (1,048,576). Both `SessionState` and `MonitorViewModel` own an `ImageAssembly`, so the cap belongs in that class, not in one caller.

On each part, before retaining it:

- Reject `partCount` outside `1..MaxImageParts` without iterating to `partCount`. Add `MaxImageParts` next to the existing image limits in `MonitorLimits`. The desktop sender uses at most six parts (`ceil(1048576 / 190000)`). Use 32 so a legal sender that chooses smaller chunks still fits, and a hostile `partCount` of 100 or `Int.MAX_VALUE` does not. Do not change the desktop codec.
- Track retained bytes as `Long`. A replacement subtracts the previous part's size before adding the new one. If the assembly would exceed `MaxImageFetchBytes`, drop that assembly and return null. Do not store the oversized part.
- Key open assemblies by image id and revision so one image's parts are not discarded, or allowed to bypass the cap, because another image's part arrived. Cap the number of open assemblies (8) and the total retained bytes across them (`MaxImageFetchBytes`).
- Reject an assembly whose mime, width, height, or part count changes for the same id and revision.
- Expire an incomplete assembly. `accept` takes `nowMs`. Drop an assembly older than a named TTL (60 seconds) instead of joining it to a later part. No timer thread in the protocol class.

Files: `protocol/src/main/kotlin/computing/michell/monitor/protocol/SessionState.kt`, `Messages.kt` only for the new limit constant, and a protocol unit test. Update the `Messages.kt` size note date only if that file changes.

Tests: the six-part hostile case is rejected on the part that crosses the byte budget, not after part 100. Duplicate parts do not double-count. A second image id does not erase a bounded first assembly and does not raise the global byte cap. Inconsistent metadata rejects. An expired partial does not complete with a later part. A six-part image at the desktop chunk size still assembles.

Do not decode bitmaps here. Do not remove the second assembler; that is 5.2.

## 3. One coordinator

### 5.3 Read frames without copying the whole buffer
Status: not started

Review finding O4, medium. Depends on 2.2 and 2.4, which own the read loop. Each 8 KiB read copies the chunk and concatenates it with every pending byte. Consuming a frame copies the remainder again.
