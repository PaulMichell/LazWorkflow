## 1. Overview

This plan comes from a read-through of every unit in `Packages/LazAssistantMonitor.lpk` (`Source/LazAssistantMonitor/*.pas` and the form `.lfm`). It lists bugs first, then threading and lifetime, then protocol data loss, then hot-path optimisations, then simplifications. Nothing was compiled or run during the review. A finding that rests on library behaviour I did not run is marked **confirm first**. Its first step is a failing test.

Goals:

- Every frame the host writes is valid JSON inside a LAM1 frame. Today some state frames are not, and those can reach the socket as raw bytes.
- No use-after-free, and no silent event loss in the mirror log.
- Inbound and outbound frames are parsed once, not three or four times. The link loop takes one outbox lock per pass, not a dozen.
- Remove dead code and duplicate helpers that make the next change harder.

## 2. Wire correctness

The most serious problems are here. A Windows project path, or a status text with a quote in it, can disconnect the phone, and the phone then reconnects into the same failure.

### 2.1 Build every hand-written JSON frame with an encoder
Status: complete

Verified 2026-11-06 at `e0ceba8` through the target test runner: `AssistantMonitorEscapeTest`, `AssistantMonitorSessionTest`, `AssistantMonitorCodecTest`, `AssistantMonitorMirrorTest` and `AssistantMonitorProtocolV3Test` all pass (exit 0). Getting there needed `1b553a0` (the escape test's missing `uses` entry) and `3884753` (the mirror escape checks used a body over the 8 KiB inline limit, so it never reached the page). The Session and Codec tests also had failures from before this plan; `b39d98f` and `e0ceba8` brought them up to date. Committed in `48bbdb1`, together with 2.2, 2.3, 2.4, 3.2 and 3.6.

Problem. Several producers concatenate user-visible text into JSON without escaping it:

- `AssistantMonitorBridge.pas` `PublishStateKeys` (≈ lines 639–739) and `ChoiceArray` (≈ 620). These carry status text, error text, model notes, paths, target roots, plan and task titles and summaries, and conversation titles. A Windows path such as `C:\Users\…` produces an invalid escape. A quote ends the string early.
- `AssistantMonitorSession.pas` `HandleResume` (≈ 1701–1711). This writes the approval tool id and the conversation id raw.
- `AssistantMonitorSession.pas` `ServeBlockGet` (≈ 2795). `revision_changed` writes `Id` and `BlockId` raw. `BlockId` comes from the phone payload and is not checked by `MonitorMessageIdIsSafe`.
- `AssistantMonitorImages.pas` chunk and bulk envelopes (≈ 363, 430). These write `Id` and `ItemType` raw.
- `AssistantMonitorSync.pas` `JsonEscape` escapes only `"` and `\`. `AssistantMonitorMirror.pas` `JsonEscape` escapes seven characters and leaves the other controls below `#32` raw (for example ESC in tool output). Raw control characters are not valid JSON. fpjson and kotlinx may each accept or reject them (**confirm first**). Either way, the output should be valid.

Fix. Add one escaping routine, built on fpjson `StringToJSONString` or an equivalent that escapes every character below `#32`. Use it everywhere, or build the payload with `TJSONObject`. Remove both local `JsonEscape` copies. Validate any id or block id that comes from the phone before echoing it back.

Test. Add codec and session tests that publish status, targets, conversations and plan rows containing `"`, `\`, a Windows path, a newline, a tab, `#27`, and non-ASCII text. Assert that every queued frame passes `TryDecodeMonitorFrame` and decodes back to the original strings.

### 2.2 Stop queuing raw JSON when a frame fails to encode
Status: complete

Verified 2026-11-07 at `588215d` through the target test runner: `AssistantMonitorSessionTest`, `AssistantMonitorLockupTest`, `AssistantMonitorLinkTest` and `AssistantMonitorGrainTest` all pass (exit 0). This item's `EncodeHostFrame` change was not the cause of the Link test failures (12 checks on 2026-11-06). There were two causes:
- `ec8daf6` made `AddBulk` wake the writer, which broke the link's ping hold-off (4.2). It was undone in `a07be2d`.
- 2.1's switch to `JsonEscapeText` made the mirror's quadratic `block_append` slicing take about 55 s for an 800 KiB append on the IDE thread. The silent client then tripped the session's 30 s heartbeat, and every later check failed on the closed socket. Fixed in `588215d` by cutting slices in linear time, with `TestLargeAppend` in the mirror test.

`5d2f3d0`, `5fb560b` and `e5f0f36` add the diagnostics that found this: session and link log lines, and credit-check timings, are now printed by the Link test.

Done in `48bbdb1`. `EncodeHostFrame` is now a private session method. When `TryEncodeMonitorFrame` fails it returns no bytes, adds one to `FFramesDropped`, and logs a warning `frame not encoded type=<type> status=<mfs…> bytes=<n>`. The type is read by a text search and cut to `[a-z0-9_]`, at most 32 characters, so no frame content is logged. Call sites are unchanged. Control and state paths still call `CloseForQueueFailure`. `PublishState` and `QueueResumeAnswer` still skip the frame, and now the skip is counted and logged. The session tests' live-part placeholders are now real envelopes (`LivePart`). The new `TestEncodeFailureNotQueued` uses a fresh session. It queues invalid JSON, a state value that is not JSON, and a placeholder live part. For each one it checks that `OutboundCount` stays 0, that `TakeOutboundFrame` returns nothing, and that `FramesDropped` rises by one. Left alone: the `Transmit(String(Bytes))` fallback in `DrainOutbound`, now unreachable for host frames. `PublishState` from the IDE thread still increments the counter without the lock (see 3.3).

Problem. `EncodeHostFrame` in `AssistantMonitorSession.pas` (≈ 678–694) falls back to `Bytes := Json` whenever `TryEncodeMonitorFrame` reports `mfsBadJson`. The comment says this keeps test placeholder strings working. In production, the link then writes bytes with no LAM1 header. The phone reads a bad magic and drops the link. On resume, `PublishRememberedState` republishes the same bad state, so the phone reconnects into the same failure.

Fix. Remove the fallback. An encode failure counts as `FFramesDropped` and logs the frame type and the status. A control frame that fails to encode closes the link, as `CloseForQueueFailure` already does. Change the session tests that pass placeholder strings so they pass real envelopes.

Test. A session test queues invalid JSON and asserts that nothing is put in the outbox and the dropped count rises.

### 2.3 Split state chunks and previews on UTF-8 boundaries
Status: complete

Verified 2026-11-06 at `e0ceba8` through the target test runner: `AssistantMonitorMirrorTest`, `AssistantMonitorSessionTest`, `AssistantMonitorCodecTest` and `AssistantMonitorProtocolV3Test` all pass (exit 0).

Done in `48bbdb1`:

- `AssistantMonitorFrames.MonitorUtf8CutLength(Text, Limit)` is the shared cut helper (see 6.2). It returns the longest prefix of at most `Limit` bytes that does not end inside a UTF-8 character. If the first character alone is longer than `Limit`, it returns that whole character.
- `Preview` now uses the helper.
- `MonitorSyncStateFrames` cuts the raw value, before escaping, at character boundaries. It works out the part count after cutting. It also halves a piece whose escaped form exceeds 28000 bytes, so a quote-heavy value still fits the 32 KiB chunk.
- `QueueResumeAnswer` needed no change. Since 2.2, `EncodeHostFrame` counts and logs any frame that fails to encode.
- Tests are in `AssistantMonitorMirrorTest`:
  - helper edge cases
  - a 36 KiB state value of euro signs that starts at an odd offset: every chunk encodes and fits 32 KiB, and the joined `data` equals the value byte for byte
  - a prompt whose 80th byte is inside a character: the snapshot page encodes, and the preview is the 79-byte prefix.

The same file's old check "other controls stay raw" contradicted 2.1. It is now "other controls are escaped" (`\u0001`).

Problem.

- `MonitorSyncStateFrames` (`AssistantMonitorSync.pas` ≈ 449–476) cuts `ValueJson` every 20000 bytes. That can split a multi-byte character, and possibly a `\u` escape. Each chunk then fails the strict UTF-8 check in `TryEncodeMonitorFrame`, and `PublishState` exits without a word. A long conversation list with non-ASCII titles never reaches the phone.
- `Preview` (Sync ≈ 239) takes `Copy(Text, 1, 80)` bytes of the prompt. That breaks UTF-8 in the same way, and the snapshot page is then lost.
- `QueueResumeAnswer` (Session ≈ 2611–2621) does `Continue` past a frame that fails to encode. A resume can lose its page without anything being reported.

Fix. Use one UTF-8-safe cut helper (see 6.2) for chunk data and for previews. Cut chunk data before it is escaped, or step back over an escape sequence. Log, and count, any frame that `QueueResumeAnswer` cannot encode.

Test. Publish a state value over 32 KiB made of 3-byte characters, and a prompt whose 80th byte falls inside a character. Assert that every chunk encodes, and that the reassembled value equals the input.

### 3.3 Make cross-thread link and session fields safe
Status: complete

Verified 2026-11-07 with `instantfpc Tests/RunAssistantTests.pas --lazarus-root /home/paul/Projects/FreePascal/Lazarus --only AssistantMonitorChaosTest --only AssistantMonitorLockupTest --only AssistantMonitorLinkTest --only AssistantMonitorSocketTest --define DEBUG`. The run printed `Build flags: -dDEBUG`. All four passed. The monitor package lazbuild log has `Param[32]="-dDEBUG"`. The Link and Socket binaries contain `StartReplace was called on the link's own thread`, so the test compiles had `-dDEBUG` as well. That assertion did not fire. The earlier normal-build note stands: on 2026-11-07 at `588215d` the same four passed, and the old link receives `bye replaced` again.

Link half, done in `7b0e252` (committed, not compiled; this target has no build input, the session had no shell, and `AssistantMonitorLink.pas` had no other pending changes):

- `Replacing` is now `ReplaceFlag: LongInt` (0 idle, 1 claimed, 2 published), read through a private `Replacing` function using `InterlockedExchangeAdd(…, 0)`. `StartReplace` claims the flag with `InterlockedCompareExchange`, writes `ReplaceUntil` once, then publishes with `InterlockedExchange`. The link reads `ReplaceUntil` only after `Replacing` is true.
- Departure from the Fix text: `ReplaceUntil` has no 64-bit interlocked store. The flag's full barrier orders the one write before any read, so a 32-bit target cannot read half of it, and `InterlockedCompareExchange64` is not needed on targets that may lack it.
- `ByeState` reads go through `ByeQueued`. `RetiredSet` is now `RetiredFlag: LongInt`, set and read through Interlocked calls.
- `Retain` is `InterlockedIncrement`. `Release` is a compare-and-swap loop that never takes the count below zero, as before. `Held` is an interlocked read. `RefLock` is removed.
- Under `-dDEBUG`, the unit turns assertions on, and `StartReplace` asserts `GetCurrentThreadId <> ThreadID`.

Session half, done in `410611c` (compiled with lazbuild, tests not run):

- `Property State` reads `GetState`, and `Property CloseRequested` reads `GetCloseRequested`. Each getter takes `LockSession`. The session's critical section is recursive, so callers that already hold the lock still work.
- A private locked `LinkPulls: Boolean` is read once in `FlushLivePatch`, `TakeOutboundFrameWithLane` and `DrainOutbound`. `PullPlanSlice(Pulls)` takes the caller's value, so it does not read the field again, and in `DrainOutbound` the pull and the wake use the same reading.

Problem.

- In `TMonitorLinkThread`, `Replacing`, `ReplaceUntil` and `ByeState` are written by another link's thread through `StartReplace`, and read without a barrier. `RetiredSet` is read in `WaitRetired` the same way.
- `Retain`, `Release` and `Held` take a critical section for a plain counter.
- In `TMonitorSession`, `FLinkPulls` (`TakeOutboundFrame`, `FlushLivePatch`), `FCloseRequested` (the `CloseRequested` property) and `FState` (the `State` property, read by `AssistantMonitorListenerRunning` and the form) are read without the session lock.

Fix. Use `InterlockedExchange` and `InterlockedExchangeAdd` (or `TAtomic`-style helpers) for the link flags and the reference count. Turn the session properties into locked getters. Keep `ReplaceUntil` as a value written once, through an interlocked 64-bit store.

Test. The existing `AssistantMonitorChaosTest` and `AssistantMonitorLockupTest` still pass. Under a `-dDEBUG` build, add asserts that `StartReplace` is not called on the link's own thread.

### 3.5 Avoid a double free after a failed hand-off
Status: complete

Verified 2026-11-07 at `588215d` through the target test runner: `AssistantMonitorSocketTest`, `AssistantMonitorLinkTest`, `AssistantMonitorChaosTest` and `AssistantMonitorAcceptance` all pass (exit 0). The code review this item asks for is done (below).

Done in `9b8b736` (committed, not compiled; this target has no build input and the session had no shell):

- The Fix text's first option, starting the link before `TakeAccepted`, is not safe. A link that finishes at once runs `ReleaseAccepted` in `Execute`'s `Finally`, before it owns the stream, so the stream could be left with no owner. The second option is used instead.
- After `TakeAccepted`, `Handoff` sets `Result := True`. It then grows `FSlots` and calls `Link.Start` inside `Try…Except`. On failure it reports the exception, drops the slot if it was added (it is always the last one, and only the listen thread changes `FSlots`), and frees the link inside its own `Try…Except`.

Paths checked by reading the code:

- `Link.Create` raises, or `WakeOpen` is false: `Result` is False and the link never took `Data`. `HandleConnect` frees `Data` once. Unchanged.
- `SetLength` raises: no slot was added. `Link.Free` releases `Data` through `ReleaseAccepted`. `Handoff` returns True, so `HandleConnect` does not free `Data`.
- `Link.Start` raises: the new slot is dropped, and `Link.Free` releases `Data`. `Handoff` returns True. Before the fix, `Result := True` was set but the exception escaped, so `Owned` stayed False, `HandleConnect` freed `Data` a second time, and the dead link stayed in its slot.
- `Link.Free` on a link that never started: the existing `WakeOpen` failure path already does this. `ReleaseAccepted` sets the field to Nil before it frees, so the destructor and `Execute`'s `Finally` cannot both free the stream.

Problem. In `TMonitorListenThread.Handoff` (`AssistantMonitorLan.pas` ≈ 1012–1043), `Link.TakeAccepted(Data)` is called before `SetLength(FSlots…)` and `Link.Start`. If either of those raises, `HandleConnect` frees `Data` while the link still owns it, and the link is leaked.

Fix. Add the slot and start the link before `TakeAccepted`. Otherwise, wrap the tail in `Try…Except`, and on failure `Link.Free` (which releases the accepted stream) and return `True`.

Test. Read the code and go through the paths. There is no fault-injection hook, so a unit test is not practical.

## 4. Protocol state, data loss and security

### 4.1 Record a mirror event that cannot be stored
Status: complete

Problem. In `TMonitorMirror.AppendLocked` (`AssistantMonitorMirror.pas` ≈ 457–481), when the log is full of unacknowledged events, `DropOldestLocked` refuses and the method exits. It neither advances `FHead` nor calls `NoteDropLocked`. The event is lost, but the model already holds its effect. The next event reuses the same sequence number. A phone that resumes from an older sequence passes `TailHeld` and replays a log that looks complete but is missing changes. This happens whenever a phone stays disconnected while about 8 MiB of conversation accumulates.

Fix. When an event cannot be stored, advance `FHead` and call `NoteDropLocked(Seq)`. A resume behind that point then falls back to a snapshot, as it already does for an oversize event.

Test. A mirror test sets a small budget with `SetLogBudget`, acknowledges nothing, appends past the budget, and asserts that `DroppedThrough` has moved. It then asserts that `MonitorSyncResumeAnswer` for an old sequence returns a snapshot, not a replay.

### 4.2 Send the credit-overflow bye once

## 5. Hot-path optimisations

### 5.1 Parse each outbound frame once
Status: not started

Problem. `TMonitorSession.QueueSend` parses every frame:

1. `LogFrameSeq` runs `GetJSON` over the whole frame.
2. `MonitorSyncClassify` runs a text search.
3. `EncodeHostFrame` → `TryEncodeMonitorFrame` → `PayloadIsJsonObject` runs `GetJSON` again, after `IsStrictUtf8`.
4. `HostLane` → `TryDecodeMonitorEnvelope` runs `GetJSON` again and re-serialises the payload with `AsJSON`.
5. On failure, `FrameIsBye` runs `GetJSON` again.

Frames go up to 256 KiB. Separately, `EncodeMonitorEnvelope` clones the payload object before freeing the original.

Fix. Add `QueueFrame(Const Json: String; Lane: TMonitorSyncLane; Const StateKey: String; Seq: Int64)` for producers that already know the lane: the codec encoders, the sync answers, plan fetch, block fetch and the bridge state keys. Add a trusted `EncodeMonitorFrameBytes` that writes the header with no JSON parse. Keep the full validation in `TryEncodeMonitorFrame` for tests and for any frame whose origin is unknown. In `EncodeMonitorEnvelope`, add the payload directly instead of cloning it. This replaces the short-term fix in 2.4.

Test. The existing session and outbox tests still pass. Add a counter test, under a test define, that queuing one state frame performs at most one JSON parse.

### 5.2 Parse each inbound frame once
Status: not started

Problem. Each inbound frame is parsed several times:

- `FinishPayload` (`AssistantMonitorFrames.pas`) copies the payload twice (`Raw`, then `Json`) and runs `GetJSON` only to check that it is an object.
- `TryDecodeMonitorEnvelope` parses again and re-serialises the payload.
- `ApplyTextLimit` parses the payload again for send and steer.
- Each `Decode*` parses it once more.
- `MonitorMessageKindFromName` loops over 58 kinds, building a case-string for each.

Fix. Let the frame layer check UTF-8 and length only. Let the envelope decoder be the one JSON gate. Keep the parsed payload object in `TMonitorMessage`, owned and freed by the caller, or decode the typed payload in the same pass. Replace the kind lookup with a constant name table and a sorted or hashed lookup. Remove the second copy in `FinishPayload`.

Test. `AssistantMonitorCodecTest` and `AssistantMonitorProtocolV3Test` still pass. The frame tests for bad UTF-8, bad JSON and oversize frames still return the same statuses, now from the envelope layer where needed.

### 5.3 Ask the outbox once per link pass
Status: not started

Problem. One pass of `TMonitorLinkThread.RunLink` calls `FrameReady` three or four times (`WantsWrite`, the hold-off check, `If Not FrameReady`, `CheckDeadlines`).

- Each call takes the outbox lock five times (`LaneCount` × 4 and `HeldLogCount`).
- Each call then calls `Host.OutboundPending`, which is `IsController` plus `CopySession` plus `OutboxPending`. `OutboxPending` runs `FillLogLane`, which takes the session lock, and `OutboundCount`, which takes five more locks.
- `NoteTime`, `NotePartialFrame`, `OutboundCount` and `CloseRequested` each add `IsController` and `CopySession` again.

Fix.

- Add `TMonitorOutbox.HasFrame` and `PendingFrameCount`, each answered under one lock.
- Compute "frame ready" once per pass and pass it along.
- Cache the controller check for the pass, since `IsController` changes only at adopt and release.
- Run `FillLogLane` only when the mirror head or the phone's ack has moved. Keep the last values seen.

Test. The existing link, socket, lockup and chaos tests still pass. In `AssistantMonitorLinkTest`, measure the passes per second, or the lock acquisitions per frame, before and after, and record both numbers in this item.

### 5.4 Index mirror events by sequence
Status: not started

Problem.

- `FindSeq` (Sync), `IndexOfSeqLocked` and `PatchIndexLocked` (Mirror) are linear searches. `TailHeld`, `MonitorSyncCanReplay` and `TryReplayPatches` call them once per sequence, which makes them O(n²).
- `MonitorSyncFill` calls `UnackedBytes` for every candidate event. `UnackedBytes` rebuilds `EventFrame` for every unacknowledged event, which is O(n²) string building on the link thread.
- `MonitorSyncFill` also copies the whole log with `CopyEvents` on every call.
- `DropOldestLocked` shifts the whole array on each drop.
- `TryReplayPatches` grows its result by one element at a time.

Fix.

- Sequences in the live log are contiguous from `FEvents[0].Seq`. Keep a head offset (or a ring) and find an event by `Seq - FirstSeq`.
- Keep a running count of framed unacknowledged bytes. Add on queue, subtract on ack.
- Let the fill take the next event under the mirror lock instead of copying the whole log.
- Pre-size result arrays.

Test. `AssistantMonitorMirrorTest`, `AssistantMonitorGrainTest` and `AssistantMonitorProtocolV3Test` still pass. Add a timing check: 20 000 small events filled and replayed in under a set bound.

### 5.5 Remove O(n²) deletes from the front of a buffer
